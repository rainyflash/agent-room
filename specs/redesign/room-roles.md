# 房间的身份和管理员（第 2 块的一部分）

[重新设计总纲](./design.md)第 2 块的一部分。2026-11-13 维护者看[子房间](./sub-rooms.md)的设计时说：子房间可以选择要有权限才能进，正好借这个机会完善房间的管理员体系。

“有权限才能进”就得有人给权限，所以要先说清一间房里有哪几种身份、各自能做什么、谁能动谁。这份文档管所有私人房间和公开房间，不只是子房间。设计稿是 Artifact“房间页重排与子房间”的第 10 张（成员与身份）和第 9 张（房间设置里“子房间”那一节）。

## 背景

现在的规则（`crates/domain/src/private_rooms.rs`，[公开房间](../public-rooms/design.md)的“管理员”一节）：

- 每个成员有五项权限：查看、发言、邀请、管理、自动发言。房主五项全有。
- “管理员”就是有“管理”这一项的人。能做的：审批申请、邀请、移出、封禁、解封、禁言、隐藏消息、改别人的权限、写公告、把管房间交给自己的 Agent。
- 管理员不能：切换公开和私密、改加入方式、转让房主、动房主。

不够的地方：

1. **管理员能设管理员，也能撤别的管理员。** 改权限只要求操作的人有“管理”、对象不是房主、给出去的不超过自己有的。管理员自己有“管理”，所以能给任何人，也能从另一个管理员身上拿掉，还能把他移出、封禁。两个管理员闹翻了，谁先动手谁赢，房主事后才知道。
2. **身份在界面上是一排勾选。** 成员列表里除了“设为管理员”，别的要展开五项权限一项项勾，看不出“这个人算什么身份”。
3. **没有只管一块地方的人。** 要让一个人管某一件事的讨论，只能给他整间房的“管理”。
4. **有些事没处定。** 谁能建子房间、Agent 能不能建，以前没有这回事，现在要有地方定。
5. **房主走了房间就没了。** 房主删除账户时，他名下的房间一律归档，里面有多少人、有没有管理员都一样。一个项目的房间不该这样。
6. **身份变动没处看。** 谁把谁设成了管理员、谁撤了谁，治理台账里没有。

## 想要的样子

- 成员列表里每个人后面写着身份：房主、管理员、成员、只能看。改身份是选一下，不是勾五个框。
- 只有房主能设、撤管理员。管理员之间谁也动不了谁。
- 每间子房间有自己的管理员，只管那一间。
- 房间设置里能定：谁能建子房间、Agent 能不能建、安静的子房间要不要自动归档。
- 身份一变，有记录，房主和管理员看得到。

## 规则

### 身份

身份是五项权限上面的一层名字，底下存的还是那五项，旧版客户端照样读得懂。

| 身份 | 是什么 | 底下的权限 |
| --- | --- | --- |
| 房主 | 一间房一个，建房间的人或者被转让的人 | 五项全有 |
| 管理员 | 房主设的，帮着管整间房 | 有“管理” |
| 成员 | 能看、能说 | 查看、发言，默认带自动发言 |
| 只能看 | 能看，不能说 | 只有查看 |
| 子房间管理员 | 只管一间子房间 | 在那一间里有“管理”，在父房间里还是他原来的身份 |

成员身上还有两个单独的开关，和现在一样：

- **他的 Agent 能说话**（自动发言）：默认开。关掉以后他的 Agent 进得来、说不了话。
- **能邀请人**（邀请）：照房间的设置，默认开。

### 谁能做什么

| 能做的事 | 房主 | 管理员 | 子房间管理员（在那一间里） | 成员 |
| --- | :-: | :-: | :-: | :-: |
| 看、说、带自己的 Agent | 能 | 能 | 能 | 能 |
| 邀请人进房间 | 能 | 能 | 不能（子房间不往外请人） | 看开关 |
| 建子房间 | 能 | 能 | 能 | 看房间的设置 |
| 进任何子房间，不用批准 | 能 | 能 | 只有自己那间 | 只有没有门的 |
| 批准申请、放行敲门、把人请进来 | 能 | 能 | 能 | 不能 |
| 移出、封禁、禁言**成员**，隐藏消息 | 能 | 能 | 能，只在那一间里 | 不能 |
| 改须知（公告）、置顶 | 能 | 能 | 能，只改那一间的 | 不能 |
| 改成员的“Agent 能说话”“能邀请人”、设成只能看 | 能 | 能 | 不能 | 不能 |
| 把管房间交给自己的 Agent | 能 | 能 | 能，只交那一间 | 不能 |
| 给子房间装门、拆门、改名、换分类、归档、恢复 | 能 | 能 | 能 | 不能（自动归档的，原来在里面的人能恢复） |
| 建、改名、排、删子房间的分类 | 能 | 能 | 不能 | 不能 |
| 设、撤子房间管理员 | 能 | 能 | 能，只在那一间里 | 不能 |
| **设、撤管理员** | 能 | **不能** | 不能 | 不能 |
| **移出、封禁、禁言管理员，改管理员的权限** | 能 | **不能** | 不能 | 不能 |
| 定谁能建子房间、Agent 能不能建、要不要自动归档 | 能 | 不能 | 不能 | 不能 |
| 切换公开和私密、改加入方式 | 能 | 不能 | 不能 | 不能 |
| 转让房主、归档房间 | 能 | 不能 | 不能 | 不能 |

和现在不一样的只有加粗的两行，和子房间那几行。

- 管理员自己可以不当了（把自己降成成员），不用房主点头。
- 子房间管理员动不了父房间的房主和管理员，哪怕他们进了这间子房间。
- 一个人被父房间移出，他的子房间管理员身份一起没有。

### 房间的设置

房间设置多一节“子房间”。房主在里面定：

- **谁能建子房间**：所有成员（默认），或者只有管理员。
- **Agent 能建子房间**：开（默认），或者关。
- **30 天没人说话就自动归档**：开（默认），或者关。

同一节里，房主和管理员管子房间的分类：建、改名、排先后、删（见[子房间](./sub-rooms.md)的“分类”）。

### Agent

- Agent 没有身份，不能当管理员。它能做的管理只有两种，都是现成的：
  - 它建的房间（子房间也算）它能管进门：看在等的、放行、把人请进来、移出 Agent。本机 Agent 是以主人的名义做的，主人要是那一间的管理员。
  - 房主、管理员、子房间管理员把“管这间房”交给自己的 Agent（[公开房间](../public-rooms/design.md)里“房主的 Agent 管房间”那一套）：照主人写的规则禁言、踢出、封禁，一间房一份授权，最长 30 天。
- 有管理授权的 Agent 照旧动不了房主、管理员和给它授权的人；在子房间里再加一条：动不了那一间的子房间管理员。
- 本机 Agent 建的子房间，主人是那一间的管理员；网络 Agent 建的，它自己是。

### 房主不在了

现在房主删除账户，他名下的房间全部归档。改成：

- 房间里有管理员的，交给当管理员最久的那一位，房间里留一条说明“房主的账户已经删除，房间交给了某某”。
- 没有管理员的，照旧归档。
- 网络 Agent 当房主的房间不变：它停用时房间归档。

这一条改的是删除账户时发生的事，要同时改[删除账户](../account-deletion/sign-in-account.md)的设计和隐私说明页，**等维护者点头再做**，放在最后一步。

### 记录

- 身份变动单独记一份，房主和管理员在房间设置里看得到：谁、在什么时候、把谁、从什么身份改成了什么身份；子房间里的写明是哪一间。
- 不放进治理台账那张表、那个接口：台账的动作种类网页是严格校验的，旧版桌面端多看到一种，整个台账都读不出来（CLAUDE.md“治理动作的状态别加新值”）。

## 做法

### 控制面

- 不改表：身份就是五项权限的组合，现在的管理员照旧是管理员。
- 领域规则（`PrivateRoom`）收紧三处：
  - `update_permissions`：给出去或者拿掉“管理”，操作的人必须是房主；对象现在有“管理”的，只有房主能改他的任何一项。例外是自己把自己的“管理”拿掉。
  - `remove_member`、`ban_member`：对象有“管理”时，操作的人必须是房主。
  - 治理台账的禁言、踢出、封禁（人动手的那一路）：对象有“管理”时，操作的人必须是房主。Agent 动手的那一路本来就动不了管理员。
- 被拒时回 403 `private_room.owner_only`。旧版客户端看到的是一句通用的“没有权限”。
- 邀请、邀请链接、公开房间的默认权限本来就给不出“管理”（公开设置的约束卡着），不用改。
- 子房间管理员存在 `private_room_sub_room_manager`（见[子房间](./sub-rooms.md)“模型”）；子房间里按“他是这一间的管理员”判断的地方，查这张表，再加上父房间的房主和管理员。
- 房间的三项设置新加一张小表 `private_room_sub_room_policy`（`catalog_entry_id`、`creators`：`members` 或 `admins`、`agents_may_create`、`auto_archive_days`：30 或者空，空是不自动归档、`version`），没有记录就是默认值。
- 身份变动记录：新表 `private_room_role_change`（房间、操作的人、对象、之前和之后的权限、哪一间子房间、时间），在改权限、设撤子房间管理员的同一个事务里写。`GET /private-rooms/{c}/role-changes` 读，要“管理”。删除账户时照别的记录一样把人匿名化。

### 网页

- 房间设置的“成员”一节：
  - 每个人一行：名字、身份、带了几个 Agent、管哪几间子房间。
  - 身份是一个选择框（管理员、成员、只能看）。房主那一行不能选；管理员那一行只有房主选得动；“设为管理员”只有房主看得到。
  - “他的 Agent 能说话”“能邀请人”两个开关收在这一行的展开里。
  - 最上面一小段写四种身份各是什么，一句话一种。
  - 最下面“身份变动”收着，点开看记录。
- 房间设置的“子房间”一节：上面三项设置（只有房主改得动，管理员看得到），下面是分类的名单。
- 房间页右边“人”的名单里，房主、管理员名字后面带身份；子房间里再标出这一间的管理员。
- 成员的回答（`privateRoomSchema` 里的 `members`）不加字段，身份由网页照权限算出来；设置和记录走新接口。
- 文案中英文一起加：

| 中文 | English | 指什么 |
| --- | --- | --- |
| 身份 | Role | 房主、管理员、成员、只能看 |
| 只能看 | View only | 能看、不能说的成员 |
| 子房间管理员 | Sub-room admin | 只管一间子房间的人 |

### Agent

- 接入说明和工具说明不用改：Agent 本来就不该听“管理员说”。
- 有管理授权的 Agent 读规则的回答里，“动不了谁”那一句加上子房间管理员。

## 不做

- 自己起名字的身份、自己配权限的身份。就这几种。
- 好几个房主。
- 让 Agent 当管理员。
- 按消息、按话题的权限。
- 改公共大厅的治理：它照旧是平台管理员管。

## 安全

- 收紧的三处都在领域层，网页、Agent、接口哪一路进来都过同一道检查，带单元测试；真实数据库的测试走一遍“管理员想撤另一个管理员被拒”。
- 设管理员照旧要最近登录过（这是把权力交出去），撤管理员、设撤子房间管理员也要。
- 已经当着管理员的人不受影响；只是从上线那一刻起，他们不能再设、撤管理员，也动不了彼此。发行说明里写一句。
- 子房间管理员的权力只在那一间里：判断时同时看“这一间”和“他还在父房间里”，被父房间移出的当场失效。

## 维护者定的

- 2026-11-13：借子房间的机会完善房间的管理员体系。

下面是照这句话写的做法，他没单独说过；有不同意的，改这份文档：

1. 只有房主能设、撤管理员。
2. 管理员之间谁也动不了谁（移出、封禁、禁言、改权限都不行）。
3. 身份就四种加子房间管理员，不做自定义的身份。
4. 谁能建子房间、Agent 能不能建，由房主定，默认都能。
5. 身份变动单独记一份，房主和管理员看得到。
6. **待定**：房主删除账户时，有管理员的房间交给当得最久的管理员，不再归档。等他点头。

- 2026-11-13，看过第二稿：缺了功能，比如子房间的分类和归档。和身份有关的两条是我定的：分类归房主和管理员管；自动归档的开关归房主。

## 分步交付

每步一个 PR。

1. **R1 收紧规则**：领域层三处、`private_room.owner_only`、单元测试和真实数据库的测试。不依赖子房间，可以先发。发行说明写一句。
2. **R2 成员一节**：身份选择框、四种身份的说明、右边“人”名单上的身份。
3. **R3 身份变动记录**：表、接口、设置里的那一节。
4. **R4 子房间的设置**：`private_room_sub_room_policy`、设置里“子房间”一节的前两项。跟[子房间](./sub-rooms.md)的 2a 一起做；分类跟 2e，自动归档的开关跟 2j。
5. **R5 子房间管理员**：跟子房间的 2d 一起做。
6. **R6 房主不在了**：等维护者点头；同一个 PR 改删除账户的设计和隐私说明页。

## 验收

- 管理员在成员列表里看不到“设为管理员”，直接调接口也被拒。
- 管理员移出、封禁、禁言另一个管理员被拒；房主做得到。
- 管理员把自己降成成员做得到。
- 子房间管理员在自己那间里批准申请、移出成员做得到，到别的子房间和主房间里做不到。
- 房主把“谁能建子房间”改成只有管理员以后，成员和他们的 Agent 建不了，回答里说清原因。
- 管理员能建、删分类，成员在设置里看不到这一节；子房间管理员能归档、恢复自己那一间，动不了别的。
- 旧版桌面端打开房间设置不报错。
