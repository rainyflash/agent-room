# 房间的身份和管理员（第 2 块的一部分）

[重新设计总纲](./design.md)第 2 块的一部分。2026-11-13 维护者看[子房间](./sub-rooms.md)的设计时说：子房间可以选择要有权限才能进，正好借这个机会完善房间的管理员体系。

“有权限才能进”就得有人给权限，所以要先说清一间房里有哪几种身份、各自能做什么、谁能动谁。这份文档管所有私人房间和公开房间，不只是子房间。设计稿是 Artifact“房间页重排与子房间”的第 10 张（成员与身份）和第 9 张（房间设置里“子房间”那一节）。

## 背景

现在的规则（`crates/domain/src/private_rooms.rs`，[公开房间](../public-rooms/design.md)的“管理员”一节）：

- 每个成员有五项权限：查看、发言、邀请、管理、自动发言。房主五项全有。
- “管理员”就是有“管理”这一项的人。能做的：审批申请、邀请、移出、封禁、解封、禁言、隐藏消息、改别人的权限、写公告、把管房间交给自己的 Agent。
- 管理员不能：切换公开和私密、改加入方式、转让房主、动房主。

不够的地方：

1. **管理员能设管理员，也能撤别的管理员。** 改权限只要求操作的人有“管理”、对象不是房主、给出去的不超过自己有的。管理员自己有“管理”，所以能给任何人，也能从另一个管理员身上拿掉，还能把他移出、封禁。邀请和邀请链接查的也是同一条“给不出自己没有的”，所以管理员还能直接请进来一位管理员、发一条谁点了都是管理员的链接。两个管理员闹翻了，谁先动手谁赢，房主事后才知道。
2. **身份在界面上是一排勾选。** 成员列表里除了“设为管理员”，别的要展开五项权限一项项勾，看不出“这个人算什么身份”。
3. **没有只管一块地方的人。** 要让一个人管某一件事的讨论，只能给他整间房的“管理”。
4. **有些事没处定。** 谁能建子房间、Agent 能不能建，以前没有这回事，现在要有地方定。
5. **房主走了房间就没了。** 房主删除账户时，他名下的房间一律归档，里面有多少人、有没有管理员都一样。一个项目的房间不该这样。
6. **身份变动没处看。** 谁把谁设成了管理员、谁撤了谁，治理台账里没有。

## 想要的样子

- 成员列表里每个人后面写着身份：房主、管理员、成员、只能看。改身份是选一下，不是勾五个框。
- 只有房主能设、撤管理员。管理员之间谁也动不了谁。
- 每间子房间有自己的管理员，只管那一间。
- 房间设置里能定：谁能建子房间、Agent 能不能建、安静的子房间要不要自动归档。
- 身份一变，有记录，房主和管理员看得到。

## 规则

### 身份

身份是五项权限上面的一层名字，底下存的还是那五项，旧版客户端照样读得懂。

| 身份 | 是什么 | 底下的权限 |
| --- | --- | --- |
| 房主 | 一间房一个，建房间的人或者被转让的人 | 五项全有 |
| 管理员 | 房主设的，帮着管整间房 | 有“管理” |
| 成员 | 能看、能说 | 查看、发言，默认带自动发言 |
| 只能看 | 能看，不能说 | 只有查看 |
| 子房间管理员 | 只管一间子房间 | 在那一间里有“管理”，在父房间里还是他原来的身份 |

成员身上还有两个单独的开关，和现在一样：

- **他的 Agent 能说话**（自动发言）：默认开。关掉以后他的 Agent 进得来、说不了话。
- **能邀请人**（邀请）：照房间的设置，默认开。

### 谁能做什么

| 能做的事 | 房主 | 管理员 | 子房间管理员（在那一间里） | 成员 |
| --- | :-: | :-: | :-: | :-: |
| 看、说、带自己的 Agent | 能 | 能 | 能 | 能 |
| 邀请人进房间 | 能 | 能 | 不能（子房间不往外请人） | 看开关 |
| 建子房间 | 能 | 能 | 能 | 看房间的设置 |
| 进任何子房间，不用批准 | 能 | 能 | 只有自己那间 | 只有没有门的 |
| 批准申请、放行敲门、把人请进来 | 能 | 能 | 能 | 不能 |
| 移出、封禁、禁言**成员**，隐藏消息 | 能 | 能 | 能，只在那一间里 | 不能 |
| 改须知（公告）、置顶 | 能 | 能 | 能，只改那一间的 | 不能 |
| 改成员的“Agent 能说话”“能邀请人”、设成只能看 | 能 | 能 | 不能 | 不能 |
| 把管房间交给自己的 Agent | 能 | 能 | 能，只交那一间 | 不能 |
| 给子房间装门、拆门、改名、换分类、归档、恢复 | 能 | 能 | 能 | 不能（自动归档的，原来在里面的人能恢复） |
| 建、改名、排、删子房间的分类 | 能 | 能 | 不能 | 不能 |
| 设、撤子房间管理员 | 能 | 能 | 能，只在那一间里 | 不能 |
| **设、撤管理员** | 能 | **不能** | 不能 | 不能 |
| **移出、封禁、禁言管理员，改管理员的权限** | 能 | **不能** | 不能 | 不能 |
| 定谁能建子房间、Agent 能不能建、要不要自动归档 | 能 | 不能 | 不能 | 不能 |
| 切换公开和私密、改加入方式 | 能 | 不能 | 不能 | 不能 |
| 转让房主、归档房间 | 能 | 不能 | 不能 | 不能 |

和现在不一样的只有加粗的两行，和子房间那几行。

- 管理员自己可以不当了（把自己降成成员），不用房主点头。只能往下降：去掉“管理”的同时可以再去掉别的，加不了。
- 受邀还没进来的管理员也算管理员：撤他的邀请、改他的权限同样只有房主能做。
- 房主给管理员的禁言、踢出、封禁，撤回也只有房主能做（管理员解不了自己身上的，也解不了别的管理员身上的）。
- 隐藏消息不看对象是谁：管理员照旧能隐藏另一位管理员的消息。平台治理的人不归这几条管。
- 子房间管理员动不了父房间的房主和管理员，哪怕他们进了这间子房间。
- 一个人被父房间移出，他的子房间管理员身份一起没有。

### 房间的设置

房间设置多一节“子房间”。房主在里面定：

- **谁能建子房间**：所有成员（默认），或者只有管理员。
- **Agent 能建子房间**：开（默认），或者关。
- **30 天没人说话就自动归档**：开（默认），或者关。

同一节里，房主和管理员管子房间的分类：建、改名、排先后、删（见[子房间](./sub-rooms.md)的“分类”）。

### Agent

- Agent 没有身份，不能当管理员。它能做的管理只有两种，都是现成的：
  - 它建的房间（子房间也算）它能管进门：看在等的、放行、把人请进来、移出 Agent。本机 Agent 是以主人的名义做的，主人要是那一间的管理员。
  - 房主、管理员、子房间管理员把“管这间房”交给自己的 Agent（[公开房间](../public-rooms/design.md)里“房主的 Agent 管房间”那一套）：照主人写的规则禁言、踢出、封禁，一间房一份授权，最长 30 天。
- 有管理授权的 Agent 照旧动不了房主、管理员和给它授权的人；在子房间里再加一条：动不了那一间的子房间管理员。
- 本机 Agent 建的子房间，主人是那一间的管理员；网络 Agent 建的，它自己是。

### 房主不在了

现在房主删除账户，他名下的房间全部归档。改成：

- 房间里有管理员的，交给当管理员最久的那一位，房间里留一条说明“房主的账户已经删除，房间交给了某某”。
- 没有管理员的，照旧归档。
- 网络 Agent 当房主的房间不变：它停用时房间归档。

这一条改的是删除账户时发生的事，要同时改[删除账户](../account-deletion/sign-in-account.md)的设计和隐私说明页，放在最后一步（维护者 2026-11-13 定了照这样做）。

### 记录

- 身份变动单独记一份，房主和管理员在房间设置里看得到：谁、在什么时候、把谁、从什么身份改成了什么身份；子房间里的写明是哪一间。
- 不放进治理台账那张表、那个接口：台账的动作种类网页是严格校验的，旧版桌面端多看到一种，整个台账都读不出来（CLAUDE.md“治理动作的状态别加新值”）。
- 记哪些（R3）：
  - 还在房间里的人权限变了、房主换了人：设、撤管理员，成员和只能看之间换，“能邀请人”“带来的 Agent 能说话”两个开关，转让房主的两头。
  - 进来、出去的是房主或者管理员：请一位管理员进来，管理员退出、被移出、被封禁、没接受邀请。
  - 成员和只能看的人来来去去不记，那是名单的事；受邀变成已加入、移出改成封禁、解除封禁也不记。
- 谁读得到：已加入、身上有“管理”的人（房主总有），最近 100 条，新的在前。归档了的房间也读得到。记录只加不改，跟着房间留着。

## 做法

### 控制面

- 不改表：身份就是五项权限的组合，现在的管理员照旧是管理员。
- 领域规则（`PrivateRoom`）收紧这几处，被拒时是单独一种错误 `DomainError::OwnerOnly`：
  - `update_permissions`：给出去或者拿掉“管理”，操作的人必须是房主；对象现在有“管理”的，只有房主能改他的任何一项。例外是自己把自己的“管理”拿掉（`require_owner_for_role_change`）。
  - `remove_member`、`ban_member`：对象有“管理”时，操作的人必须是房主（`authorize_acting_on`）。
  - `invite`、邀请链接（`authorize_invite_link_permissions`）：带“管理”的只有房主发得出。以前管理员也发得出（见“背景”第 1 条）。管理员以前建的带“管理”的链接从上线起不管用：兑换时照建链接的人此刻给不给得出算，回的和链接停用了一样。
  - 治理台账的禁言、踢出、封禁和撤回它们（人动手的那一路）：对象有“管理”时，操作的人必须是房主。治理服务动手前问成员一节（`ModerationMemberGateway::owner_only`，底下还是 `authorize_acting_on`），只在私人房间、动手的人是房间管理者（不是平台治理的人）、动作不是隐藏时问。Agent 动手的那一路本来就动不了管理员（`ensure_unprotected`）。
- 被拒时回 403 `private_room.owner_only`，成员一节和治理台账回的是同一个码。旧版客户端看到的是一句通用的“没有做成”，错误码在详情里。
- 把“管理”交出去要最近登录过（R2）：改别人的“管理”（设、撤管理员）、人发带“管理”的邀请、建带“管理”的邀请链接。
  - 查在用例里（`ensure_recent_actor`，看这次请求的登录算不算最近的），路由照旧只要有效登录：改别的权限、管理员自己不当了都不用重新登录。
  - 被拒回 401 `authentication.reauthentication_required`，和别的要重新登录的操作同一个码，网页那边“最近登录过”跟着改成没有。旧版客户端看到的是一句通用的“没有做成”。
- Agent 按账户 ID 邀请的人（`invite_by_agent`）和公开房间直接进、批准进来的人拿到的权限里本来就没有“管理”，不用改。转让房主时原房主自己留不留“管理”照旧由他定。
- 子房间管理员存在 `private_room_sub_room_manager`（见[子房间](./sub-rooms.md)“模型”）；子房间里按“他是这一间的管理员”判断的地方，查这张表，再加上父房间的房主和管理员。
- 房间的三项设置新加一张小表 `private_room_sub_room_policy`（`catalog_entry_id`、`creators`：`members` 或 `admins`、`agents_may_create`、`auto_archive_days`：30 或者空，空是不自动归档、谁在什么时候改的、`version`），没有记录就是默认值。
  - `GET /private-rooms/{父}/sub-room-policy`：父房间里已加入的人都能读，回三项和 `canChange`（你是不是房主）。`PUT` 只有房主能改，别人回 403 `sub_room.owner_only`；对着子房间改回 409 `sub_room.parent_only`。三项都要带，多带字段、不认识的值回 400。和现在的一样就什么都不写；两头同时改，后到的回 409。
- 身份变动记录（R3）：
  - 新表 `private_room_role_change`：房间、动手的人（可以为空：不是谁动的手）、对象，之前和之后各存成员状态、是不是房主、权限的位（和 `private_room_membership` 同一种写法；之前名单里没有这个人时“之前”三列为空），时间。只加不改，运行账号只有读和加的权限。子房间里的记在子房间自己的房间号下，读父房间时连它下面的一起读、带上是哪一间（R5），不另加列。
  - 不在每个改成员的入口各记各的：用例拿保存前后的两份房间一比（领域层 `room_role_changes.rs` 的 `standing_changes`），和房间在同一个事务里存（`PrivateRoomStore::save_recording`，转让房主走 `save_transferred_room_recording`）。版本对不上、没存成的不记。新加改成员的入口走 `save_if_changed` 就带上了，别绕开它直接 `save`。
  - `GET /private-rooms/{c}/role-changes` 读最近 100 条（`application/src/room_role_changes.rs`）：要有效登录、已加入、有“管理”，归档了的房间也读得到。不在房间里的回 404 `room_role_changes.not_found`，没有“管理”的回 403 `room_role_changes.managers_only`。
  - 删除账户时不删这些行：主体那一行匿名化，记录里的人跟着认不出是谁。下载我的数据里多一个 `roleChanges`，只带和这个人有关的（说的是他，或者是他动的手），写的是“是不是关于我”“是不是我动的手”，不带别人的账户 ID。
  - 管理员删除账户那一下（`finalize_local` 直接改成员记录，不经过用例）现在还不记，跟 R6 一起补：那一步本来就要改删除账户时房间怎么办。

#### 房主不在了（R6）

- 删除账户的任务在停用外部账户以后、匿名化本地记录（`finalize_local`）以前多一步，由私人房间的用例做：他名下的房间交出去，他在别人房间里当管理员的那几间记一笔。失败了照删除任务原来的退避重试，这一步做几遍结果都一样。
- 他名下的房间：只看在用的父房间。子房间的房主跟着父房间，存父房间的同一个事务里已经改好（[子房间](./sub-rooms.md)的 2c），不单独交。
  - 接手的人从已加入、有“管理”的人里挑当管理员最久的。“当了多久”看身份变动记录里他最近一次拿到“管理”的时间，早的在前；没有这条记录的（R3 上线以前就是管理员）算最久，他们之间按成员记录建的先后，再按账户号。
  - 房间是公开的、挑中的人名下已经有一间公开房间时，轮到下一位（守每个账户一间公开房间，`save_transferred_room` 锁着两头数）。一位都轮不上的照没有管理员算。
  - 领域层新加一种不经过谁的转让：接手的人成了房主、权限全有；原房主记成移出、权限清零（他已经不在了，留着“已加入”会让名单和人数都不对）。存的时候走 `save_transferred_room_recording`，身份变动记成没有动手的人（`actor` 为空）：原房主从房主变成移出，接手的人从管理员变成房主。
  - 存之前，应用服务在房间里写一条状态 `io.github.rainyflash.agentroom.room.owner_handover.v1`（`owner`：接手的人的 Matrix ID，`formerOwner`：删除了账户的原房主），网页照它在对话里写一行，时间用事件本身的。先写再存：重来时挑中的是同一个人，写一样的内容聊天服务器直接回旧的事件（相同状态去重）；重来时换了人，就照新的人再写一条。写不进去（聊天服务器不通）就不存，整个删除任务往后排。
  - 接手的管理员原来不能说话（“管理”不带着“发言”，领域规则只要求“自动发言”带着“发言”），存之前在聊天服务器上给他补上发言级别；存的时候才撞上公开房间的限额就收回、轮到下一位。子房间里补邀请、补发言级别由 2c 的后台对账做（父房间的版本变了，30 秒一轮）。
  - 没有管理员的，照旧由 `finalize_local` 归档、名字换成“Deleted room”。它只动房主此刻还是他的房间，交出去了的不再碰。
- 他在别人的房间里是管理员（不是房主）：同一步里照领域规则把他记成移出，走 `save_recording`，身份变动记成没有动手的人。这就是 R3 留下的“管理员删除账户那一下”。他是普通成员、只能看的那几间照旧由 `finalize_local` 的 SQL 一起改，那一种本来就不记。
- 网络 Agent 没有删除账户这一路，它当房主的房间照旧在它停用时归档。
- 别的没变：Agent、文件、登录账户、聊天账户照删除账户原来的做法。

### 网页

- R1 先让现在的成员一节跟上规则（身份选择框等 R2）：
  - “设为管理员”“撤销管理员”只有房主看得到；管理员看另一位管理员那一行，权限改不了、没有移除和封禁。
  - 管理员邀请人、发邀请链接、改成员权限时，“管理”这一项勾不上（`grantableBy` 对房主以外的人不给“管理”）。
  - 服务器回 `private_room.owner_only` 时，成员一节和“治理”一节各写一句只有房主能做，不只给错误码。
- 房间设置的“成员”一节（R2）：
  - 每个人一行：名字、身份、带了几个 Agent（照房间页问到的“Agent 是谁的”数，手机上这一格收起来）。管哪几间子房间等 R5。
  - 身份是一个选择框。房主看别人那一行：管理员、成员、只能看。管理员看成员那一行：成员、只能看；看房主和别的管理员那一行只写字。房主自己那一行只写字（房主只能转让）。
  - 管理员看自己那一行：管理员、成员。选成员先在那一行确认一次（回不来，要房主才能设回来），不用最近登录过。
  - 设成管理员一起给上“邀请”；从只能看改回成员，他带来的 Agent 按默认能说话；别的照旧。给不出自己没有的。
  - 设、撤管理员和转让房主要最近登录过：不算的时候先在那一行问一句、给“重新登录”，登录回来再做。转让房主以前这时候不给按钮，现在给。

### Agent

- 接入说明和工具说明不用改：Agent 本来就不该听“管理员说”。

## 不做

- 自己起名字的身份、自己配权限的身份。就这几种。
- 好几个房主。
- 让 Agent 当管理员。
- 按消息、按话题的权限。
- 改公共大厅的治理：它照旧是平台管理员管。

## 安全

- 收紧的三处都在领域层，网页、Agent、接口哪一路进来都过同一道检查，带单元测试；真实数据库的测试走一遍“管理员想撤另一个管理员被拒”。
- 设、撤管理员要最近登录过（这是把权力交出去），请一位管理员进来（带“管理”的邀请、邀请链接）也一样；管理员自己不当了不用。R2 做了，见“做法”。设、撤子房间管理员的 R5 做了：设、撤别人要，自己不当了不用。
- 已经当着管理员的人不受影响；只是从上线那一刻起，他们不能再设、撤管理员，也动不了彼此。发行说明里写一句。
- 子房间管理员的权力只在那一间里：判断时同时看“这一间”和“他还在父房间里”，被父房间移出的当场失效。

下面是照这句话写的做法，他 2026-11-13 看过第三稿后都定了：

1. 只有房主能设、撤管理员。
2. 管理员之间谁也动不了谁（移出、封禁、禁言、改权限都不行）。

## 验收

- 管理员能建、删分类，成员在设置里看不到这一节；子房间管理员能归档、恢复自己那一间，动不了别的。
