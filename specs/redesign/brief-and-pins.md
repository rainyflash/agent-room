# 须知与置顶（第 4 块的后一半）

[总纲](./design.md)第 4 块里“须知与置顶”这一半。另一半“提醒”在 [reminders.md](./reminders.md)。

## 现在是什么样

- 每间私人房间、公开房间有一段“公告”：纯文字，最多 2000 字，新的盖掉旧的。设计和实现在 [specs/public-rooms/design.md](../public-rooms/design.md) 的“常驻公告”。
- 存成房间状态 `io.github.rainyflash.agentroom.room.notice.v1`（内容 `text`、`updatedBy`、`updatedAt`），控制面查过“管理”这一位后以应用服务写（`PUT /private-rooms/{c}/notice`，不要最近登录过，每人每小时 30 次）。没有读的接口，大家都从聊天服务器读。控制面的库里不存公告，只有网络 Agent 那边记着给它的是哪一版（`network_agent_room.notice_*`）。
- 网页：对话上面一行收着的公告，点开看全文和谁改的；改动在对话里留一行“谁改了公告”；有没看过的改动时亮一个点，看没看过只记在这个浏览器里（`localStorage` 的 `agent-room.room-notice-seen.<房间>`）。编辑在房间设置里。
- Agent：本机的进房间时拿到，之后改了跟着下一批消息给（IPC 4.6 的 `ReadRoomNotices`，回答里叫 `notices`），改了不叫醒它；网络 Agent 一样（进房间时的 `notice`、等消息的 `notices`）。后台回复不给。
- 子房间有自己的一段，和父房间的没关系（[sub-rooms.md](./sub-rooms.md)“父房间的须知对子房间也算放到第 4 块”）。
- 没有置顶。

## 想要的样子

总纲定的：拆成两样。

1. **房间须知**长期挂着：这间房干什么、给 Agent 的规矩。就是现在的公告，改个名字，补上记录和跨设备的未读。子房间里父房间的须知也算。
2. **置顶**可以有几条，放当前的事：把房间里的某一句置顶，挂在须知下面。

两样都“改了留记录，给人标未读”。

## 房间须知

- 现在的公告直接改叫“房间须知”（英文 Room brief，和房间页的用词表一样），存法、接口、给 Agent 的路都不变：`room.notice.v1` 照旧是它。只改给人看的字。
  - 给 Agent 的说明、接口和工具里照旧叫 `notice`，说明里写成 room brief：改名字会让已经装着的客户端读不到。
- 谁能改照旧：房主、管理员（子房间里是这一间的管理员和父房间的房主、管理员）。Agent 照旧只读。
- 编辑照旧在房间设置里，提示里那句“Agent 把它当这间房的规矩”留着。

### 子房间里父房间的须知也算

- 网页：子房间对话上面那一行先写父房间的须知（标着“来自 <父房间>”），再写这一间自己的。两段都没有就不显示这一行。人都在父房间里（子房间只收父房间里的人），网页直接读父房间的状态。
- Agent：进子房间的 Agent 不一定在父房间的聊天房间里，读不到父房间的状态。所以控制面在子房间里放一份父房间须知的副本：
  - 新的房间状态 `io.github.rainyflash.agentroom.room.parent_notice.v1`，内容和 `room.notice.v1` 一样多一个 `parentRoomId`，由应用服务写；
  - 父房间改须知时，控制面给它每一间子房间（归档了的也算）都写一份：同一个请求里写完父房间的，先写一批子房间的，写不完、没写成的排在新的任务表 `private_room_parent_notice_sync` 里，由控制面的 `sub_room_sync.rs` 在子房间对账那一轮后台补做（带迁移）；新建子房间时写上当时的那份；
  - 本机 Bridge 和网关读到它，当成父房间的那一段交给 Agent：进房间时一起给，改了跟着下一批给。回答里每一段本来就带 `roomId`，父房间那段的 `roomId` 是父房间的，不用加字段，旧版 MCP 和命令行照样读得懂（IPC 回答是 `deny_unknown_fields`，加字段会让还开着的旧进程整个读不出来）。
  - 旧版网页会把这个新的状态当成认不出的事件在对话里列一行，更新以后就没了。这一步发版以后旧网页只会在父房间改了须知时看到。

## 置顶

- 把房间里已经有的一句置顶，不另写一段文字：当前的事多半已经有人说过了（一句安排、Agent 的一份总结），置顶它最省事，对话里也找得到上下文。
- 存成 Matrix 标准的 `m.room.pinned_events`（`pinned` 是事件 ID 的列表），别的 Matrix 客户端也认得。加一个我们自己的字段记谁、什么时候改的（应用服务替人写，发件人看不出是谁）。
  - 只存事件 ID，不存内容。加密房间里置顶的那句照旧是加密的，在各自的设备上解开；比须知（不加密）少给服务器看一样东西。
  - 这个状态现在只有应用服务够得着（私人房间的 `state_default` 是 100），所以和须知一样由控制面查过权限后替人写。
- 谁能置顶、取消置顶：和须知一样，有“管理”的人。别的成员只能看。
- 一间房最多 5 条，新的在最前面。满了要先取消一条再置顶，界面上照实说。
- 被撤回、删掉的那句：列表里写“这句已经删了”，管的人能取消置顶；不自动从列表里拿掉（自动改状态要有人能写，又多一条后台的路）。
- 网页：
  - 须知那一行下面一行“置顶 N 条”，点开列出每一句的开头、谁说的、什么时候，点了跳到对话里那一句（那句没加载就往前补，和点回复那句跳过去是同一套）。
  - 管的人把鼠标移到一句话上，“复制”“回复”旁边多一个“置顶”（已经置顶的是“取消置顶”）；置顶的列表里每条也能取消。
  - 对话里留一行“谁置顶了一句”“谁取消了一条置顶”，点了跳到那一句。
- 子房间有自己的置顶，不跟父房间走：当前的事各间不一样。
- 私聊没有须知也没有置顶（两边都能写状态，没法照“管理”判断），照旧。公共大厅也没有。

### Agent 读置顶

- 进房间时和须知一起给：置顶的每一句给事件 ID、谁说的、开头一小段；要全文照旧用 `agent_room_get_messages`（命令行 `show`）按 ID 取。
- 改了跟着下一批消息给，不叫醒它，和须知一样。
- 本机要 IPC 加一个方法（`ReadRoomPins`，版本升到 4.8），Bridge 同时认 4.4 到 4.7；回答的格式新定，不往须知的回答里塞。网络 Agent 在进房间、等消息的回答里加一个 `pins`（远程 MCP 和 HTTP 的回答本来就允许多字段）。
- 网络 Agent 读不到它进来以前的加密消息：置顶的那句在它进来以前的，给 ID 和“进来以前的，读不到”，不给内容。
- 两份 MCP 服务说明都贴着 1536 字节的上限，加一句要先删别处的字。

## 记录和未读

- **记录**：
  - 须知：对话里“谁改了须知”那一行点开能看那一版写的什么（那一版的内容本来就在那条状态事件里，不用另存）。设置里须知那一节写上次谁、什么时候改的。不另做“历史版本”页：要往前找就在对话里找那几行。
  - 置顶：对话里“谁置顶了一句”“谁取消了一条置顶”那几行就是记录。
  - 都不另建表，服务器上不多存东西。
- **未读**：
  - 看过哪一版须知、看过哪一次置顶，从只记在这个浏览器改成记在个人工作区里（和读到哪、免打扰同一份，换设备也算），用工作区里已有的 `acknowledged` 那一种：键是 `brief:<房间>`、`pins:<房间>`，值是看过的那一版的时间。工作区的索引现在只留了 `acknowledged` 的键（收件箱只问有没有），要连值一起留。
    - 不新加一种条目：网页读工作区是严格的，旧版网页看到认不出的种类会整份读不出来。`acknowledged` 收件箱也在用，键不一样不会撞。
    - 这台浏览器以前记着的看过，第一次打开时搬进工作区。
  - 点开须知、点开置顶的列表就算看过。自己改的不亮点。
  - 房间列表上不为须知、置顶单独亮点（列表上已经有未读和 @，再多一种点就分不清了）；进了房间那一行上亮。

## 接口

- 须知不变：`PUT /private-rooms/{c}/notice`。父房间改须知时多排一批子房间的副本，回答不变。
- 置顶：`PUT /private-rooms/{c}/pins`，带 `{ "eventId": "...", "pinned": true | false }`，回整份列表 `{ pinned: [{ eventId, pinnedBy, pinnedAtUnixMs }] }`。
  - 只认这间房里的事件：控制面以应用服务问一下这条事件在不在这间房里、是不是消息；状态事件、别的房间的都回 400。
  - 和须知一样：有效登录就行，不要最近登录过；每人每小时 30 次（两样合起来算）；归档了的回 409。
  - 改列表是“读出整份、改一项、整份写回”，同一个房间一次只改一个（照 `update_power_levels` 那样在控制面里排队），不然两个人同时置顶会盖掉一条。
- 网页对新接口的回答 `.strict()` 校验；旧接口一个字段都不加。

## 隐私说明页

- 置顶那一步改：置顶的列表（哪几句、谁置顶的、什么时候）存在聊天服务器的房间状态里，不加密，服务器看得到列表、看不到加密房间里那句写了什么。
- 父房间须知的副本那一步改：须知照旧不加密，子房间里多一份父房间的；控制面不存。
- 顺手改正一处和代码对不上的：说明页说控制面不存公告的副本，可网络 Agent 那边存着给它的是哪一版、写的什么（`network_agent_room.notice_text`），跟着房间删。
- 这份设计文档里记一笔每条说法的依据（`specs/privacy-page/design.md`）。

## 分步

1. **4N-1** 这份设计和设计稿，只改文档。
2. **4N-2** 网页：公告改叫须知；对话里改动那一行点开看那一版；看过没看过记进个人工作区。
3. **4N-3** 子房间里父房间的须知：
   - **4N-3a** 网页直接读父房间的状态显示；
   - **4N-3b** 控制面写子房间里的副本（新建子房间时、父房间改须知时，后台任务重试）；隐私说明页一起改；
   - **4N-3c** 本机 Bridge 和网关把副本当父房间那一段交给 Agent。
4. **4N-4** 置顶：
   - **4N-4a** 控制面的接口和写状态，隐私说明页一起改；
   - **4N-4b** 网页：须知下面那一行、句子上的置顶按钮、对话里的记录、未读（拆成 4N-4b-1 只读和显示、4N-4b-2 置顶和取消）；
   - **4N-4c** Agent：IPC 4.8、本机 MCP 和命令行、网络 Agent 和远程 MCP、说明。
5. **4N-5** 无头验收，只在派发 `suite=all` 时跑：房主改父房间须知，子房间里的本机 Agent 和网络 Agent 都拿到；置顶一句，两个 Agent 都拿到，取消以后也知道。

4N-2 可以先发；4N-3a 和 4N-3b 不碍事，可以分开发；4N-3c 要在 4N-3b 之后（副本先得有）；4N-4a 先于 4N-4b（接口先合）。

## 验收

- 房主改了须知：另一个人在另一台设备上打开这间房，须知那一行亮一个点；点开看过以后，他换到手机上打开不再亮。
- 对话里“谁改了须知”那一行点开，看到那一次改成了什么；往前那几行就是以前的版本。
- 子房间里先看到父房间的须知、再看到这一间的；房主改了父房间的须知，子房间里的 Agent 下一批消息带着新的那段。
- 管理员把一句置顶：须知下面多一行“置顶 1 条”，点开跳到那一句；别人那里亮点；Agent 下一批消息带着这条置顶。
- 满 5 条再置顶，照实说要先取消一条。
- 不是管理员的人看不到“置顶”。

## 维护者定的

- 2026-11-13（总纲）：须知长期挂着，置顶可以有几条、放当前的事；改了留记录，给人标未读。
- 他没单独说过、照这里写的：
  1. 置顶的是房间里已经有的一句，不另写一段文字。
  2. 最多 5 条。
  3. 记录就是对话里那几行，不另做历史版本页，服务器不另存。
  4. 看过没看过换设备也算（记进个人工作区）。
  5. 子房间里父房间的须知也给 Agent，置顶不跟父房间走。
