# 子房间（第 2 块）

[重新设计总纲](./design.md)的第 2 块。2026-11-13 维护者说：一个项目一间房可能不够，房间下面要能开子房间，房间里的人和 Agent 可以任意创建和加入。同一天看过第一版设计又定了：子房间默认没有门，但可以选择要有权限才能进；借这个机会把房间的管理员体系补全（[房间的身份和管理员](./room-roles.md)）。看过第二稿他又说：缺了一些功能，比如子房间的分类和归档。

设计稿是 Artifact“房间页重排与子房间”的第 1 张和第 4 到 9 张。房间页左边那一栏在[第 1 块](./room-page.md)里留好了位置。

## 背景

- 一个项目里同时有好几件事：发版、某个 issue、官网改版。现在只能都在一间房里说，或者另建几间互不相干的房间，每间都要重新请人、请 Agent。
- 对 Agent 更要紧：它一直守着房间等消息，房间里说的每件事都可能叫醒它。一件事一个子房间，它只进跟自己手上的事有关的，别的吵不到它。
- 有的事不该所有人都在场：维护者之间商量、处理还没公开的安全问题。公开房间里尤其需要。
- 现在已经有的、能直接用的：
  - 一个 Agent 用同一个身份进好几个房间，一次等所有房间的消息，每个房间各记读到哪（[本机 Agent 跨房间用同一个身份](../agent-identity/design.md)；网络 Agent 也能进好几间）。
  - Agent 能建房间，也能管自己建的房间：放行敲门、请人、移出 Agent（[Agent 自己建房间、管房间](../agent-rooms/design.md)）。
  - 公开房间的三种加入方式（直接进、申请后批准、只能邀请）和申请、批准那一套（[公开房间](../public-rooms/design.md)）。
  - 服务器记着某人“已加入”、Matrix 上他只是受邀时，网页替他加入（`PrivateRoomJoinBoundary`）。
- 现在的房间模型里没有“房间属于另一个房间”这回事：
  - 房间目录只有三种（公共大厅、私人房间、私聊），公开房间也是私人房间加一张公开设置的表。种类和可见范围都有约束卡着，加新值会让回滚读不出来。
  - 每间私人房间必须有一个房主，房主必须是已加入、五项权限全有的成员（提交时才查的约束触发器）。
  - 人进房间只有“先邀请、再自己加入”一条路；Agent 进房间要它的主人已加入、能发言，或者它自己凭口令、敲门进来过。
  - 禁言、踢出、封禁按房间记，一间房里的不管另一间。

## 想要的样子

- 房间页左边一栏：最上面是“主房间”和“浏览子房间”，下面是你在的子房间，按分类分组，带未读和 @。能直接进的前面是 `#`，要批准或者只能请进来的前面是一把锁。
- 点“新建子房间”，起个名字、写一句用途、选个分类，子房间就建好了，你已经在里面。要装门就在这里选。
- “浏览子房间”里是这间房所有的子房间，按分类排着，能搜。没进的在这里加入或者申请。
- 一件事说完了，把它归档：只能看、不能说，从左栏拿掉，在“已归档”里还找得到，能恢复。没人管的，30 天没人说话自己归档。
- 跟你的 Agent 说“开个子房间说发版的事”，它建好、进去，你这边左栏里多出这一项。
- 把人请进房间，他就能进任何没有门的子房间；把人移出房间，他在所有子房间里也一起出去。

## 规则

### 是什么

- 子房间是挂在一间房下面的房间，只有一层：子房间下面不能再开。
- 能有子房间的是私人房间和公开房间。公共大厅和私聊没有。
- 子房间自己是一间完整的房间：有自己的对话、自己的成员、自己的 Agent、自己的须知，Agent 等消息、读到哪都按它单独算。
- **门只对房间里面的人开关。** 不在父房间里的人，子房间有没有门都进不来：子房间没有口令、没有邀请链接、不能单独设成公开。要让一个外面的人进子房间，先请他进父房间。

### 门

子房间默认没有门。建的人、这间子房间的管理员、父房间的房主和管理员随时能装门、拆门、换一种门。界面上这一项叫“谁能进”，三个选项是“直接进”“要批准”“只能请进来”，和公开房间的加入方式是同一套词。

| 门 | 谁能进 | 人怎么进 | Agent 怎么进 |
| --- | --- | --- | --- |
| **没有门**（默认） | 父房间里的人和 Agent | 点“加入”，不用谁批准 | 自己进 |
| **要批准** | 申请了、被批准的 | 点“申请加入”，可以留一句话，子房间的管理员批准 | 主人在里面的，跟着主人进；凭口令或敲门进了父房间的，对子房间敲门、等放行 |
| **只能请进来** | 管理员加进来的 | 不能申请，等管理员把他加进来 | 主人在里面的，跟着主人进；别的由管理员按名字请进来 |

- 父房间的房主和管理员进任何子房间都不用批准。子房间拦不住这间房自己的管理者：一间房里不该有房主看不见的地方。他们进来时，里面的人看得到。
- 有门的子房间还可以勾“不在名单里显示”：只有里面的人、父房间的房主和管理员看得到有这一间。不勾的话，父房间里的人都看得到它的名字、用途和谁在管，只是进不去。
- 装门不会把已经在里面的人请出去；拆门以后谁都能进。
- 申请和公开房间一样：一直等着，没人处理也不作废；同一个人对同一间只有一个在等的申请。
- Agent 敲门照现在的规则：等一小时，一间子房间最多 5 个在等。

### 建

- 父房间里已加入、能发言的人都能建。
- 父房间里的 Agent 都能建：
  - 本机 Agent 替它的主人建，主人要在父房间里能发言；
  - 网络 Agent 自己建，它要是凭口令或敲门进了父房间的，或者父房间就是它建的。
- 父房间的房主可以把“谁能建子房间”收紧成只有管理员，也可以关掉“Agent 能建”（见[房间的身份和管理员](./room-roles.md)）。默认都开着。
- 建的时候填名字（同一间房里没归档的子房间不重名，不分大小写）、一句用途（可以不填）、放进哪个分类（可以不选）、要不要门。
- 建的人是这间子房间的管理员。Agent 建的：本机 Agent 的主人是管理员，Agent 照主人的名义管；网络 Agent 自己是管理员。
- 建好以后建的人已经在里面；Agent 建的，它自己在里面，它的主人也在里面。
- 上限是防失控用的，不是为了管人：每间房最多 100 个没归档的子房间；同一个人或 Agent 一小时最多建 10 个。子房间不占账户的公开房间名额，也不占网络 Agent 的建房名额。

### 加入和退出

- **没有门的**：
  - 父房间里已加入的人，点一下就加入。
  - 本机 Agent 按名字进（`父房间名/子房间名`），它的主人要在父房间里能发言。**它进去的时候，主人也记成这个子房间的成员**：你的 Agent 在哪间子房间，你就在哪间，左栏里看得到，也对它在里面说的话负责。
  - 网络 Agent 拿子房间的房间号进，不用等人放行，只要它在父房间里。
- **有门的**：
  - 人照上面“门”那张表：申请，或者等管理员加进来。被加进来的人直接就在里面，不用再点接受（他本来就是这间房里的人，不想待可以退出）。
  - 本机 Agent 只在主人已经是这间子房间的成员时才进得去；主人不在里面时不会替主人加入，它拿到的回答里写明“这间要主人先申请”。
  - 凭口令或敲门进了父房间的 Agent（网络 Agent 等）对子房间敲门，管理员放行。
- 退出随时可以。人退出时他的 Agent 跟着退出（和现在的房间一样）。房主退不出去：他在每一间子房间里，嫌吵用免打扰。
- 被移出某个子房间的人：没有门的还能再进；有门的要重新申请或者重新被请进来。要彻底不让他进，封禁他（在这个子房间里，或者在父房间里）。

### 权限和管理

身份和各自能做什么写在[房间的身份和管理员](./room-roles.md)，这里只说和子房间有关的：

- 一个人在子房间里能不能看、能不能说、他的 Agent 能不能说，照他在父房间里的权限，不单独设。在父房间里被改了，子房间里跟着变。
- 父房间的房主也是每个子房间的房主；父房间转让了，子房间一起转。
- 父房间的管理员进了哪个子房间，在那里也是管理员。
- **子房间管理员**只管这一间：批准申请、把人和 Agent 请进来、移出、封禁、改名、改用途、改须知、装门拆门、归档。建的人自动是；房主、父房间的管理员、这间的管理员可以再设别人。他得是这一间里已加入的人：退出、被移出、被封禁的，这一间的管理员记录跟着删，再进来是普通成员（建的人也一样）。
- 子房间管理员可以把这间子房间交给自己的 Agent 管（现成的“把管房间交给自己的 Agent”，一间房一份授权）。
- 父房间里的禁言、踢出、封禁，在所有子房间里一起算；到期解除、撤回也一样。
- 子房间可以单独归档、恢复，见下面“归档和恢复”。

### 加密和谁读得到

- 没装过门的子房间跟父房间一样：父房间加密，它就加密；父房间是公开的、不加密，它也不加密。
- **有门的子房间一律加密。** 装门的那一刻，不加密的子房间会开加密（和公开房间改回私密一样，开了关不掉）。
- 有门的子房间以后拆了门，加密还在。这时照“私密房间改成公开”的规则办：拆门以后才进来的人，不给他们补发以前的房间钥匙，他们看不到拆门以前的话。
- 父房间以后改了，子房间跟着改（2d-5，见下面“跟着父房间公开、改回私密”）：公开改回私密会开加密，还没加密的子房间一起开；父房间公开时，没有门的子房间和它一样写下这一刻，之后才进来的人不补发以前的房间钥匙。
- 父房间是网络 Agent 建的，服务器读得到全部消息，子房间也一样，界面上照父房间那样写明。有门的子房间里要是进了网络 Agent，服务器读得到发给它的消息（和私人房间一样）。
- 后进子房间的人，不加密的看得到以前的消息；加密的只看得到自己进来以后的，别人的设备和 Agent 会照现在“找回加入前的消息”的规则补发（网络 Agent 照旧不补）。
- 保留期跟父房间。

### 跟着父房间公开、改回私密

子房间没有自己的公开设置，跟着父房间走。公开、改回私密的那个请求里，父房间以外每一间子房间也一起做（归档了的也算：恢复以后照样是这间房下面的）：

- **改回私密**：父房间先开加密、改好目录上的标记，再把还没加密的子房间一间间开加密、改标记，最后才存设置。有门的本来就加密，剩下的是父房间公开、不加密时建的没有门的那些。
- **公开**：没有门、还没写过 `room.listing.v1` 的子房间一间间写下这一刻，再记进 `door_opened_at`（这一列现在说的是“第一次写 `room.listing.v1` 的时间”：第一次拆门，或者父房间公开时它没有门），然后才写父房间自己的、存设置。有门的要批准才进得来，拆门时再写；写过的不再写，和拆门“只写第一次”一个道理。每次存公开的设置都看一遍，上一次没写成的这次补上。
- 哪一间没写进去，这次公开、改回私密就不算做成，房主再点一次接着做：开加密重写不出错，写过的不再写。子房间先写、父房间后写，是因为父房间那一刻只在第一次公开时写，写过以后不再挪。
- **建的当口父房间正好改了**：建子房间时读的是那一刻的父房间，存好以后再读一遍，照它补开加密、补写这一刻。改回私密那边先改父房间的标记、再读子房间；公开那边存好设置以后再读一遍子房间、补上存的当口刚建好的。所以两边总有一边看得到对方。补的时候没写进去就回错，同一个请求重发（回已经建好的那间）时再补。
- 父房间私密着的时候，没有门的子房间不写这一刻：和私人房间一样，后进来的人照“找回加入前的消息”的规则拿得到以前的钥匙。

### 分类

- 分类是给子房间分的组，只有名字和先后。一间子房间最多在一个分类里，没分的在“未分类”。
- 分类是整间房共用的：每个人看到的分法一样，不是各人自己的。
- 房主和管理员建分类、改名、排先后、删。一间房最多 20 个分类，名字不重名（不分大小写）。
- 建子房间时从已有的分类里选一个，不选就是“未分类”。之后这一间的管理员、父房间的房主和管理员能把它挪到别的分类。
- 删掉一个分类，里面的子房间回到“未分类”，不归档、不删。
- 分类只管怎么摆，不管权限：不能给整个分类装门。
- 一个分类里的子房间按建的先后排。
- 隐藏的子房间照样有分类；看不到它的人，分类的个数里也不算它。

### 归档和恢复

现在归档一间房只有房主能做，归档了不能恢复。子房间不一样：一件事一个子房间，事情做完就该收起来，收错了要拿得回来。

- **谁能归档**：这一间的子房间管理员、父房间的房主和管理员。
- **归档以后**：
  - 只能看、不能说（和归档的房间一样），也不能再加入；
  - 从左栏拿掉，在“浏览子房间”的“已归档”里；
  - 成员、门、分类、管理员都原样留着；在等的申请和敲门作废；
  - 不占 100 个的名额，名字也让出来（恢复时撞了名字要先改名）；
  - 未读清掉；Agent 等消息时不再看它，列房间时默认不列它。
- **谁看得到归档的**：归档以前看得到它的人，在“已归档”里都看得到这一行。原来在里面的人能打开看以前的话；没进过的要看，请能恢复的人先恢复。
- **恢复**：能归档的人都能恢复。恢复以后回到原来的分类（分类没了就回“未分类”），原来的人和 Agent 都还在，接着说。没归档的已经满 100 个时恢复不了，说明原因。
- **自动归档**：30 天里人和 Agent 都没说过话的子房间自动归档，记成“30 天没人说话，自动归档”。
  - 房主能在房间设置里关掉，默认开。
  - 自动归档的没有谁决定过要关它，所以原来在里面的人谁都能恢复。
  - 建好不到 30 天的不算。
- 父房间归档，子房间一起归档。父房间照旧不能恢复，所以它们也回不来。
- 没有“删除子房间”：归档就是结束。里面的消息照父房间的保留期到期。

### 每个人自己的

- **免打扰**：这间子房间没读的不算进“房间”页的卡片，也不提醒；提到你的照样算。只对你自己起作用，换一台设备还在。
- **标为已读**。
- 分类收没收起来，记在这台设备上。

### 看得到什么

- 左栏只放你在的子房间。别的在“浏览子房间”里：父房间里已加入的人都看得到名单，每间有名字、用途、分类、哪种门；没有门的再给里面有几个人、几个 Agent。没进去的看不到里面的话。
- 有门的子房间对没进去的人只给：名字、用途、分类、哪种门、谁在管。里面有谁、多久以前有人说话不给。勾了“不在名单里显示”的整个不给。
- 有你没见过的新子房间时，“浏览子房间”那一行带一个点（见没见过记在这台设备上）。
- “房间”页的卡片只有父房间一张，未读和 @ 把你在的子房间的也算进去（免打扰的不算没读的）。
- 发现页和分享页不单独列子房间。分享子房间的链接就是父房间的链接。
- 不登录的围观只看主房间。

## 做法

### 模型

- 子房间在房间目录里就是一间私人房间（`kind = 'private_room'`），不加新的种类。另加三张表，做法和公开设置那张表一样：

  `private_room_parent`：`catalog_entry_id`（子房间，主键）、`parent_catalog_entry_id`、`name_key`（名字去掉两头的空白、转成小写；同一间房里没归档的子房间靠它不重名，是一个只算 `archived_at` 为空的唯一索引）、`access`（`open`、`request`、`invite_only`，和公开设置的加入方式用同样的三个词）、`hidden`（只有 `access` 不是 `open` 时能为真）、`door_opened_at`（有门的拆门的时间，可空）、`created_by_principal_id`、`created_by_agent_id`（可空）、`parent_version_applied`、`created_at`；分类和归档用的 `category_id`（可空，分类删掉时置空）、`last_message_at`、`archived_at`、`archived_by_principal_id`（都可空）、`archived_reason`（`manual`、`inactive`、`parent`，可空）。约束：父房间自己不能在这张表里当子房间（只有一层）。

  `private_room_sub_room_manager`：`catalog_entry_id`、`principal_id`、`granted_by_principal_id`、`granted_at`。子房间管理员。

  `private_room_sub_room_category`：`id`、`parent_catalog_entry_id`、`name`、`name_key`（小写，和父房间一起唯一）、`position`、`created_by_principal_id`、`created_at`、`updated_at`。

- 因为它就是一间私人房间，现成的都能用：建 Matrix 房间、成员表、Agent 的位置、发言级别、须知、归档、网页的加入、Agent 进门、等消息、读到哪、把管房间交给 Agent。
- 约束触发器要求房主已加入、权限全有：子房间的房主记成父房间的房主，建的时候就给他一条已加入的成员记录。他在 Matrix 上只是受邀，打开时由网页替他加入。父房间的房主是网络 Agent 时照旧不邀请。
- 有门的子房间照用现成的两张表：人的申请（`private_room_join_request`）和 Agent 的敲门（`private_room_agent_knock`）。
- 归没归档还是记在房间自己的状态上（和现在归档一间房一样），`archived_*` 三列只记谁、什么时候、为什么。领域层给子房间单开归档和恢复，认子房间管理员和父房间的房主、管理员；现在的 `archive` 只认房主、没有恢复，不动它。恢复时 Matrix 那边把发言级别整份重写回来（现成的 `apply_active_private_policy`）。
- 谁能建、Agent 能不能建、自动归档开没开，记在 `private_room_sub_room_policy`（见[房间的身份和管理员](./room-roles.md)）。
- 子房间的公开设置、口令、邀请链接这三张表不写：生成和查看口令、建和查看邀请链接、设成公开，对子房间回 409 `sub_room.parent_only`。停用口令、停用链接、改回私密不拦，回滚到旧版那段时间建出来的要清得掉；那样的口令和链接拿来用时当它不存在。
- 整间房才有的另外几样在子房间上也回 `sub_room.parent_only`：往外请人（人请、Agent 请、凭邀请链接）、改成员权限、转让房主、整间房的归档和改名。子房间自己的加入退出、改名、归档和恢复走后面几步新开的入口。只对已经在这间子房间里的人这么说；不在里面的照旧按“不是成员”回，免得拿房间号试得出哪间是子房间。
- 名字的规则和个数（重名、每间房 100 间、每人每小时 10 间）由存储在锁着父房间目录那一行的事务里数。建之前先问一遍（`sub_room_creation_block`），过了才建 Matrix 房间；存的时候同一段再查一遍。数的时候不算要建的这一间自己：同一个请求重发时它已经在了，存的时候撞上房间号，用例照重试回已经建好的那间。
- 父子关系只记在控制面，不用 Matrix 的 Space，也不往房间状态里写。拆门那一刻、父房间公开时没有门的那些，写一条现成的 `room.listing.v1`（“这一刻以后进来的人不补发钥匙”就看它），别的不往房间状态里加。

### 进门

- **人加入没有门的**：`POST /private-rooms/{父}/sub-rooms/{子}/membership`。查他在父房间里已加入、在子房间里没被封禁，然后直接记成已加入，在 Matrix 上邀请他、设好发言级别。网页接着照“服务器记着已加入、Matrix 上是受邀”那一套替他加入。不走“受邀 → 接受”两步：加入是他自己点的。
  - 先后是：设发言级别（他还没被邀请，设了也用不上）、记成员、最后才邀请。没记成的不会留下一张没人认的邀请。
  - 记成员的那个事务里再看一眼他在父房间里还是不是已加入，并把那条成员记录锁到存完：读到以后、存之前他被移出父房间的，什么都不写，回的和不在父房间里的人一样。
  - 已经在里面的再点一次不算错：只补一遍邀请（邀请没发成的、他自己在 Matrix 上拒了的，这样回得来），不再存，也不重设发言级别（被禁言的人再点一次加入不该把它冲掉）。
- **人退出**：`DELETE` 同一个地址，只要这一个请求。控制面替他在 Matrix 上离开（他可能从没点开过这一间，在 Matrix 上还只是受邀），把他的 Agent 移出去，再记成已退出。本来就不在里面的不算错。
- **人申请要批准的**：`POST .../join-requests`（可以留一句话）；子房间管理员、父房间的房主和管理员 `GET` 看在等的、`PUT .../join-requests/{账户}` 批准或拒绝。批准以后和上一条一样直接记成已加入。规矩见下面“申请”。
- **管理员把人请进来**：`PUT .../members/{账户}`。他要是父房间里已加入的人。直接记成已加入。哪种门都能用，没有门的也能。规矩见下面“请进来、移出和封禁”。
- **父房间的房主和管理员**：走第一条，不看门。
- **本机 Agent 进**：进门的规则（`admits_agent_of`）不变，还是要主人在这间房里已加入、能发言。没有门的子房间里主人还不在时，先照第一条把主人加进去，再让 Agent 进；有门的不替主人加，回 403 `sub_room.owner_not_inside`。
- **Agent 成员进**（网络 Agent、凭口令或敲门进了父房间的本机 Agent）：对子房间敲门。没有门的，它在父房间里是已加入的 Agent 成员就直接放行；要批准的照现成的敲门等放行；只能请进来的不收敲门，由管理员按名字放行（现成的放行入口，不要求先有敲门记录）。
  - 本机 Agent 没有敲门这条路：主人带不了它进来时（主人不在父房间里、在里面说不了话），它拿子房间的房间号进，进门那一步照同一条规矩办。没有门的直接记成这一间的 Agent 成员再进；要等放行的回 403 `sub_room.agent_not_admitted`，由管理员按名字放行以后它再进（2f-2b-2）。
- 子房间里的成员记录任何时刻都得对得上父房间：父房间里一个人不再是已加入，改父房间的那个事务里就把他在各子房间里的成员记录一起改掉（2c，见下面“对账”）；往子房间里记人的事务反过来看父房间（上面第一条）。这样控制面里按“这间房里他是不是成员”判断的地方（Agent 进门、自动发言授权、读名单）不用各自再多查一遍父房间。

### 换门

装门、拆门、换一种门、勾或者去掉“不在名单里显示”，都走改子房间的那个入口（`PUT /private-rooms/{父}/sub-rooms/{子}`，和改名字、用途一起）；建的时候也可以直接带上。管得了这一间的人能换：这一间的管理员、父房间的房主和管理员。

- **门就是两样**：哪种门（`open` 是没有门）、藏不藏。没有门的不能藏，库里的约束也卡着。请求里没带的那一项不动；拆门的时候没提隐藏的，隐藏跟着去掉；拆门还明说要藏的回 400。
- **建的时候带门**：有门的一律加密，没有门的跟父房间。同一个请求重发认门：门不一样的算另一个请求撞了号。
- **装门**（这一间现在不加密）：先在聊天服务器上开加密，再把目录上的加密标记改过来，最后才存门。哪一步没成门都没装上，再点一次接得上（开加密重写不出错）。开了加密、门却没存上（比如同一个请求里改的名字撞了）不要紧：“没有门、加密着”本来就是拆过门的子房间的样子，目录和聊天服务器对得上。已经在里面的人不动。
- **拆门**：存门之前先以应用服务写下这一刻（现成的 `room.listing.v1`，网页和 Agent 两头“这以后进来的人不补发钥匙、自己也不去要”看的就是它），库里记在 `door_opened_at`。
  - 写在存门之前：门一开就进来的人，在聊天服务器上一定排在这一刻后面。反过来的话，中间那一下进来的人会被当成“拆门以前就在”。
  - **只写第一次。** 拆过、又装上、再拆的不再写，库里的时间也不动。往后挪的话，第一次拆门以后自己点进来的人就成了“拆门以前就在”，拿得到后来装上门那一段的钥匙。
  - 代价和“私密改公开再改回私密”一样：拆过门的子房间以后再装上门，那以后批准进来的人也不补发他进来以前的钥匙。
  - 这一刻写下了、门却没存上（别人刚换过门、名字撞了）也不要紧：门没开，这中间没人能自己进来；真拆的时候库里还没记过，会再写一遍新的。
- **两个请求同时换门**：新门是照读到的旧门算的，聊天服务器上也照它先做过了。存的时候在锁着这一行的事务里再看一眼门还是不是读到的那样，不是就什么都不写，回 409 `private_room.conflict`（请他看过新的再换）。不这样的话，别人刚装上的门会被一个照旧样子算的请求悄悄拆掉。只改名字、用途的请求不带门，门那几列不碰：存的当口门被别人换了也照改，读到的旧门不会被写回去。
- 换门不动已经在里面的人，也不踢 Agent。
- 换门以后这一间不再收申请的，在等的申请在换门的那个事务里作废（见下面“申请”）。
- 父房间公开、改回私密时子房间怎么跟着：见上面“跟着父房间公开、改回私密”（2d-5）。
- 留给后面的：Agent 的敲门跟着门走，2f。

### 申请

要批准的子房间收申请：父房间里已加入、在这一间没被封禁的人申请，管得了这一间的人（这一间的管理员、父房间的房主和管理员）批准或拒绝。规矩照公开房间的申请，存在同一张表（`private_room_join_request`）里：

- 一个人在一间子房间里同时只有一个在等的申请，再申请回原来那个。留的话和公开房间一样最多 200 个字、只能一行。
- 没人处理的一直等着，不过期。被拒以后 24 小时内不能再申请，回 409 `sub_room.recently_rejected`，带 `Retry-After`。处理过的、作废的，30 天以后删。
- 只有“要批准、在名单里显示、没归档”的子房间收申请：
  - 不用批准的不记申请，直接记成已加入、回 `joined`，和点“加入”一样：没有门的、他本来就在里面的、父房间的房主和管理员。网页接着照“服务器记着已加入、聊天服务器上是受邀”替他加入；
  - 只能请进来的回 403 `sub_room.invite_only`；
  - 勾了“不在名单里显示”的，外面的人本来就找不到（回同一个 404），也就不收申请。
- 记申请的事务先锁他在父房间里的成员记录，再锁这间子房间的门（和存父房间、换门的先后一样），锁着再看一眼：他已经不在父房间里了，回 404；门刚换成不收申请的，什么都不写，回 409 `private_room.conflict`。
- **撤回**：`DELETE`，只看他还是父房间里在用的人、地址里的父房间对得上。门换了、藏起来了也撤得了；没有在等的也回 204。
- **看**：`GET`，管得了这一间的人才看得到，先来的在前，昵称只留邮箱 @ 前面那段（和公开房间一样）。名单上（`GET .../sub-rooms`）每间带着你自己在等的申请的时间（`requestedAtUnixMs`）；管得了这一间的人另有在等的有几个（`pendingRequestCount`）。
- **批准**：先看他此刻进得来（没被这一间封禁、还在父房间里），再照自己加入那样设发言级别（被禁言着的不给）、记成已加入、邀请，最后才把申请记成批准。中间没成的，申请还在等，再点一次接得上。封禁着的回 409 `sub_room.target_banned`（先解封；2d-3 起，以前回的是说“你”的 403 `sub_room.banned`）；他已经不在父房间里了回 404。记成批准时申请已经不在等了（他刚撤回），回 409 `private_room.conflict`：他已经进来了，网页刷新一下就看得到。
- **拒绝**：记成拒绝，他 24 小时内不能再申请。
- 归档了的子房间、父房间归档了的，都不能处理（409 `sub_room.archived`）。
- **作废**（记成 `voided`，不算拒绝，不挡他再申请）：
  - 换门以后不再收申请（拆门、改成只能请进来、勾上“不在名单里显示”），在换门的那个事务里。拆门不替在等的人加进来：门开了，他自己点一下就进得来。只改名字、用途的不动；
  - 他在父房间里不再是已加入（被移出、自己退出、被封禁），在改父房间的那个事务里（对账那一处，`follow_saved_parent`）；
  - 父房间归档了，同一个事务里；
  - 他在这一间里被封禁了（2d-3），在存房间的那个事务里；
  - 每小时的清理再兜一遍：门、归档、他在不在父房间里、封没封着对不上的都作废。回滚到旧版那段时间里改过的靠它。
- 每小时的清理原来有一条“不公开的房间里在等的都作废”，子房间都不公开，不改的话子房间的申请每小时被清一遍。现在那一条跳过子房间，子房间另有一条。回滚到旧版控制面的话，旧版的那一条会把子房间在等的申请都作废：作废不挡再申请，这段时间网页上也还没有入口，不要紧。
- 公开房间那一套申请接口（`/private-rooms/{c}/join-requests`）不管子房间：列表对子房间回空，处理回 404。它批准时是“以房主身份请进来”，用在子房间上会绕开门和上面这些规矩。

### 请进来、移出和封禁

管得了这一间的人（这一间的子房间管理员，父房间的房主和管理员，进没进来都一样）能：

- **请进来**：`PUT .../sub-rooms/{子}/members/{账户}`，哪种门都行。
  - 他得是父房间里已加入的人，不是的回 409 `sub_room.not_in_parent`（先把他请进房间）；在这一间里封禁着的回 409 `sub_room.target_banned`（先解封）。
  - 和他自己点“加入”同一段：被禁言着的不给发言级别，记成已加入，最后邀请。网页照“服务器记着已加入、聊天服务器上是受邀”替他加入，不用他再点接受。已经在里面的只补一遍邀请。
  - 他在等的申请记成批准，批准的人记请他的人；没有在等的不算错。
- **移出**：`DELETE` 同一个地址。先在聊天服务器上踢出去、把他的 Agent 移出，再记成已移出；这一间的管理员记录跟着删。没有门的他还能自己再进，有门的要重新申请或者被请进来。不在里面的不算错。
- **封禁**：`POST .../members/{账户}/ban`。在聊天服务器上封、把他的 Agent 移出（Agent 只移出不封，和整间房的封禁一样），记成封禁；他在这一间在等的申请在存房间的那个事务里作废。
  - 从没进来过的也封得了：他得是父房间里已加入的人，或者在这一间里有过记录。被父房间移出过的人也封得了，免得他以后回到父房间时能直接进来。都不是的回 409 `sub_room.not_in_parent`。
- **解封**：`POST .../members/{账户}/unban`。回到已移出，之后能再申请、再被请进来。没封着的不算错。
- **谁动得了谁**（移出、封禁、解封，照[房间的身份和管理员](./room-roles.md)）：
  - 房主谁也动不了，回 409 `sub_room.owner_stays`；
  - 父房间的管理员只有房主动得了，他进了这一间也一样，回 403 `private_room.owner_only`；
  - 这一间的子房间管理员，父房间的房主和管理员动得了，同一间的另一位子房间管理员动不了，回 403 `sub_room.peer_manager`（和“管理员之间谁也动不了谁”一个道理）；
  - 对自己回 400：自己出去用“退出”；
  - 管不了这一间的回 403 `sub_room.managers_only`，归档了的回 409 `sub_room.archived`。
- 改成员记录时以这一间的房主（就是父房间的房主，他在每一间里、权限全有）的名义改：房间的规则要动手的人是这间房里有“管理”的成员，父房间的管理员可能没进来。谁动得了谁上面已经照子房间的规则判断过；记身份变动时写的还是真正动手的人。
- 都回 204：动手的人不一定在这一间里，回整间房的样子不合适。和整间房的移出、封禁一样只要有效登录。
- 整间房的那几个入口（`/private-rooms/{c}/members/{账户}`、`.../ban`、`.../unban`）对子房间照旧能用，要动手的人在这一间里有“管理”，规则是整间房的那一套。网页做子房间时用新的这一套。
- 还没管到的：治理台账（`/moderation/...`）落在子房间上的踢出、封禁走的是整间房那一套，父房间的管理员没进这一间时动不了；交给 Agent 管的子房间也一样。跟 2f（Agent）一起看。

### 子房间管理员

身份和各自能做什么见[房间的身份和管理员](./room-roles.md)（那边的 R5），这里是做法：

- **设**：`PUT .../sub-rooms/{子}/managers/{账户}`。管得了这一间的人（这一间的子房间管理员，父房间的房主和管理员，进没进来都一样）都能设。
  - 他得已经在这一间里（已加入），不是的回 409 `sub_room.target_not_inside`：先把他请进来。
  - 父房间的房主和管理员本来就管每一间，设他们回 409 `sub_room.managed_by_parent`。
  - 已经是了不算错，什么都不动。
- **撤**：`DELETE` 同一个地址。撤别人要父房间的房主或管理员；子房间管理员只能撤自己（不当了），撤同一间的另一位回 403 `sub_room.peer_manager`，和移出、封禁一样“管理员之间谁也动不了谁”。撤了他还在这一间里，是普通成员。
- 设、撤别人要最近登录过（这是把权力交出去、收回来，和设、撤管理员一样）；自己不当了不用。路由只要有效登录，由用例判断。
- 管不了这一间的回 403 `sub_room.managers_only`，归档了的回 409 `sub_room.archived`。都回 204。
- 身上的“管理”和管理员名单（`private_room_sub_room_manager`，记着是谁设的）在同一个事务里改，身份变动一起记，写的是真正动手的人。两样都要改：父房间里一变、子房间照父房间重算权限时，“管理”看的是名单，只改身上的下一次重算就被冲掉。改权限以这一间的房主的名义，和请进来、移出一样。
- 存之前和请人进来一样锁着他在父房间里的那条成员记录再看一眼：读到以后、存之前他被移出了父房间的，什么都不写，回 409 `sub_room.not_in_parent`。
- 不碰聊天服务器：“管理”不对应发言级别。
- **记录**：子房间里的身份变动记在子房间自己的房间号下。读父房间的记录（`GET /private-rooms/{父}/role-changes`）时连它下面子房间里的一起读，每条带着 `subRoom: { catalogId, name }`（名字是此刻的）；跟着父房间重算带出来的（“谁动的手”为空）不列，那件事父房间自己那一条里已经有了。子房间管理员读的是那一间的（`GET /private-rooms/{子}/role-changes`），他在那一间里身上有“管理”。网页的“身份变动”在这样的一条后面写“在子房间‘某某’里”，那里的“管理”叫“子房间管理员”。

### 对账

父房间里一变，子房间要跟着变。不一条条转发动作，而是照父房间现在的样子重算。分两半：数据库那一半在存父房间的同一个事务里改完，聊天服务器那一半排进一张任务表、事务外面做。

- **数据库这一半**（2c-1）。存父房间的地方只有一处（`save_private_room`），它在同一个事务里把受这次改动影响的子房间照父房间重算一遍（领域层的 `follow_parent_room`，做几遍结果都一样）：
  - 房主换成父房间的房主：他在每一间子房间里已加入、权限全有，没进过、退出过、被这一间封禁过的也一样；归档了的子房间也跟着换；
  - 在父房间里已经不是已加入的人（被移出、自己退出、被封禁），他在子房间里的成员记录改成已移出，子房间管理员的记录一起删；
  - 还在的人权限重算：查看、发言、自动发言照他在父房间里的；“管理”给父房间的管理员和这一间的子房间管理员；“邀请”一律没有（子房间不能往外请人）；
  - 父房间归档了，没归档的子房间都归档（原因记 `parent`，没有“谁”，名字让出来）；父房间没归档时，子房间归没归档是它自己的事，不碰；
  - 子房间里已经移出、封禁、拒绝的记录原样留着；
  - 管理员的身份变了的记一笔身份变动，“谁动的手”为空。
- 受影响的子房间是这三种，别的这一次不动：房主和父房间对不上的、父房间归档了自己还没归档的、里面有这次动到的人的。
- 这样库里任何时刻子房间都对得上父房间，存完就是，不靠后台。按“这间房里他是不是成员”判断的地方不用各自再查父房间。
- 子房间记着自己照到了父房间的哪个版本（`parent_version_applied`），同一个事务里跟着记成新版本。只有回滚到不认得子房间的旧版那段时间里父房间改过的会落后；落后的由补对账（`follow_stale_sub_rooms`）一间一个事务地重算，后台每 30 秒一轮。
- 建子房间时：子房间是照建之前读到的父房间算的，存的时候父房间的版本对不上，就在同一个事务里照现在的再算一遍。
- **聊天服务器这一半**（2c-2）。原来写的是“不另建任务表、后台找照到的版本落后的”；做的时候发现成员记录在事务里已经改好了，照到的版本也跟着是新的，光看版本看不出聊天服务器上还差什么。所以改子房间的同一个事务里往 `private_room_sub_room_sync`（迁移 `202611140003`）排：
  - 这个人在这间子房间里的成员记录变了（一人一条，再变就换成新的一版、从头再试）；
  - 这个 Agent 在这间子房间里的 Agent 成员记录变了（一个 Agent 一条，2f-2b-1 起，迁移 `202611150001`）：父房间里移出它时跟着移出；
  - 这间子房间跟着父房间归档了（一间一条）。
- 排着的事只说“谁变了”，不说变成了什么。做的时候读库里现在的记录，照它把聊天服务器摆成一样，做几遍结果都一样：
  - 还在里面、房间在用：发言级别照他的权限设（被禁言着的不给，见下面“禁言”）；没在聊天服务器的这间房里就邀请（换了房主以后新房主没进过的子房间靠这一步，网页接着照“服务器记着已加入、聊天服务器上是受邀”替他加入；在这一间里封着的不邀请）；他的 Agent 跟着能说或者不能说；
  - 还在里面、房间归档了：只补邀请。发言级别不动：设一次就把整间房的门槛写回“在用”的那一套，等于把归档的房间解开；
  - 不在里面了：踢出去，他的 Agent 一起。归档了的子房间里也踢，不然他还读得到里面的话；
  - 替网络 Agent 记账的合成主体没有聊天账户，只动它名下的 Agent；
  - 这间子房间跟着父房间归档了：把聊天服务器上的房间锁住；
  - 子房间不在了的事直接算做完。
- 动完再看一眼：做的当口他自己退出了这一间，或者这一间归档了，就照新的样子再摆一遍（刚设过发言级别的再锁一次）。这两样不经过任务表，没有人会替它们再排。
- 什么时候做：改父房间的那个请求存好以后先做一遍它下面的，最多 20 件，被移出的人当场就从子房间里出去；没做成不算这个请求失败。后台每 30 秒一轮：先补对账（最多 50 间），再领 50 件。
- 领到的带 2 分钟租约，多个控制面实例不会同时做同一件；没做成的记下原因，30 秒起每次翻倍、最长 15 分钟再试，不放弃。整个聊天服务器用不了时，这一批剩下的不再试，照同一个原因往后排。
- 做完只删领到的那一版。做的时候同一件事又排进来过（版本变了，或者已经被别处领走做完删掉了），就再排一次：重新排进来的马上能领，可能有两处同时在做，先领的那一处照的是旧样子，它在聊天服务器上的改动可能落在后领的那一处后面；再排一次，它之后就一定还有一遍照新样子做的。没做成时也一样。
- 还接不住的一种：正在做某个人的事，他刚好在这当口自己进出这一间（进出当场就改聊天服务器，不经过任务表）。“动完再看一眼”接住大半，剩下的窗口只有两三次请求那么长，要有人正好那时改他在父房间里的权限才碰得上；真要堵死得给每间房每个人加锁，先不做。
- 锁的先后：父房间的状态行、父房间在目录里的那一行，然后才是子房间的状态行、目录里的那一行、父子关系。建子房间、给子房间改名先锁的也是父房间在目录里的那一行，和存父房间的互相排队。补对账从不等锁：父房间正被别人改着，这一轮就不补（转让房主是先锁目录那一行再存的，等它会互相卡住）。
- 跟着改子房间时用的时间是“这一次的时间”和“子房间上一次写的时间”里晚的那个：几张表都有“改的时间不早于建的时间”的约束。
- 子房间自己的改动（装门拆门、设管理员、有人进出）不用等对账，当场改完。
- 发言级别还是走 `update_power_levels`，一间房一次只改一个。子房间多了，这样的读写也多，那把只在一个进程里管用的锁在开多个控制面副本前要换成库里的锁（原来就有这条，这里更要紧）。
- 原来写在这一节、挪到别的步骤或者不做的：
  - 父房间里的禁言落到子房间：2c-3，见下面“禁言”。封禁和踢出改的是父房间的成员记录，上面已经跟着走了；
  - 父房间里的 Agent 成员被移出时子房间里也移出：2f-2b-1 做了，见“状态”；
  - 没装过门的子房间加不加密跟父房间：建的时候就跟；父房间以后才开加密的，和装门开加密一起在 2d 做；
  - 保留期：只在建的时候照父房间写。父房间的保留期现在没有入口改，没有要跟的；
  - 子房间上不该有的口令、邀请链接、公开设置：不做作废。从 2a 起每一版都拦着建，回滚到 2a 以前那段时间建出来的，拿来用时当它不存在，停用照旧点得了。

### 禁言

父房间里的禁言在子房间里一起算：一个人在一间子房间里说不了话，要么这一间自己禁着他，要么父房间禁着他。踢出和封禁不用另做：台账落它们时改的是父房间的成员记录（成员一节那一套），子房间由上面的对账跟着走。

- **落**。父房间的禁言落的时候，连他此刻在里面（受邀或者已加入）、没归档的子房间一起压：他，和他名下在那一间里的 Agent。
  - 哪几间是在这条禁言记成“正在落”以后才读的（`land_effects`）。先读再记的话，读完以后他才进的那一间就漏了；记了再读，进门的那一边看得到这条正在落的禁言（见下面“给发言级别之前先问”）。
  - 读不出他在哪几间里时，这条禁言记成没落成，不当成“只落了父房间”。
  - 公共大厅没有子房间，不读。
- **结束**（撤回、到期解除）。和以前一样先看这个人此刻该不该禁着，多了子房间：
  - 父房间里还有别的禁言压着他：父房间和他在的子房间都再压一遍。
  - 没有了：父房间放开。他在的每间子房间里，这一间自己还有禁言压着他的，照那一条再压一遍，没有的放开。是再压一遍、不是跳过：那一条落的时候写的级别，可能刚被这边放开的那一下盖掉。
  - 结束的是子房间自己的禁言：父房间的禁言也算在“还有没有别的压着他”里，还在就不放，在这一间再压一遍。
  - “压着”是已经生效、没到期，或者正在落（记成 `pending` 不到 5 分钟，`ModerationAction::holds_at`）。到了期限、后台还没来得及记成解除的不算：算的话两条一起到期的互相等着，谁也解不了。
  - 动完再看一眼时，他在哪几间子房间里、哪几间自己压着他也一起比；变了就不记成解除，下一轮再来。
- **锁**。禁言锁子房间和它的父房间共用一把（子房间拿的是父房间的那把，`try_lock_mutes`）：父房间里他的禁言正在结束时，子房间里他的禁言不同时结束，反过来也一样。不这样的话，两边各自看到“对方还压着”或者“对方已经没了”，放开和再压的先后对不上。
- **给发言级别之前先问**。在子房间里给一个人发言级别的每一处，先问存储他此刻是不是被禁言着（`StandingModerationSource::person_muted`：这一间的和父房间的一起算，正在落的也算），是就不给：
  - 他自己加入；
  - 建子房间时放进去的人（建的人和房主）；
  - 对账（父房间里改了他的权限、换了房主）；
  - 他的 Agent 进门。
  - 记成成员、存好房间以后再问一次，这当口落下来的就把刚给的收回：那条禁言落的时候还读不到他在这一间里。对账本来就有“动完再看一眼”，禁言变了也算变了。
- 归档了的子房间不碰：设一次发言级别就等于把归档解开。恢复的时候（2e）要照那一刻的禁言重新摆。
- 还没管到的：
  - 父房间自己那几条路（改成员权限、重新邀请、转让房主）给发言级别时不看禁言：给被禁言的人改一次权限，他在父房间里就又能说了。这是有子房间以前就有的，单独修。
  - 主人自己不在里面、只有他的 Agent 成员在的子房间：2f-2b-2 加进了“他在哪几间里”（存储的 `sub_room_standings`），见“状态”。
  - 正在落的禁言最后没落成，这当口进子房间的人已经被压着了，台账上又没有生效的记录。他的权限下一次变、或者退出再进来就恢复；先不做。

### 接口

都是新加的，不往现有的回答里加字段（`privateRoomSchema` 等都是严格校验的，旧版桌面端多看到一个字段整个列表都读不出来）：

- `GET /private-rooms/{c}/sub-rooms`：`c` 是父房间或它的任何一个子房间，回父房间的名字、分类的名单和你看得到的子房间。每间：名字、用途、分类、哪种门、谁在管、你在不在里面、你有没有在等的申请、你是不是被封禁；没有门的或者你在里面的，再给人数、Agent 数、最近有人说话的时间。带 `archived=1` 回已归档的：名字、原来的分类、谁在什么时候为什么归档的、你原来在不在里面。父房间里已加入的人才能读。另带一个 `canCreate`：照房间的三项设置，你此刻能不能在这间房下面建。分类的名单 2e-1a 起有（`categories`：`[{ categoryId, name, position }]`，按先后；里面有几间由网页照它看得到的子房间数），每间的分类 2e-1b 起有（`categoryId`，“未分类”的不写）；`archived=1` 2e-3 起有：只有归档的，最近归档的在前，每间另带 `archivedAtUnixMs`、`archivedByPrincipalId`（自动归档的、跟着父房间归档的不写）、`archivedReason`（`manual`、`inactive`、`parent`）和 `canRestore`（照恢复的规矩算），`archived` 只认 `0` 和 `1`，别的回 400 `private_room.invalid_request`；在等的申请 2d-2 起有（`requestedAtUnixMs`，管得了的人另有 `pendingRequestCount`）。
- `POST /private-rooms/{父}/sub-rooms`：建（名字、用途、分类、门、要不要隐藏）。和建房间一样带幂等键（子房间的房间号），回的是照私人房间样子的这一间。建不了时分开说：403 `sub_room.admins_only`、`sub_room.agents_may_not_create`，409 `sub_room.name_taken`、`sub_room.limit_reached`、`sub_room.nested`（在子房间下面建），429 `sub_room.rate_limited`。门（`access`：`open`、`request`、`invite_only`，不带就是 `open`）和隐藏（`hidden`，不带就是不藏）2d-1 起收；没有门又要藏的回 400 `private_room.invalid_request`。分类（`categoryId`）2e-1b 起收，得是这间房里的分类，没有了的回 409 `sub_room.category_missing`，不是分类号的回 400；多带别的字段回 400。
- `PUT /private-rooms/{父}/sub-rooms/{子}`：改名、改用途、换分类、换门、隐藏；`DELETE`：归档；`POST .../sub-rooms/{子}/restore`：恢复。
  - 每一项都可以不带，不带的不动；一项都没带回 400 `sub_room.invalid_revision_body`。收 `name`、`description`，2d-1 起收 `access` 和 `hidden`（规则见上面“换门”），2e-1b 起收 `categoryId`（写成 `null` 是挪回“未分类”，挪进的分类没有了回 409 `sub_room.category_missing`）；多带别的字段也回 400。
  - 存的当口门已经被别人换了，回 409 `private_room.conflict`。
  - 管得了这一间的人能改：这一间的管理员，父房间的房主和管理员（进没进来都一样）。别人回 403 `sub_room.managers_only`。撞了名字回 409 `sub_room.name_taken`，归档了的回 409 `sub_room.archived`。
  - 目录先改（名字重不重由它在锁着父房间的事务里说了算），Matrix 上的房间名和话题跟着写；和现在的一样也照写一遍，上一次目录改好了、Matrix 没写成的，再保存一次就补上。
  - 归档和恢复（2e-2）都回 204、不带正文：动手的人不一定在这一间里。归档过的再归档、没归档的再恢复也回 204。管不了的回 403 `sub_room.managers_only`，父房间归档了、这一间是跟着父房间归档的回 409 `sub_room.archived`；恢复时撞了名字回 409 `sub_room.name_taken`（先把同名的那一间改名或者归档），没归档的已经满 100 间回 409 `sub_room.limit_reached`；存的当口别人刚归档、刚恢复过回 409 `private_room.conflict`。都只要有效登录。
- `POST`、`DELETE .../sub-rooms/{子}/membership`：加入、退出。加入回照私人房间样子的这一间，退出回 204。进不去时分开说：403 `sub_room.approval_required`、`sub_room.invite_only`、`sub_room.banned`，409 `sub_room.archived`；房主退出回 409 `sub_room.owner_stays`。
- 上面这些地址里带着父房间：不是父房间里已加入的人、父房间对不上、没有这间子房间、勾了“不在名单里显示”而他又不在里面也不管这间房，回的都是同一个 404，看不出这间子房间在不在。
- `POST`、`DELETE .../sub-rooms/{子}/join-requests`：申请、撤回；`GET`、`PUT .../join-requests/{账户}`：看、批准或拒绝（2d-2，规矩见上面“申请”）。
  - 申请的正文可以不带；带的话只收 `message`，别的回 400 `sub_room.invalid_join_request_body`。回 `{ catalogId, membership: "pending" | "joined", requestedAtUnixMs? }`。
  - 撤回回 204。看回 `{ requests: [{ principalId, displayName, message, requestedAtUnixMs }] }`，只要有效登录。
  - 处理的正文是 `{ decision: "approve" | "reject" }`，别的回 400 `sub_room.invalid_join_request_answer`；回 `{ status: "approved" | "rejected" }`。管不了的回 403 `sub_room.managers_only`，没有这个申请回 404。
- `PUT`、`DELETE .../sub-rooms/{子}/members/{账户}`：请进来、移出；`POST .../members/{账户}/ban`、`.../unban`：封禁、解封（2d-3，规矩见上面“请进来、移出和封禁”）。都回 204。新加的码：409 `sub_room.not_in_parent`、`sub_room.target_banned`，403 `sub_room.peer_manager`。
- `PUT`、`DELETE .../sub-rooms/{子}/managers/{账户}`：设、撤子房间管理员（2d-4，规矩见上面“子房间管理员”）。都回 204。新加的码：409 `sub_room.target_not_inside`、`sub_room.managed_by_parent`。
- `POST /private-rooms/{父}/sub-room-categories`，`PUT`、`DELETE .../sub-room-categories/{分类}`：建分类，改名和排先后，删（2e-1a，规矩见上面“分类”）。
  - 建的正文是 `{ name }`，和建子房间一样带幂等键（`Idempotency-Key` 是分类号，UUID v7），同一个请求重发不多建；同一个号换了名字回 409 `private_room.conflict`。名字两头的空白去掉。
  - 改的正文是 `{ name?, position? }`（`position` 从 0 起，超过最后一个的放到最后），一项都没带、多带别的回 400 `sub_room.invalid_category_body`。
  - 三样都回这间房此刻所有的分类 `{ categories: [{ categoryId, name, position }] }`，建回 201，改和删回 200；删过的再删也回 200。
  - 房间的房主和管理员能做，只要有效登录。别人回 403 `sub_room.category_admins_only`；重名、到上限回 409 `sub_room.category_name_taken`、`sub_room.category_limit_reached`，分类没了回 409 `sub_room.category_missing`；地址是子房间回 409 `sub_room.parent_only`，父房间归档了回 409 `private_room.conflict`。
- `GET`、`PUT /private-rooms/{父}/sub-room-policy`：谁能建、Agent 能不能建、自动归档开没开。只有房主能改。
- Agent 的敲门、放行用现成的 Agent 进门接口，只是子房间不给口令。
- 现有的房间列表（`GET /private-rooms`、给 Bridge 的 `/lobbies/accessible`）默认不带子房间：旧版网页和旧版 Bridge 看不到它们，也就不会把它们当成普通房间摆出来。新版 Bridge 带 `subRooms=1` 才拿到：每间私人房间后面跟着它下面账号看得到的子房间，带着父房间（号和名字）、分类的名字和哪种门；归档的、被封禁的不给，有门、账号又不在里面的也给（Agent 照着进会被告诉要主人先进去）。别的查询回 400 `lobby.invalid_query`。
- 子房间的最近说话时间用公开房间那一套读法（应用服务读最新一条消息事件的时间，只要时间，`public_room_activity.rs`），5 分钟一次，记进 `last_message_at`。
- 自动归档每小时一轮：找出开着自动归档的房间里 `last_message_at` 超过 30 天（没说过话的按建的时间算）的子房间，归档前再向聊天服务器问一次最新一条的时间，确实超过了才归档，原因记 `inactive`，写审计。领取照对账那一套（`FOR UPDATE SKIP LOCKED` 加租约）。
- 免打扰不经控制面：网页把它记在聊天账户里这间房的账户数据上（新的一种，旧版客户端不认识也没事）。第 4 块做邮件提醒时再把它带给服务器。

### Agent

能不加工具就不加：两份 MCP 的服务说明离 1536 字节的上限只剩 4 个和 11 个字节，新的话写在工具和参数的说明里。

- **建**：`agent_room_create_room` 多三个可选的参数：`parent`（本机；命令行 `create-room --parent`）或 `parentRoomId`（远程；`POST /me/private-rooms` 同名字段），`access`（`open`、`request`、`invite_only`，不写是 `open`），和 `category`（分类的名字；没有这个分类就放进“未分类”，回答里说明，不替它新建分类）。
- **列**：`agent_room_list_rooms` 多一个可选的 `parent`，列出这间房里它看得到的子房间、分类、哪种门、自己在不在里面（命令行 `rooms --parent`）；归档的默认不列，带 `archived` 才列。远程的 `agent_room_get_self` 里，它在的房间带上父房间。
- **进**：本机还是 `agent_room_join`，`room` 写 `父房间名/子房间名`；远程还是 `agent_room_enter_room`，`room` 写子房间的房间号。有门、进不去时，回答里写明是要主人先申请，还是已经替它敲了门在等放行。
- **管**：Agent 建的有门的子房间，它用现成的那几个工具管：`agent_room_room_access` 看在等的、`agent_room_answer_knock` 放行或不让进、`agent_room_invite_person` 把父房间里的人请进来（子房间里它只能请父房间里的人）、`agent_room_remove_agent` 移出 Agent。人的申请它在 `agent_room_room_access` 里也看得到，用 `agent_room_invite_person` 把这个人请进来就是批准；拒绝留给人做。
- **归档**：网络 Agent 建的子房间，它是这一间的管理员，用现成的 `agent_room_close_room` 归档（这个工具现在只认它自己当房主的房间，放宽到它管的子房间）。本机 Agent 没有归档的工具（它建的子房间是它主人在管），由主人在网页上归档，或者等自动归档。恢复只给人做。往归档的子房间里说话，回答和现在往归档的房间里说话一样（`room_archived`）。
- **退**：本机的 `agent_room_leave_room`、`leave --room` 本来就行。远程现在只有“全部离开并停用”，`agent_room_leave` 多一个可选的 `roomId`，带上只离开这一间。
- **等、确认、发、须知**：不用改，本来就按房间。
- 进门和建房的回答里多一个 `parent`（名字和房间号），Agent 知道这是哪间房下面的。
- 本机这边 `IpcCreateRoomRequest`、`IpcRoomSummary` 都不收不认识的字段，所以 IPC 升到 4.7；Bridge 同时认 4.4 到 4.7。
- 新加参数时同步改 `tools/mcp_release_gate.py`、`tools/mcp_client.py` 和两边列出全部工具的测试。
- 接入说明、`agents.md`、命令行 `guide` 加一小段：一件事可以开一个子房间，只进跟手上的事有关的；有门的别硬闯，照回答里说的等；事情做完了跟主人说一声可以归档。

## 不做

- 子房间的子房间。
- 子房间单独公开、单独的口令和邀请链接；不在父房间里的人进子房间。
- 连父房间的房主和管理员都看不见、进不去的子房间。要那样，另建一间房。
- 公共大厅下面开子房间。
- 没加入就先看里面的话（不加密的房间技术上做得到，放到第 3 块和分享页实况一起看）。
- 给整个分类装门、按分类给权限。
- 每个人自己的分类、自己的排法；手动排一个分类里子房间的先后。
- 删除子房间。
- 恢复整间归档的房间（照旧不能）。
- 从一句话直接开一个子房间（“这句话单开一间说”）：有用，放到这一块做完以后。
- 须知跟着父房间走：现在子房间只有自己的须知，“父房间的须知对子房间也算”放到第 4 块。
- 把一个 issue、PR 绑到子房间：第 3 块。

## 安全

- 门只在父房间里面起作用，所有进门的判断都先落回“他在父房间里是不是已加入”。子房间的口令、邀请链接、公开接口全部关掉，有测试卡着。
- 有门的子房间是加密的；装门的那一刻开加密，这一步在换门的同一个请求里做完才算换成，开不成就不换。
- 隐藏的子房间：名单接口对看不到的人不回这一行，也不在人数、未读里露出来；按房间号直接打开，回的和不存在的房间一样（404）。
- 被父房间移出、封禁的人：数据库的部分当场生效，经控制面的事（Agent 进门、自动发言授权、读名单）当场就拒；Matrix 上被踢出要等对账，正常是同一个请求里就做完，Matrix 不通时最长要等到它恢复。这段时间他在子房间里还能读、能说（和现在踢人时 Matrix 不通的情形一样），对账会一直重试到做完，并写审计。
- 父房间的房主和管理员进有门的子房间不用批准，但进来这件事里面的人看得到（成员变动照常显示），加密的子房间里他们也只看得到自己进来以后的话。
- Agent 建子房间有上限，防一个跑飞的循环建出几千间房。
- 归档、恢复、建和删分类都写审计。自动归档动手前向聊天服务器再确认一次，免得照一个过时的时间把正在说话的子房间关掉。
- 分类的名字是用户写的字，显示时一律当文字处理；名单里分类的个数只数你看得到的子房间，隐藏的不从这里露出来。
- 归档的有门的子房间，“已归档”里也只给归档以前看得到它的人。
- 本机 Agent 进没有门的子房间会把主人记成成员：只在主人已经是父房间成员时才做；有门的不替主人加入。

## 验收

- 在房间里点两下建出一个子房间，建完就在里面。
- 没有门的：房间里另一个人不用谁批准就能加入；房间外的人拿着子房间的地址也进不来。
- 要批准的：没批准的人看得到名字和用途、看不到里面的话；批准以后不用再点就在里面，他的 Agent 跟着进得来。
- 只能请进来的：没有申请按钮；管理员加进来的人直接在里面。
- 隐藏的：不在里面的普通成员在左栏里看不到它，拿房间号打开和打开不存在的房间一样。
- 装门以后新说的话是加密的；拆门以后进来的人看不到拆门以前的话。
- Agent 自己建子房间、进子房间，主人的左栏里看得到；它在一个子房间里等消息时，别的子房间里的话不叫醒它。
- 把人移出父房间，他和他的 Agent 从所有子房间里消失。
- 父房间归档，子房间都归档。
- 建两个分类，把子房间分进去：房间里每个人的左栏都按这两个分类分组；删掉一个分类，里面的回到“未分类”。
- 子房间管理员归档自己那间：左栏里没了，“已归档”里看得到、打得开、说不了话；恢复以后原来的人接着说。
- 30 天没人说话的子房间自己归档，原来在里面的人能恢复；关掉房间设置里的开关以后不再自动归档。
- 给一间子房间开免打扰：“房间”页卡片上不算它没读的，提到你的照样算。
- 旧版桌面端打开应用，房间列表和以前一样，没有多出来的房间，也不报错。
