# 子房间（第 2 块）

[重新设计总纲](./design.md)的第 2 块。2026-11-13 维护者说：一个项目一间房可能不够，房间下面要能开子房间，房间里的人和 Agent 可以任意创建和加入。

设计稿是 Artifact“房间页重排与子房间”的第 1、2、4 张。房间页左边那一栏在[第 1 块](./room-page.md)里留好了位置。

## 背景

- 一个项目里同时有好几件事：发版、某个 issue、官网改版。现在只能都在一间房里说，或者另建几间互不相干的房间，每间都要重新请人、请 Agent。
- 对 Agent 更要紧：它一直守着房间等消息，房间里说的每件事都可能叫醒它。一件事一个子房间，它只进跟自己手上的事有关的，别的吵不到它。
- 现在已经有的、能直接用的：
  - 一个 Agent 用同一个身份进好几个房间，一次等所有房间的消息，每个房间各记读到哪（[本机 Agent 跨房间用同一个身份](../agent-identity/design.md)；网络 Agent 也能进好几间）。
  - Agent 能建房间（[Agent 自己建房间、管房间](../agent-rooms/design.md)）。
  - 服务器记着某人“已加入”、Matrix 上他只是受邀时，网页替他加入（`PrivateRoomJoinBoundary`）。
- 现在的房间模型里没有“房间属于另一个房间”这回事：
  - 房间目录只有三种（公共大厅、私人房间、私聊），公开房间也是私人房间加一张公开设置的表。种类和可见范围都有约束卡着，加新值会让回滚读不出来。
  - 每间私人房间必须有一个房主，房主必须是已加入、五项权限全有的成员（提交时才查的约束触发器）。
  - 人进房间只有“先邀请、再自己加入”一条路；Agent 进房间要它的主人已加入、能发言，或者它自己凭口令、敲门进来过。
  - 禁言、踢出、封禁按房间记，一间房里的不管另一间。

## 想要的样子

- 房间页左边一栏：最上面是主房间，下面是你在的子房间（带未读和 @），再下面是还没加入的。
- 点“+”，起个名字、写一句用途，子房间就建好了，你已经在里面。
- 点一个没加入的子房间，看到它的名字、用途、谁在里面、多久以前有人说话，一个“加入”按钮。
- 跟你的 Agent 说“开个子房间说发版的事”，它建好、进去，你这边左栏里多出这一项。
- 把人请进房间，他就能进任何子房间；把人移出房间，他在所有子房间里也一起出去。

## 规则

### 是什么

- 子房间是挂在一间房下面的房间，只有一层：子房间下面不能再开。
- 能有子房间的是私人房间和公开房间。公共大厅和私聊没有。
- 子房间自己是一间完整的房间：有自己的对话、自己的成员、自己的 Agent、自己的须知，Agent 等消息、读到哪都按它单独算。
- **子房间没有自己的门。** 进得了父房间的就进得了它的任何子房间，进不了父房间的谁也进不来：子房间没有口令、没有邀请链接、不能单独邀请人、不能敲门、不能单独设成公开。要让一个人进子房间，就请他进父房间。

### 建

- 父房间里已加入、能发言的人都能建。
- 父房间里的 Agent 都能建：
  - 本机 Agent 替它的主人建，主人要在父房间里能发言；
  - 网络 Agent 自己建，它要是凭口令或敲门进了父房间的，或者父房间就是它建的。
- 建的时候填名字（同一间房里没归档的子房间不重名，不分大小写）和一句用途（可以不填）。
- 建好以后建的人已经在里面；Agent 建的，它自己在里面，它的主人也算在里面（见下面“加入和退出”）。
- 上限是防失控用的，不是为了管人：每间房最多 100 个没归档的子房间；同一个人或 Agent 一小时最多建 10 个。子房间不占账户的公开房间名额，也不占网络 Agent 的建房名额。

### 加入和退出

- 父房间里已加入的人，点一下就加入，不用谁批准。
- 父房间里的 Agent 自己进：
  - 本机 Agent 按名字进（`父房间名/子房间名`），它的主人要在父房间里能发言。**它进去的时候，主人也记成这个子房间的成员**：你的 Agent 在哪间子房间，你就在哪间，左栏里看得到，也对它在里面说的话负责。
  - 网络 Agent 拿子房间的房间号进，不用等人放行，只要它在父房间里。
- 退出随时可以。人退出时他的 Agent 跟着退出（和现在的房间一样）。
- 被移出某个子房间的人还能再进；要不让他进，封禁他（在这个子房间里，或者在父房间里）。

### 权限和管理

- 每个人在子房间里的权限就是他在父房间里的权限，不单独设。在父房间里被改了权限，子房间里跟着变。
- 父房间的房主也是每个子房间的房主；父房间转让了，子房间一起转。
- 父房间的管理员进了哪个子房间，在那里也是管理员：能改须知、移出、封禁。
- 建子房间的人能给它改名、改用途、归档它。
- 父房间里的禁言、踢出、封禁，在所有子房间里一起算；到期解除、撤回也一样。
- 父房间归档，子房间一起归档。子房间可以单独归档，归档了不占 100 个的名额，“归档的”里还看得到。

### 加密和谁读得到

- 子房间跟父房间一样：父房间加密，它就加密；父房间是公开的、不加密，它也不加密。
- 父房间以后改了（公开改回私密会开加密），子房间跟着改。
- 父房间是网络 Agent 建的，服务器读得到全部消息，子房间也一样，界面上照父房间那样写明。
- 后进子房间的人，不加密的看得到以前的消息；加密的只看得到自己进来以后的，别人的设备和 Agent 会照现在“找回加入前的消息”的规则补发（网络 Agent 照旧不补）。
- 保留期跟父房间。

### 看得到什么

- 父房间里已加入的人都看得到子房间的名单：名字、用途、里面有几个人几个 Agent、多久以前有人说话。没加入的看不到里面的话。
- “房间”页的卡片只有父房间一张，未读和 @ 把你在的子房间的也算进去。
- 发现页和分享页不单独列子房间。分享子房间的链接就是父房间的链接。
- 不登录的围观只看主房间。

## 做法

### 模型

- 子房间在房间目录里就是一间私人房间（`kind = 'private_room'`），不加新的种类。另加一张表记它属于谁，做法和公开设置那张表一样：

  `private_room_parent`：`catalog_entry_id`（子房间，主键）、`parent_catalog_entry_id`、`created_by_principal_id`、`created_by_agent_id`（可空）、`parent_version_applied`、`created_at`。约束：父房间自己不能在这张表里当子房间（只有一层）。

- 因为它就是一间私人房间，现成的都能用：建 Matrix 房间、成员表、Agent 的位置、发言级别、须知、归档、网页的加入、Agent 进门、等消息、读到哪。
- 约束触发器要求房主已加入、权限全有：子房间的房主记成父房间的房主，建的时候就给他一条已加入的成员记录。他在 Matrix 上只是受邀，打开时由网页替他加入。父房间的房主是网络 Agent 时照旧不邀请。
- 子房间的公开设置、口令、邀请链接、敲门记录这几张表不写；对应的接口对子房间一律回 409 `sub_room.no_own_door`。
- 父子关系只记在控制面，不用 Matrix 的 Space，也不往房间状态里写。

### 进门

- **人加入**：`POST /private-rooms/{父}/sub-rooms/{子}/membership`。查他在父房间里已加入、在子房间里没被封禁，然后直接记成已加入（权限照抄父房间的），以房主的名义在 Matrix 上邀请他、设好发言级别。网页接着照“服务器记着已加入、Matrix 上是受邀”那一套替他加入。不走“受邀 → 接受”两步：加入是他自己点的。
- **本机 Agent 进**：进门的规则（`admits_agent_of`）不变，还是要主人在这间房里已加入、能发言。只是子房间的进门请求里，主人还不在子房间时，先照上一条把主人加进去，再让 Agent 进。主人不在父房间、在父房间里不能发言、在子房间里被封禁，都进不去。
- **Agent 成员进**（网络 Agent、凭口令或敲门进了父房间的本机 Agent）：对子房间敲门时，它在父房间里是已加入的 Agent 成员就直接放行，记成敲门进来的，不留等待记录。
- 控制面里凡是按“这间房里他是不是成员”判断的地方（进门、自动发言授权、读名单），子房间多查一条：他在父房间里还是已加入。这样对账还没跑到时，经控制面的事也不会放错。

### 对账

父房间里一变，子房间要跟着变。不一条条转发动作，而是按版本对账：

- 父房间每次改动本来就会加版本号（`private_room_state.version`）。子房间记着自己照到了父房间的哪个版本（`parent_version_applied`）。
- 对账做的事是照父房间现在的样子重算一遍子房间，做几遍结果都一样：
  - 房主换成父房间的房主；
  - 每个成员的权限换成他在父房间里的；在父房间里已经不是已加入的，从子房间移出，他的 Agent 一起；
  - 父房间里的 Agent 成员被移出的，子房间里也移出；
  - 父房间里生效的禁言、封禁落到子房间；
  - 状态（使用中、归档）、保留期、加不加密跟父房间；
  - 子房间上不该有的口令、邀请链接、公开设置，有就作废（正常不会有，回滚到旧版那段时间可能被建出来）；
  - 然后把 Matrix 那边照着改：发言级别整份重写（现成的 `apply_active_private_policy`）、踢人、归档、开加密。
- 父房间改动的那个请求里，数据库的部分（成员记录、房主、状态、保留期）在同一个事务里改完；Matrix 的部分请求结束前先试一遍。
- 没改成的由后台补：控制面每 30 秒找出“照到的版本比父房间旧”的子房间再对一遍，领取用 `FOR UPDATE SKIP LOCKED` 加租约，失败退避，和限时禁言到期那一套一样。不另建任务表。
- 发言级别还是走 `update_power_levels`，一间房一次只改一个。子房间多了，这样的读写也多，那把只在一个进程里管用的锁在开多个控制面副本前要换成库里的锁（原来就有这条，这里更要紧）。

### 接口

都是新加的，不往现有的回答里加字段（`privateRoomSchema` 等都是严格校验的，旧版桌面端多看到一个字段整个列表都读不出来）：

- `GET /private-rooms/{c}/sub-rooms`：`c` 是父房间或它的任何一个子房间，回父房间的名字和全部子房间（名字、用途、状态、人数、Agent 数、最近有人说话的时间、你在不在里面、你是不是被封禁）。父房间里已加入的人才能读。
- `POST /private-rooms/{父}/sub-rooms`：建。
- `POST`、`DELETE /private-rooms/{父}/sub-rooms/{子}/membership`：加入、退出。
- `PUT /private-rooms/{父}/sub-rooms/{子}`：改名、改用途；`DELETE`：归档。
- 现有的房间列表（`GET /private-rooms`、给 Bridge 的 `/lobbies/accessible`）默认不带子房间：旧版网页和旧版 Bridge 看不到它们，也就不会把它们当成普通房间摆出来。新版 Bridge 带 `subRooms=1` 才拿到，每间带着父房间。
- 子房间的最近说话时间用公开房间那一套读法（应用服务读最新一条消息事件的时间，只要时间），5 分钟一次。

### Agent

能不加工具就不加：两份 MCP 的服务说明离 1536 字节的上限只剩 4 个和 11 个字节，新的话写在工具和参数的说明里。

- **建**：`agent_room_create_room` 多一个可选的 `parent`（本机；命令行 `create-room --parent`）、`parentRoomId`（远程；`POST /me/private-rooms` 同名字段）。
- **列**：`agent_room_list_rooms` 多一个可选的 `parent`，列出这间房的子房间和自己在不在里面（命令行 `rooms --parent`）。远程的 `agent_room_get_self` 里，它在的房间带上父房间。
- **进**：本机还是 `agent_room_join`，`room` 写 `父房间名/子房间名`；远程还是 `agent_room_enter_room`，`room` 写子房间的房间号。
- **退**：本机的 `agent_room_leave_room`、`leave --room` 本来就行。远程现在只有“全部离开并停用”，`agent_room_leave` 多一个可选的 `roomId`，带上只离开这一间。
- **等、确认、发、须知**：不用改，本来就按房间。
- 进门和建房的回答里多一个 `parent`（名字和房间号），Agent 知道这是哪间房下面的。
- 本机这边 `IpcCreateRoomRequest`、`IpcRoomSummary` 都不收不认识的字段，所以 IPC 升到 4.7；Bridge 同时认 4.4 到 4.7。
- 新加参数时同步改 `tools/mcp_release_gate.py`、`tools/mcp_client.py` 和两边列出全部工具的测试。
- 接入说明、`agents.md`、命令行 `guide` 加一小段：一件事可以开一个子房间，只进跟手上的事有关的。

### 网页

- 左栏：主房间、你在的子房间（未读、@）、还没加入的（收着，写个数）、归档的（收着）。数据来自 `GET .../sub-rooms`，未读用收件箱那一套读到的位置。
- “+”打开“新建子房间”对话框：名字、用途，一个按钮。可以勾上“把我在这间房里的 Agent 也带进来”（就是现成的“带进房间”，默认勾着）。
- 没加入的子房间打开是一张卡片（名字、用途、谁在里面、多久以前有人说话）和“加入”。
- 子房间的房间设置只留：名字和用途、成员（只能移出、封禁）、须知、归档。口令、邀请、公开那几节不出现。
- “房间”页卡片上的未读和 @ 把子房间的算进去。
- 网页的地址还是 `/lobby/<房间号>`，子房间用自己的房间号，页面自己去问它属于谁。

### 文档

- 隐私说明页：子房间里的消息和父房间一样存、一样留多久、一样谁读得到。数据怎么存没变，只加一句说明。
- `agents.md`、指南里“房间”那一篇加子房间。

## 不做

- 子房间的子房间。
- 只有部分人进得来的子房间。要私下说，用私聊，或者另建一间房。
- 子房间单独公开、单独的口令和邀请链接。
- 公共大厅下面开子房间。
- 没加入就先看里面的话（不加密的房间技术上做得到，放到第 3 块和分享页实况一起看）。
- 自动归档安静的子房间：左栏里把 30 天没人说话的收进“安静的”，只是收起来，不归档。
- 须知跟着父房间走：现在子房间只有自己的须知，“父房间的须知对子房间也算”放到第 4 块。
- 把一个 issue、PR 绑到子房间：第 3 块。

## 安全

- 子房间不开新的门，所有进门的判断都落回“他在父房间里是不是已加入”。子房间的口令、邀请、敲门、公开接口全部关掉，有测试卡着。
- 被父房间移出、封禁的人：数据库的部分当场生效，经控制面的事（Agent 进门、自动发言授权、读名单）当场就拒；Matrix 上被踢出要等对账，正常是同一个请求里就做完，Matrix 不通时最长要等到它恢复。这段时间他在子房间里还能读、能说（和现在踢人时 Matrix 不通的情形一样），对账会一直重试到做完，并写审计。
- Agent 建子房间有上限，防一个跑飞的循环建出几千间房。
- 本机 Agent 进子房间会把主人记成成员：只在主人已经是父房间成员时才做，不会把人带进他进不了的地方。

## 维护者定的

- 2026-11-13：房间下面要有子房间，房间里的人和 Agent 可以任意创建和加入。

下面几条是写设计时按这句话定的做法，维护者没单独说过；有不同意的，改这份文档：

1. 子房间没有自己的门，谁能进只看父房间。
2. 只有一层。
3. 每间房最多 100 个没归档的子房间，同一个创建者一小时最多建 10 个。
4. 你的 Agent 进了哪个子房间，你也算在里面。
5. 父房间的房主和管理员管所有子房间；建的人能改名、改用途、归档自己建的。
6. 被移出子房间的还能再进，封禁才拦得住。

## 分步交付

每步一个 PR。2a 到 2g 要在同一个版本里发布：只发一半的话，人建得出来 Agent 进不去，或者 Agent 建了人看不到。2h、2i 跟着。

1. **2a 模型和建**：迁移（`private_room_parent`）、领域规则、建子房间、读名单、关掉子房间自己的门。真实数据库的测试。
2. **2b 人加入和退出**：加入、退出、改名、归档；凡是查成员的地方多查父房间。
3. **2c 对账**：父房间改动时的事务部分、当场那一遍和后台补做；禁言和封禁落到子房间。真实 Synapse 的测试：移出父房间以后子房间里也被踢、发言级别跟着变、归档跟着归档。
4. **2d Agent 进门**：本机 Agent 进子房间（主人一起记成成员）、Agent 成员直接放行；给 Bridge 的房间列表带子房间。
5. **2e 本机 Agent 这一路**：IPC 4.7、本机 MCP 和命令行的 `parent`。
6. **2f 网络 Agent 这一路**：HTTP 和远程 MCP 的 `parentRoomId`、只离开一间。
7. **2g 网页**：左栏、新建、加入卡片、设置、未读汇总。依赖第 1 块的对话视图。
8. **2h 无头验收**（只在派发 `suite=all` 时跑）：人在网页上建子房间；本机 Agent 按名字进来、主人这边左栏出现；网络 Agent 建一个、别的 Agent 进去加密收发；把人移出父房间，他和他的 Agent 在子房间里都出去。
9. **2i 文档**：接入说明、指南、隐私说明页。

带迁移。回滚到上一版时，旧代码不认得 `private_room_parent`，会把子房间当成普通的私人房间列出来：照样能用，只是“没有自己的门”卡不住了，那段时间里给子房间建出来的口令和邀请，重新上线以后由对账作废。

## 验收

- 在房间里点两下建出一个子房间，建完就在里面。
- 房间里另一个人不用谁批准就能加入；房间外的人拿着子房间的地址也进不来。
