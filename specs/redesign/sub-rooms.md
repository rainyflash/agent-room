# 子房间（第 2 块）

[重新设计总纲](./design.md)的第 2 块。2026-11-13 维护者说：一个项目一间房可能不够，房间下面要能开子房间，房间里的人和 Agent 可以任意创建和加入。同一天看过第一版设计又定了：子房间默认没有门，但可以选择要有权限才能进；借这个机会把房间的管理员体系补全（[房间的身份和管理员](./room-roles.md)）。看过第二稿他又说：缺了一些功能，比如子房间的分类和归档。

设计稿是 Artifact“房间页重排与子房间”的第 1 张和第 4 到 9 张。房间页左边那一栏在[第 1 块](./room-page.md)里留好了位置。

## 背景

- 一个项目里同时有好几件事：发版、某个 issue、官网改版。现在只能都在一间房里说，或者另建几间互不相干的房间，每间都要重新请人、请 Agent。
- 对 Agent 更要紧：它一直守着房间等消息，房间里说的每件事都可能叫醒它。一件事一个子房间，它只进跟自己手上的事有关的，别的吵不到它。
- 有的事不该所有人都在场：维护者之间商量、处理还没公开的安全问题。公开房间里尤其需要。
- 现在已经有的、能直接用的：
  - 一个 Agent 用同一个身份进好几个房间，一次等所有房间的消息，每个房间各记读到哪（[本机 Agent 跨房间用同一个身份](../agent-identity/design.md)；网络 Agent 也能进好几间）。
  - Agent 能建房间，也能管自己建的房间：放行敲门、请人、移出 Agent（[Agent 自己建房间、管房间](../agent-rooms/design.md)）。
  - 公开房间的三种加入方式（直接进、申请后批准、只能邀请）和申请、批准那一套（[公开房间](../public-rooms/design.md)）。
  - 服务器记着某人“已加入”、Matrix 上他只是受邀时，网页替他加入（`PrivateRoomJoinBoundary`）。
- 现在的房间模型里没有“房间属于另一个房间”这回事：
  - 房间目录只有三种（公共大厅、私人房间、私聊），公开房间也是私人房间加一张公开设置的表。种类和可见范围都有约束卡着，加新值会让回滚读不出来。
  - 每间私人房间必须有一个房主，房主必须是已加入、五项权限全有的成员（提交时才查的约束触发器）。
  - 人进房间只有“先邀请、再自己加入”一条路；Agent 进房间要它的主人已加入、能发言，或者它自己凭口令、敲门进来过。
  - 禁言、踢出、封禁按房间记，一间房里的不管另一间。

## 想要的样子

- 房间页左边一栏：最上面是“主房间”和“浏览子房间”，下面是你在的子房间，按分类分组，带未读和 @。能直接进的前面是 `#`，要批准或者只能请进来的前面是一把锁。
- 点“新建子房间”，起个名字、写一句用途、选个分类，子房间就建好了，你已经在里面。要装门就在这里选。
- “浏览子房间”里是这间房所有的子房间，按分类排着，能搜。没进的在这里加入或者申请。
- 一件事说完了，把它归档：只能看、不能说，从左栏拿掉，在“已归档”里还找得到，能恢复。没人管的，30 天没人说话自己归档。
- 跟你的 Agent 说“开个子房间说发版的事”，它建好、进去，你这边左栏里多出这一项。
- 把人请进房间，他就能进任何没有门的子房间；把人移出房间，他在所有子房间里也一起出去。

## 规则

### 是什么

- 子房间是挂在一间房下面的房间，只有一层：子房间下面不能再开。
- 能有子房间的是私人房间和公开房间。公共大厅和私聊没有。
- 子房间自己是一间完整的房间：有自己的对话、自己的成员、自己的 Agent、自己的须知，Agent 等消息、读到哪都按它单独算。
- **门只对房间里面的人开关。** 不在父房间里的人，子房间有没有门都进不来：子房间没有口令、没有邀请链接、不能单独设成公开。要让一个外面的人进子房间，先请他进父房间。

### 门

子房间默认没有门。建的人、这间子房间的管理员、父房间的房主和管理员随时能装门、拆门、换一种门。界面上这一项叫“谁能进”，三个选项是“直接进”“要批准”“只能请进来”，和公开房间的加入方式是同一套词。

| 门 | 谁能进 | 人怎么进 | Agent 怎么进 |
| --- | --- | --- | --- |
| **没有门**（默认） | 父房间里的人和 Agent | 点“加入”，不用谁批准 | 自己进 |
| **要批准** | 申请了、被批准的 | 点“申请加入”，可以留一句话，子房间的管理员批准 | 主人在里面的，跟着主人进；凭口令或敲门进了父房间的，对子房间敲门、等放行 |
| **只能请进来** | 管理员加进来的 | 不能申请，等管理员把他加进来 | 主人在里面的，跟着主人进；别的由管理员按名字请进来 |

- 父房间的房主和管理员进任何子房间都不用批准。子房间拦不住这间房自己的管理者：一间房里不该有房主看不见的地方。他们进来时，里面的人看得到。
- 有门的子房间还可以勾“不在名单里显示”：只有里面的人、父房间的房主和管理员看得到有这一间。不勾的话，父房间里的人都看得到它的名字、用途和谁在管，只是进不去。
- 装门不会把已经在里面的人请出去；拆门以后谁都能进。
- 申请和公开房间一样：一直等着，没人处理也不作废；同一个人对同一间只有一个在等的申请。
- Agent 敲门照现在的规则：等一小时，一间子房间最多 5 个在等。

### 建

- 父房间里已加入、能发言的人都能建。
- 父房间里的 Agent 都能建：
  - 本机 Agent 替它的主人建，主人要在父房间里能发言；
  - 网络 Agent 自己建，它要是凭口令或敲门进了父房间的，或者父房间就是它建的。
- 父房间的房主可以把“谁能建子房间”收紧成只有管理员，也可以关掉“Agent 能建”（见[房间的身份和管理员](./room-roles.md)）。默认都开着。
- 建的时候填名字（同一间房里没归档的子房间不重名，不分大小写）、一句用途（可以不填）、放进哪个分类（可以不选）、要不要门。
- 建的人是这间子房间的管理员。Agent 建的：本机 Agent 的主人是管理员，Agent 照主人的名义管；网络 Agent 自己是管理员。
- 建好以后建的人已经在里面；Agent 建的，它自己在里面，它的主人也在里面。
- 上限是防失控用的，不是为了管人：每间房最多 100 个没归档的子房间；同一个人或 Agent 一小时最多建 10 个。子房间不占账户的公开房间名额，也不占网络 Agent 的建房名额。

### 加入和退出

- **没有门的**：
  - 父房间里已加入的人，点一下就加入。
  - 本机 Agent 按名字进（`父房间名/子房间名`），它的主人要在父房间里能发言。**它进去的时候，主人也记成这个子房间的成员**：你的 Agent 在哪间子房间，你就在哪间，左栏里看得到，也对它在里面说的话负责。
  - 网络 Agent 拿子房间的房间号进，不用等人放行，只要它在父房间里。
- **有门的**：
  - 人照上面“门”那张表：申请，或者等管理员加进来。被加进来的人直接就在里面，不用再点接受（他本来就是这间房里的人，不想待可以退出）。
  - 本机 Agent 只在主人已经是这间子房间的成员时才进得去；主人不在里面时不会替主人加入，它拿到的回答里写明“这间要主人先申请”。
  - 凭口令或敲门进了父房间的 Agent（网络 Agent 等）对子房间敲门，管理员放行。
- 退出随时可以。人退出时他的 Agent 跟着退出（和现在的房间一样）。
- 被移出某个子房间的人：没有门的还能再进；有门的要重新申请或者重新被请进来。要彻底不让他进，封禁他（在这个子房间里，或者在父房间里）。

### 权限和管理

身份和各自能做什么写在[房间的身份和管理员](./room-roles.md)，这里只说和子房间有关的：

- 一个人在子房间里能不能看、能不能说、他的 Agent 能不能说，照他在父房间里的权限，不单独设。在父房间里被改了，子房间里跟着变。
- 父房间的房主也是每个子房间的房主；父房间转让了，子房间一起转。
- 父房间的管理员进了哪个子房间，在那里也是管理员。
- **子房间管理员**只管这一间：批准申请、把人和 Agent 请进来、移出、封禁、改名、改用途、改须知、装门拆门、归档。建的人自动是；房主、父房间的管理员、这间的管理员可以再设别人。
- 子房间管理员可以把这间子房间交给自己的 Agent 管（现成的“把管房间交给自己的 Agent”，一间房一份授权）。
- 父房间里的禁言、踢出、封禁，在所有子房间里一起算；到期解除、撤回也一样。
- 子房间可以单独归档、恢复，见下面“归档和恢复”。

### 加密和谁读得到

- 没装过门的子房间跟父房间一样：父房间加密，它就加密；父房间是公开的、不加密，它也不加密。
- **有门的子房间一律加密。** 装门的那一刻，不加密的子房间会开加密（和公开房间改回私密一样，开了关不掉）。
- 有门的子房间以后拆了门，加密还在。这时照“私密房间改成公开”的规则办：拆门以后才进来的人，不给他们补发以前的房间钥匙，他们看不到拆门以前的话。
- 父房间以后改了（公开改回私密会开加密），没装过门的子房间跟着改。
- 父房间是网络 Agent 建的，服务器读得到全部消息，子房间也一样，界面上照父房间那样写明。有门的子房间里要是进了网络 Agent，服务器读得到发给它的消息（和私人房间一样）。
- 后进子房间的人，不加密的看得到以前的消息；加密的只看得到自己进来以后的，别人的设备和 Agent 会照现在“找回加入前的消息”的规则补发（网络 Agent 照旧不补）。
- 保留期跟父房间。

### 分类

- 分类是给子房间分的组，只有名字和先后。一间子房间最多在一个分类里，没分的在“未分类”。
- 分类是整间房共用的：每个人看到的分法一样，不是各人自己的。
- 房主和管理员建分类、改名、排先后、删。一间房最多 20 个分类，名字不重名（不分大小写）。
- 建子房间时从已有的分类里选一个，不选就是“未分类”。之后这一间的管理员、父房间的房主和管理员能把它挪到别的分类。
- 删掉一个分类，里面的子房间回到“未分类”，不归档、不删。
- 分类只管怎么摆，不管权限：不能给整个分类装门。
- 一个分类里的子房间按建的先后排。
- 隐藏的子房间照样有分类；看不到它的人，分类的个数里也不算它。

### 归档和恢复

现在归档一间房只有房主能做，归档了不能恢复。子房间不一样：一件事一个子房间，事情做完就该收起来，收错了要拿得回来。

- **谁能归档**：这一间的子房间管理员、父房间的房主和管理员。
- **归档以后**：
  - 只能看、不能说（和归档的房间一样），也不能再加入；
  - 从左栏拿掉，在“浏览子房间”的“已归档”里；
  - 成员、门、分类、管理员都原样留着；在等的申请和敲门作废；
  - 不占 100 个的名额，名字也让出来（恢复时撞了名字要先改名）；
  - 未读清掉；Agent 等消息时不再看它，列房间时默认不列它。
- **谁看得到归档的**：归档以前看得到它的人，在“已归档”里都看得到这一行。原来在里面的人能打开看以前的话；没进过的要看，请能恢复的人先恢复。
- **恢复**：能归档的人都能恢复。恢复以后回到原来的分类（分类没了就回“未分类”），原来的人和 Agent 都还在，接着说。没归档的已经满 100 个时恢复不了，说明原因。
- **自动归档**：30 天里人和 Agent 都没说过话的子房间自动归档，记成“30 天没人说话，自动归档”。
  - 房主能在房间设置里关掉，默认开。
  - 自动归档的没有谁决定过要关它，所以原来在里面的人谁都能恢复。
  - 建好不到 30 天的不算。
- 父房间归档，子房间一起归档。父房间照旧不能恢复，所以它们也回不来。
- 没有“删除子房间”：归档就是结束。里面的消息照父房间的保留期到期。

### 每个人自己的

- **免打扰**：这间子房间没读的不算进“房间”页的卡片，也不提醒；提到你的照样算。只对你自己起作用，换一台设备还在。
- **标为已读**。
- 分类收没收起来，记在这台设备上。

### 看得到什么

- 左栏只放你在的子房间。别的在“浏览子房间”里：父房间里已加入的人都看得到名单，每间有名字、用途、分类、哪种门；没有门的再给里面有几个人、几个 Agent。没进去的看不到里面的话。
- 有门的子房间对没进去的人只给：名字、用途、分类、哪种门、谁在管。里面有谁、多久以前有人说话不给。勾了“不在名单里显示”的整个不给。
- 有你没见过的新子房间时，“浏览子房间”那一行带一个点（见没见过记在这台设备上）。
- “房间”页的卡片只有父房间一张，未读和 @ 把你在的子房间的也算进去（免打扰的不算没读的）。
- 发现页和分享页不单独列子房间。分享子房间的链接就是父房间的链接。
- 不登录的围观只看主房间。

## 做法

### 模型

- 子房间在房间目录里就是一间私人房间（`kind = 'private_room'`），不加新的种类。另加三张表，做法和公开设置那张表一样：

  `private_room_parent`：`catalog_entry_id`（子房间，主键）、`parent_catalog_entry_id`、`access`（`open`、`request`、`invite_only`，和公开设置的加入方式用同样的三个词）、`hidden`（只有 `access` 不是 `open` 时能为真）、`door_opened_at`（有门的拆门的时间，可空）、`created_by_principal_id`、`created_by_agent_id`（可空）、`parent_version_applied`、`created_at`；分类和归档用的 `category_id`（可空，分类删掉时置空）、`last_message_at`、`archived_at`、`archived_by_principal_id`（都可空）、`archived_reason`（`manual`、`inactive`、`parent`，可空）。约束：父房间自己不能在这张表里当子房间（只有一层）。

  `private_room_sub_room_manager`：`catalog_entry_id`、`principal_id`、`granted_by_principal_id`、`granted_at`。子房间管理员。

  `private_room_sub_room_category`：`id`、`parent_catalog_entry_id`、`name`、`name_key`（小写，和父房间一起唯一）、`position`、`created_by_principal_id`、`created_at`、`updated_at`。

- 因为它就是一间私人房间，现成的都能用：建 Matrix 房间、成员表、Agent 的位置、发言级别、须知、归档、网页的加入、Agent 进门、等消息、读到哪、把管房间交给 Agent。
- 约束触发器要求房主已加入、权限全有：子房间的房主记成父房间的房主，建的时候就给他一条已加入的成员记录。他在 Matrix 上只是受邀，打开时由网页替他加入。父房间的房主是网络 Agent 时照旧不邀请。
- 有门的子房间照用现成的两张表：人的申请（`private_room_join_request`）和 Agent 的敲门（`private_room_agent_knock`）。
- 归没归档还是记在房间自己的状态上（和现在归档一间房一样），`archived_*` 三列只记谁、什么时候、为什么。领域层给子房间单开归档和恢复，认子房间管理员和父房间的房主、管理员；现在的 `archive` 只认房主、没有恢复，不动它。恢复时 Matrix 那边把发言级别整份重写回来（现成的 `apply_active_private_policy`）。
- 谁能建、Agent 能不能建、自动归档开没开，记在 `private_room_sub_room_policy`（见[房间的身份和管理员](./room-roles.md)）。
- 子房间的公开设置、口令、邀请链接这三张表不写；对应的接口对子房间一律回 409 `sub_room.parent_only`。
- 父子关系只记在控制面，不用 Matrix 的 Space，也不往房间状态里写。拆门那一刻写一条现成的 `room.listing.v1`（“这一刻以后进来的人不补发钥匙”就看它），别的不往房间状态里加。

### 进门

- **人加入没有门的**：`POST /private-rooms/{父}/sub-rooms/{子}/membership`。查他在父房间里已加入、在子房间里没被封禁，然后直接记成已加入，以房主的名义在 Matrix 上邀请他、设好发言级别。网页接着照“服务器记着已加入、Matrix 上是受邀”那一套替他加入。不走“受邀 → 接受”两步：加入是他自己点的。
- **人申请要批准的**：`POST .../join-requests`（可以留一句话）；子房间管理员、父房间的房主和管理员 `GET` 看在等的、`PUT .../join-requests/{账户}` 批准或拒绝。批准以后和上一条一样直接记成已加入。
- **管理员把人请进来**：`PUT .../members/{账户}`。他要是父房间里已加入的人。直接记成已加入。哪种门都能用，没有门的也能。
- **父房间的房主和管理员**：走第一条，不看门。
- **本机 Agent 进**：进门的规则（`admits_agent_of`）不变，还是要主人在这间房里已加入、能发言。没有门的子房间里主人还不在时，先照第一条把主人加进去，再让 Agent 进；有门的不替主人加，回 403 `sub_room.owner_not_inside`。
- **Agent 成员进**（网络 Agent、凭口令或敲门进了父房间的本机 Agent）：对子房间敲门。没有门的，它在父房间里是已加入的 Agent 成员就直接放行；要批准的照现成的敲门等放行；只能请进来的不收敲门，由管理员按名字放行（现成的放行入口，不要求先有敲门记录）。
- 控制面里凡是按“这间房里他是不是成员”判断的地方（进门、自动发言授权、读名单），子房间多查一条：他在父房间里还是已加入。这样对账还没跑到时，经控制面的事也不会放错。

### 对账

父房间里一变，子房间要跟着变。不一条条转发动作，而是按版本对账：

- 父房间每次改动本来就会加版本号（`private_room_state.version`）。子房间记着自己照到了父房间的哪个版本（`parent_version_applied`）。
- 对账做的事是照父房间现在的样子重算一遍子房间，做几遍结果都一样：
  - 房主换成父房间的房主；
  - 每个成员的权限重算：查看、发言、自动发言照他在父房间里的；“管理”给父房间的房主、进来了的父房间管理员、这间的子房间管理员；“邀请”一律没有（子房间不能往外请人）；
  - 在父房间里已经不是已加入的，从子房间移出，他的 Agent 一起，子房间管理员的记录一起删；
  - 父房间里的 Agent 成员被移出的，子房间里也移出；
  - 父房间里生效的禁言、封禁落到子房间；
  - 保留期跟父房间；没装过门的，加不加密跟父房间；
  - 父房间归档了，没归档的子房间都归档（原因记 `parent`）；父房间没归档时，子房间归没归档是它自己的事，对账不碰；
  - 子房间上不该有的口令、邀请链接、公开设置，有就作废（正常不会有，回滚到旧版那段时间可能被建出来）；
  - 然后把 Matrix 那边照着改：发言级别整份重写（现成的 `apply_active_private_policy`）、踢人、归档、开加密。
- 父房间改动的那个请求里，数据库的部分（成员记录、房主、状态、保留期）在同一个事务里改完；Matrix 的部分请求结束前先试一遍。
- 没改成的由后台补：控制面每 30 秒找出“照到的版本比父房间旧”的子房间再对一遍，领取用 `FOR UPDATE SKIP LOCKED` 加租约，失败退避，和限时禁言到期那一套一样。不另建任务表。
- 子房间自己的改动（装门拆门、设管理员、有人进出）不用等对账，当场改完。
- 发言级别还是走 `update_power_levels`，一间房一次只改一个。子房间多了，这样的读写也多，那把只在一个进程里管用的锁在开多个控制面副本前要换成库里的锁（原来就有这条，这里更要紧）。

### 接口

都是新加的，不往现有的回答里加字段（`privateRoomSchema` 等都是严格校验的，旧版桌面端多看到一个字段整个列表都读不出来）：

- `GET /private-rooms/{c}/sub-rooms`：`c` 是父房间或它的任何一个子房间，回父房间的名字、分类的名单和你看得到的子房间。每间：名字、用途、分类、哪种门、谁在管、你在不在里面、你有没有在等的申请、你是不是被封禁；没有门的或者你在里面的，再给人数、Agent 数、最近有人说话的时间。带 `archived=1` 回已归档的：名字、原来的分类、谁在什么时候为什么归档的、你原来在不在里面。父房间里已加入的人才能读。
- `POST /private-rooms/{父}/sub-rooms`：建（名字、用途、分类、门、要不要隐藏）。
- `PUT /private-rooms/{父}/sub-rooms/{子}`：改名、改用途、换分类、换门、隐藏；`DELETE`：归档；`POST .../sub-rooms/{子}/restore`：恢复。
- `POST`、`DELETE .../sub-rooms/{子}/membership`：加入、退出。
- `POST`、`DELETE .../sub-rooms/{子}/join-requests`：申请、撤回；`GET`、`PUT .../join-requests/{账户}`：看、批准或拒绝。
- `PUT`、`DELETE .../sub-rooms/{子}/members/{账户}`：请进来、移出。
- `PUT`、`DELETE .../sub-rooms/{子}/managers/{账户}`：设、撤子房间管理员。
- `POST /private-rooms/{父}/sub-room-categories`，`PUT`、`DELETE .../sub-room-categories/{分类}`：建分类，改名和排先后，删。
- `GET`、`PUT /private-rooms/{父}/sub-room-policy`：谁能建、Agent 能不能建、自动归档开没开。只有房主能改。
- Agent 的敲门、放行用现成的 Agent 进门接口，只是子房间不给口令。
- 现有的房间列表（`GET /private-rooms`、给 Bridge 的 `/lobbies/accessible`）默认不带子房间：旧版网页和旧版 Bridge 看不到它们，也就不会把它们当成普通房间摆出来。新版 Bridge 带 `subRooms=1` 才拿到，每间带着父房间、分类和哪种门；归档的不给。
- 子房间的最近说话时间用公开房间那一套读法（应用服务读最新一条消息事件的时间，只要时间，`public_room_activity.rs`），5 分钟一次，记进 `last_message_at`。
- 自动归档每小时一轮：找出开着自动归档的房间里 `last_message_at` 超过 30 天（没说过话的按建的时间算）的子房间，归档前再向聊天服务器问一次最新一条的时间，确实超过了才归档，原因记 `inactive`，写审计。领取照对账那一套（`FOR UPDATE SKIP LOCKED` 加租约）。
- 免打扰不经控制面：网页把它记在聊天账户里这间房的账户数据上（新的一种，旧版客户端不认识也没事）。第 4 块做邮件提醒时再把它带给服务器。

### Agent

能不加工具就不加：两份 MCP 的服务说明离 1536 字节的上限只剩 4 个和 11 个字节，新的话写在工具和参数的说明里。

- **建**：`agent_room_create_room` 多三个可选的参数：`parent`（本机；命令行 `create-room --parent`）或 `parentRoomId`（远程；`POST /me/private-rooms` 同名字段），`access`（`open`、`request`、`invite_only`，不写是 `open`），和 `category`（分类的名字；没有这个分类就放进“未分类”，回答里说明，不替它新建分类）。
- **列**：`agent_room_list_rooms` 多一个可选的 `parent`，列出这间房里它看得到的子房间、分类、哪种门、自己在不在里面（命令行 `rooms --parent`）；归档的默认不列，带 `archived` 才列。远程的 `agent_room_get_self` 里，它在的房间带上父房间。
- **进**：本机还是 `agent_room_join`，`room` 写 `父房间名/子房间名`；远程还是 `agent_room_enter_room`，`room` 写子房间的房间号。有门、进不去时，回答里写明是要主人先申请，还是已经替它敲了门在等放行。
- **管**：Agent 建的有门的子房间，它用现成的那几个工具管：`agent_room_room_access` 看在等的、`agent_room_answer_knock` 放行或不让进、`agent_room_invite_person` 把父房间里的人请进来（子房间里它只能请父房间里的人）、`agent_room_remove_agent` 移出 Agent。人的申请它在 `agent_room_room_access` 里也看得到，用 `agent_room_invite_person` 把这个人请进来就是批准；拒绝留给人做。
- **归档**：网络 Agent 建的子房间，它是这一间的管理员，用现成的 `agent_room_close_room` 归档（这个工具现在只认它自己当房主的房间，放宽到它管的子房间）。本机 Agent 没有归档的工具（它建的子房间是它主人在管），由主人在网页上归档，或者等自动归档。恢复只给人做。往归档的子房间里说话，回答和现在往归档的房间里说话一样（`room_archived`）。
- **退**：本机的 `agent_room_leave_room`、`leave --room` 本来就行。远程现在只有“全部离开并停用”，`agent_room_leave` 多一个可选的 `roomId`，带上只离开这一间。
- **等、确认、发、须知**：不用改，本来就按房间。
- 进门和建房的回答里多一个 `parent`（名字和房间号），Agent 知道这是哪间房下面的。
- 本机这边 `IpcCreateRoomRequest`、`IpcRoomSummary` 都不收不认识的字段，所以 IPC 升到 4.7；Bridge 同时认 4.4 到 4.7。
- 新加参数时同步改 `tools/mcp_release_gate.py`、`tools/mcp_client.py` 和两边列出全部工具的测试。
- 接入说明、`agents.md`、命令行 `guide` 加一小段：一件事可以开一个子房间，只进跟手上的事有关的；有门的别硬闯，照回答里说的等；事情做完了跟主人说一声可以归档。

### 网页

样子见[第 1 块](./room-page.md)的“风格”。

  - 一个分类里你一间都不在，这个分类不出现。
  - “新建子房间”。再下面是私聊。

- **“浏览子房间”一页**（父房间的地址带 `view=sub-rooms`）：
  - 搜名字和用途；三个标签：全部、我在的、已归档。
  - 按分类分组。每行是名字、用途、几个人几个 Agent（有门没进的写哪种门）、一个动作：已加入、加入、申请加入、等批准中、只能请进来。

- “房间”页卡片上的未读和 @ 把子房间的算进去。
- 网页的地址还是 `/lobby/<房间号>`，子房间用自己的房间号，页面自己去问它属于谁。

## 不做

- 子房间的子房间。
- 子房间单独公开、单独的口令和邀请链接；不在父房间里的人进子房间。
- 连父房间的房主和管理员都看不见、进不去的子房间。要那样，另建一间房。
- 公共大厅下面开子房间。
- 没加入就先看里面的话（不加密的房间技术上做得到，放到第 3 块和分享页实况一起看）。
- 给整个分类装门、按分类给权限。
- 每个人自己的分类、自己的排法；手动排一个分类里子房间的先后。
- 删除子房间。
- 恢复整间归档的房间（照旧不能）。
- 从一句话直接开一个子房间（“这句话单开一间说”）：有用，放到这一块做完以后。
- 须知跟着父房间走：现在子房间只有自己的须知，“父房间的须知对子房间也算”放到第 4 块。
- 把一个 issue、PR 绑到子房间：第 3 块。

## 安全

- 门只在父房间里面起作用，所有进门的判断都先落回“他在父房间里是不是已加入”。子房间的口令、邀请链接、公开接口全部关掉，有测试卡着。
- 有门的子房间是加密的；装门的那一刻开加密，这一步在换门的同一个请求里做完才算换成，开不成就不换。
- 隐藏的子房间：名单接口对看不到的人不回这一行，也不在人数、未读里露出来；按房间号直接打开，回的和不存在的房间一样（404）。
- 被父房间移出、封禁的人：数据库的部分当场生效，经控制面的事（Agent 进门、自动发言授权、读名单）当场就拒；Matrix 上被踢出要等对账，正常是同一个请求里就做完，Matrix 不通时最长要等到它恢复。这段时间他在子房间里还能读、能说（和现在踢人时 Matrix 不通的情形一样），对账会一直重试到做完，并写审计。
- 父房间的房主和管理员进有门的子房间不用批准，但进来这件事里面的人看得到（成员变动照常显示），加密的子房间里他们也只看得到自己进来以后的话。
- Agent 建子房间有上限，防一个跑飞的循环建出几千间房。
- 归档、恢复、建和删分类都写审计。自动归档动手前向聊天服务器再确认一次，免得照一个过时的时间把正在说话的子房间关掉。
- 分类的名字是用户写的字，显示时一律当文字处理；名单里分类的个数只数你看得到的子房间，隐藏的不从这里露出来。
- 归档的有门的子房间，“已归档”里也只给归档以前看得到它的人。
- 本机 Agent 进没有门的子房间会把主人记成成员：只在主人已经是父房间成员时才做；有门的不替主人加入。

## 分步交付

每步一个 PR。[房间的身份和管理员](./room-roles.md)的第 1 步（收紧管理员的规则）先做，它不依赖子房间。

2a 到 2i 要在同一个版本里发布：只发一半的话，人建得出来 Agent 进不去，或者 Agent 建了人看不到。后面三步跟着。

1. **2a 模型和建**：迁移（三张表）、领域规则、建子房间、读名单、关掉子房间的口令、邀请链接和公开。真实数据库的测试。
2. **2b 人加入和退出**（没有门的）：加入、退出、改名；凡是查成员的地方多查父房间。
3. **2c 对账**：父房间改动时的事务部分、当场那一遍和后台补做；禁言和封禁落到子房间。真实 Synapse 的测试：移出父房间以后子房间里也被踢、发言级别跟着变、父房间归档跟着归档。
4. **2d 门**：三种门、隐藏、申请和批准、请进来、子房间管理员；装门开加密、拆门写 `room.listing.v1`。真实 Synapse 的测试：没批准的进不来、看不到；装门以后新消息是加密的。
5. **2e 分类、归档和恢复**：分类的接口；子房间的归档和恢复；“已归档”的名单。真实 Synapse 的测试：归档以后发不了言，恢复以后原来的人接着说。
6. **2f Agent 进门**：本机 Agent 进子房间（没有门的把主人一起记成成员）、Agent 成员直接放行或敲门；给 Bridge 的房间列表带子房间。
7. **2g 本机 Agent 这一路**：IPC 4.7、本机 MCP 和命令行的 `parent`、`access`、`category`。
8. **2h 网络 Agent 这一路**：HTTP 和远程 MCP 的 `parentRoomId`、`access`、`category`、只离开一间、归档自己管的子房间。
9. **2i 网页**：左栏、浏览子房间、新建、申请的卡片、子房间设置、房间设置的“子房间”一节、免打扰、未读汇总。依赖第 1 块的对话视图。
10. **2j 自动归档**：记最近说话的时间、每小时一轮、房间设置里的开关。可以晚一版。
11. **2k 无头验收**（只在派发 `suite=all` 时跑）：人在网页上建子房间、放进分类；本机 Agent 按名字进来、主人这边左栏出现；网络 Agent 建一个要批准的、别的 Agent 敲门、它放行以后加密收发；人申请、管理员批准；归档以后说不了话、恢复以后接着说；把人移出父房间，他和他的 Agent 在子房间里都出去。
12. **2l 文档**：接入说明、指南、隐私说明页。

带迁移。回滚到上一版时，旧代码不认得这三张表，会把子房间当成普通的私人房间列出来：照样能用，门还在（Matrix 上本来就是邀请制，旧代码不会替人加入），只是“不能有口令和邀请链接”卡不住了，那段时间里给子房间建出来的，重新上线以后由对账作废。

## 验收

- 在房间里点两下建出一个子房间，建完就在里面。
- 没有门的：房间里另一个人不用谁批准就能加入；房间外的人拿着子房间的地址也进不来。
- 要批准的：没批准的人看得到名字和用途、看不到里面的话；批准以后不用再点就在里面，他的 Agent 跟着进得来。
- 只能请进来的：没有申请按钮；管理员加进来的人直接在里面。
- 隐藏的：不在里面的普通成员在左栏里看不到它，拿房间号打开和打开不存在的房间一样。
- 装门以后新说的话是加密的；拆门以后进来的人看不到拆门以前的话。
- Agent 自己建子房间、进子房间，主人的左栏里看得到；它在一个子房间里等消息时，别的子房间里的话不叫醒它。
- 把人移出父房间，他和他的 Agent 从所有子房间里消失。
- 父房间归档，子房间都归档。
- 建两个分类，把子房间分进去：房间里每个人的左栏都按这两个分类分组；删掉一个分类，里面的回到“未分类”。
- 子房间管理员归档自己那间：左栏里没了，“已归档”里看得到、打得开、说不了话；恢复以后原来的人接着说。
- 30 天没人说话的子房间自己归档，原来在里面的人能恢复；关掉房间设置里的开关以后不再自动归档。
- 给一间子房间开免打扰：“房间”页卡片上不算它没读的，提到你的照样算。
- 旧版桌面端打开应用，房间列表和以前一样，没有多出来的房间，也不报错。
