# 带时限的禁言到期自动撤销：设计

2026-10-09 做 #348（新开的公开大厅分片补上生效的禁言和封禁）时发现：带时限的禁言到期以后没有人去撤。记录上按到期时间算它已经不生效了，Matrix 里这个人却一直禁着，直到有人手动撤销；#348 按到期时间补新分片，于是同一个人在旧分片里说不了话，被分到新分片却能说。本文写清现状、怎么撤、记录怎么标、并发、租约、重试和分步交付。实现以本文为准，做完一步回来更新“状态”一节。

## 现状

2026-10-09 读代码确认：

- 网页治理表单（`moderation-action-form.tsx`）只有禁言能选时长：1 小时、24 小时、7 天，或者“直到撤回”。选了时长就带 `expiresAtUnixMs`，控制面收下，应用层存进 `moderation_action.expires_at`。接口本身不看动作，带到期时间的封禁、踢出、隐藏也收，只是网页不发。
- 落下禁言时，Matrix 上把这个人压到发言门槛以下：公开大厅在每个活跃分片上只压这个人（`set_public_speaker`），私人房间用成员发言权那一套（`set_speaking`）。
- 没有任何地方处理到期：
  - 控制面没有后台任务去找到期的禁言；
  - 读治理列表照样是“已生效”，网页还给“撤回”按钮，列表上也看不到什么时候到期；
  - 撤销接口不看到期时间；
  - 进房间、分配分片时不看治理记录。#348（还没合并）建新分片时只补没到期的禁言，到期的不补。
- 只有记录上算“已经不生效”：`ModerationAction::is_effective_at` 按到期时间算，只有 #348 用它。
- 手动撤销一条已经过期的禁言走得通：撤销不看到期时间，`ModerationAction::reverse` 只要求这条已经落下、撤销时间不早于开始时间；管人的动作在每个活跃分片上撤，记成 `reversed`，写 `moderation.action.reversed` 审计。但撤销有几个原来就有的毛病，自动到期会把它们放大：
  - **同一个人有两条生效的禁言**（比如先禁 1 小时，后来又禁到撤回）：撤其中一条，Matrix 上就解了，另一条还记着生效。自动到期以后就成了“1 小时一到人就放出来”。
  - **私人房间撤销禁言一律把发言权还给他**，不看他此刻在房间设置里有没有发言权。禁言期间管理者又关掉了他的发言权，到期一撤他又能说了。
  - **两个人同时撤同一条**：后到的那个回 409，因为两边记的撤销时间对不上。后台和手动撤销撞上时就是这样。
  - **人或房间没了**：被禁言的人删了账户、或者房间已经停用时，撤销回 404，这条记录永远是“已生效”。

## 做法

### 谁来撤

- 控制面里一个后台任务，和账户删除那个一样：跟 HTTP 服务一起启动、一起关，一轮做完才开始下一轮。每 15 秒一轮，每轮最多做 20 条。
- 只领禁言：`status = 'applied'`、`action_type = 'mute'`、`expires_at` 已过，而且没有别的实例在做、不在退避里（见“多个控制面实例”“Matrix 撤不掉时”）。先到期的先做。
- 用例放在应用层（`ModerationExpiryWorker`），控制面只负责定时调它、按结果记日志。

### 撤之前先看这个人此刻该不该禁着

不只看到期的这一条，而是看这个人在这个房间的全部禁言记录，加上房间此刻的活跃分片、他的 Matrix 账号，私人房间里再看他此刻有没有发言权（在房间里、房间设置里开着发言权）。认人按 UUID：落治理时目标是解析成 UUID 才放行的，同一个人的两条禁言写法可能不一样（大写、不带横线），不能拿文本比（和 #348 同一个坑）。

| 这个人此刻的情况 | 后台怎么做 |
| --- | --- |
| 有一条禁言正在落（`pending`，开始不到 5 分钟） | 先不动，15 秒后再看 |
| 房间没了（目录停用、没有活跃分片），或者人没了（账户停用、没有 Matrix 账号） | 不动 Matrix，直接记成到期 |
| 还有别的生效的禁言 | 在每个活跃分片上把那一条再落一次（已经禁着的不写），记成到期 |
| 私人房间里他此刻没有发言权 | 不动 Matrix，记成到期 |
| 都不是 | 在每个活跃分片上撤（`ModerationEffectGateway::reverse`），记成到期 |

- 开始超过 5 分钟还是 `pending` 的，是没落完控制面就断了的（中途重启），当它没有。正常落一条禁言是每个分片读一次、写一次权限，几秒钟。
- “再落一次那一条”是为了把之前可能被误解的改回来：比如那条生效的禁言落下的同一刻，有人在撤另一条。落禁言本来就能重放，已经禁着的分片什么也不写。

### 动完再看一眼

动完 Matrix 再读一遍上面的情况。要是判断变了（期间有人又禁了他、那条生效的被撤了），或者活跃分片变了（期间新开了分片），这次就不记，15 秒后从头再来；一样才记成到期。

这样“刚解禁，管理员又禁了他”不会被我们的解禁盖掉。他那条禁言先记成 `pending`，再去动 Matrix：

- 记 `pending` 在我们第二次读之前：我们看得到，这次不记，下一轮确保禁着；
- 在第二次读之后：他动 Matrix 也在我们解禁之后，最后是禁着的。

两种结果都对。反过来，我们确保禁着的同一刻有人撤了那条生效的禁言，第二次读也看得到，下一轮再解。

### 记录和审计

- **不加新状态，沿用 `reversed`。** 网页（桌面端里也是这份网页）对治理动作严格校验：`status` 只认四种，对象是 `.strict()`。旧版桌面端见到新状态或新字段，整张治理列表都读不出来。回滚到旧版控制面时，旧代码读到不认识的状态当成坏数据，这个房间的治理列表也会报错。所以接口的形状一点不改。
- **`reversed_at` 记真正记成到期的那一刻**，不早于 `expires_at`。到期的和手动撤回的靠时间区分：`reversed_at >= expires_at` 的就是到期的。到期以后才手动撤回的也算到期，它本来就到期了。不加“原因”列。
- **审计**：成功写 `moderation.action.expired`（allowed）。Matrix 撤不掉写 `moderation.action.expire_failed`（failed），同一条连着失败只写第一次，之后只记日志。
- 审计的操作者照旧记成下这条禁言的人，和这条动作的其他审计（`requested`、`applied`、`reversed`）一样，靠动作码看出是到期。审计表的操作者类别虽然允许 `service`，但读审计的代码只认 `principal`：写了别的，现在的和旧版的控制面都读不出整张审计。

### 只有禁言能带到期时间

- 落治理时，别的动作带了到期时间就回 400 `moderation.invalid_request`。网页本来就只给禁言发；封禁、隐藏要不要限时，以后要做再单独定。
- 只在新落的动作上查。数据库里已有的旧记录照读不误，不会因为这条规则变成坏数据。生产上不大可能有带到期时间的非禁言动作（只有绕过网页直接调接口才会有）；有的话后台不碰它们。要确认得只读查一次生产，先问维护者。

### 手动撤销也用同一套判断

撤的是禁言时，和后台一样先看这个人此刻该不该禁着、动完再看一眼，区别只在定不下来的时候：

- 有一条禁言正在落：什么也不动，回 409 `moderation.conflict`，管理员过一会儿再点。
- 动完再看一眼变了：照新的情况再动一次（正在落的那条当它会生效，确保禁着），然后照常记成撤回。手动撤销不能叫管理员等 15 秒。

结果是：还有别的生效的禁言时不再误解禁；私人房间看他此刻的发言权；和后台同时撤同一条时，后到的直接回已经撤了的那条，不报 409（见下一节）。封禁、踢出、隐藏的撤销不变。

### 多个控制面实例

生产的控制面可以开好几个副本（`AGENT_ROOM_CONTROL_PLANE_REPLICAS`）。

- **领取**：`FOR UPDATE SKIP LOCKED` 选一条，同一条语句把“下次能领的时间”设成 2 分钟以后，这就是租约。处理完（记成到期，或者排好下次）改掉它。进程中途死了，2 分钟后别的实例接着做。Matrix 上的动作都能重放，重做一遍没关系。
- **排下次**：领的时候次数加一。排下次只在次数还是自己领时的那个数时才写，别的实例接手以后不覆盖它的。
- **记成到期**：只有 `applied` 能改成 `reversed`，谁先改谁算。后到的看到已经 `reversed` 就当做完了，不再写审计。这一条对手动撤销一样：以前两边撤销时间对不上就回 409，现在 `reversed` 再撤一次直接回已经撤了的那条。

### Matrix 撤不掉时

- 有一个分片动不了就停下，已经动了的不回滚（撤和落都能重放）。
- 这条留在 `applied`，下次能领的时间按退避往后推：30 秒起，每次翻倍，最长 15 分钟。一直试到成功，或者房间、人没了。
- 失败码（和落治理失败同一套 `matrix.*`）记在新列里，给排查用，接口不返回。控制面每次失败记一条警告，带动作 ID 和失败码。
- 不设“试了多少次就放弃”：放弃了这个人就一直禁着，比一直重试更糟。

### 网页

- 治理记录里，禁言写出到什么时候（“到 10 月 10 日 14:00”）；不限时的写“直到撤回”。
- 过了到期时间的显示“已到期”，不再给“撤回”：后台 15 秒内会解除；Matrix 撤不掉的时候，手动撤回也一样撤不掉。
- 手动撤回的照旧“已撤回”。
- 接口不变，网页用已有的 `expiresAtUnixMs`、`reversedAtUnixMs` 判断。中英文一起改。

### 数据库

一个新迁移，只加列和索引：

```sql
ALTER TABLE agent_room.moderation_action
    ADD COLUMN expiry_attempts integer NOT NULL DEFAULT 0,
    ADD COLUMN expiry_next_attempt_at timestamptz,
    ADD COLUMN expiry_failure_code text,
    ADD CONSTRAINT moderation_action_expiry_attempts CHECK (expiry_attempts >= 0),
    ADD CONSTRAINT moderation_action_expiry_failure_code_length CHECK (
        expiry_failure_code IS NULL OR length(expiry_failure_code) BETWEEN 1 AND 128
    );

CREATE INDEX moderation_action_expiry_due_idx
    ON agent_room.moderation_action (expires_at)
    WHERE status = 'applied' AND expires_at IS NOT NULL;
```

- `expiry_next_attempt_at` 一列管两件事：在做的时候是租约到期的时间，失败以后是下次重试的时间。空着就是到期马上能领。
- 旧版控制面不读也不写这几列：迁移可以在切换服务器之前跑，回滚到旧版照常读写治理记录。已经撤了的记录上留着这几列的旧值，没关系，领取只看 `applied` 的。
- 不建新表。读一个人的禁言是按房间读出这个房间的禁言、再按 UUID 挑出这个人的，用已有的按房间的索引就够：一个房间的治理动作不多。

## 上线时

上线后的第一轮，会把生产上已经过期、还禁着的禁言全部解除，并记成到期。这正是要修的；只是先说一声，要事先知道有几条，得只读查一次生产，先问维护者。

## 不做的

- 不给封禁、隐藏加时限。
- 不去扫 Matrix 核对：比如找出房间里还压着、记录却都不生效的人。

## 还留着的

- **建分片和到期同时发生。** #348 补的时候这条还没到期，补到了新分片上；补完、发布之前（新分片还不在活跃分片里），后台正好把它撤了，新分片就留着这条禁言。窗口是建一个分片的最后几步，和 #348 记下的“撤销反过来也一样”是同一个问题；要堵上，得让建分片发布以后再看一眼。发布正好落在后台两次读之间的，第二次读看得到分片变了，会再来一遍。
- **两个管理员同时手动撤同一个人的两条禁言。** 两边都看到对方那条还生效，都不解；两条都撤了，人还禁着。再禁一次、再撤就好。
- **手动撤销时，正在落的那条禁言后来失败了。** 我们已经确保他禁着，记录里却没有生效的禁言。网页上那条显示“失败”，再提交一次就有了生效的记录，能撤。
- 撤销的审计记的是下禁言的人，不是撤的人。原来就这样，这次不改。

## 测试

- 应用层：
  - 到期的禁言在每个活跃分片上撤，记成 `reversed`，写 `moderation.action.expired`；
  - 还有别的生效的禁言（按 UUID 认人，大小写不同也算）时不撤，在每个分片上确保禁着，记成到期；
  - 有一条正在落时不动、15 秒后再看，不写失败审计；超过 5 分钟的 `pending` 当它没有；
  - 动完再看一眼变了（多了一条禁言、分片变了）就不记，下一轮按新的情况做；
  - 房间没了、人没了、私人房间里他没有发言权：不动 Matrix，记成到期；
  - Matrix 有一个分片失败：留在 `applied`，退避从 30 秒翻倍到 15 分钟，第一次失败写 `expire_failed`，之后不再写；
  - 手动撤销一条已经过期的禁言照样走得通；有别的生效的禁言时不解；有一条正在落时回 409；和后台同时撤时后到的不报错；
  - 别的动作带到期时间被拒，旧记录照读。
- Postgres（`#[ignore]`，派发 `suite=all` 时跑）：
  - 只领到期的、已落下的禁言；两个实例同时领只有一个领到；租约过了能再领；退避期间不领；别的实例接手以后，前一个排下次不覆盖；
  - 读一个人的禁言：只读这个房间、这个人的，大写写法的 UUID 也认；私人房间按成员状态和发言权位算他能不能说；人停用、房间停用时照实给出；
  - 已经 `reversed` 的再撤一次直接回原来那条，审计只有一条。
- 真实 Synapse（`#[ignore]`，派发 `suite=all` 时跑）：两个公开大厅分片里禁言一个人，到期后后台跑一轮，他在两个分片里都能说话了，旁人不受影响；另有一条不限时的禁言时，后台跑完他还是说不了。
- 网页：到期时间写出来；到期的显示“已到期”、没有“撤回”；手动撤回的照旧。

## 分步交付

1. 本文。
2. 后台到期撤销：迁移、应用层的判断和后台任务、Postgres、控制面接线；只有禁言能带到期时间；已经撤了的再撤直接回原来那条。
3. 手动撤销禁言用同一套判断：不误解禁、私人房间看发言权、有一条正在落时回 409。
4. 网页：治理记录写出到期时间，到期的显示“已到期”。
