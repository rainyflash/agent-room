# 带时限的禁言到期：在 #350 之上补齐租约、退避和并发

带时限的禁言到期以后，原来没有人去撤：记录上按到期时间算它不生效了，Matrix 里这个人却一直禁着；#348 建新的公开大厅分片时按到期时间补禁言、过期的不补，于是同一个人在旧分片里说不了话，被分到新分片却能说。

#350 做了第一版：控制面每 30 秒找出到期的治理动作，撤掉副作用，记成 `reversed`（`reversed_at` 不早于 `expires_at`），写一条 `moderation.action.expired` 审计；网页台账把“到期解除”和“已撤回”分开说。本文补齐它没做的几件：多个控制面实例的租约、Matrix 撤不掉时的退避、和“同一个人又被禁言”的并发、按 UUID 认人、私人房间里的发言权；手动撤销禁言也改用同一套判断。实现以本文为准，做完一步回来更新“状态”一节。

## 现状

2026-10-09 读代码确认（#350 合并以后）：

- 网页只有禁言能选时长（1 小时、24 小时、7 天，或者“直到撤回”），带 `expiresAtUnixMs`；接口别的动作也收到期时间，只是网页不发。
- 落下禁言时，Matrix 上把这个人压到发言门槛以下：公开大厅在每个活跃分片上只压这个人（`set_public_speaker`），私人房间用成员发言权那一套（`set_speaking`）。
- #350 的到期解除：每 30 秒一轮，按到期时间一页页翻 `applied`、已到期的动作（一页 50 个，最多 20 页），一个个撤。禁言、封禁在每个活跃分片上撤，隐藏回到消息所在的分片撤，踢出只记账、不发邀请。同一个对象在同一房间还有别的同类动作在生效时只记账、不碰 Matrix。撤不成的留在 `applied`，下一轮再试；整台 Synapse 不通时这一轮先停。
- 手动撤销一条已经过期的禁言走得通：撤销不看到期时间，`ModerationAction::reverse` 只要求这条已经落下、撤销时间不早于开始时间。#350 起，撤回落库时发现已经到期解除了，照实交回已撤销的记录，不再报 409。

#350 留下的问题：

- **多个控制面实例。** 生产的控制面可以开好几个副本（`AGENT_ROOM_CONTROL_PLANE_REPLICAS`）。每个副本每 30 秒都把全部到期的动作做一遍：两个副本同时撤同一条，Matrix 上撤两遍，落库只有一个算数。结果是对的，但副本多了，Synapse 上的写跟着翻倍。
- **撤不掉时不退避。** 每 30 秒重试、每次一条警告。一直撤不掉的（比如应用服务在那个房间没了权限），每 30 秒一条日志一直记下去，审计里也看不出来。
- **又被禁言的并发。** 只看“已生效、没到期”的别的禁言，看不到正在落的（`pending`）。管理员在后台解禁的同一刻又禁了他：他那条先在 Matrix 上落下，后台的解禁随后到，就把新禁言盖掉了。记录上新禁言“已生效”，人却能说话。
- **认人按文本。** “还有没有别的生效的禁言”拿 `target_reference` 的文本比。落治理时目标是解析成 UUID 才放行的，写法不一定规范（大写、不带横线），同一个人的两条禁言写法不一样就认不出来（和 #348 同一个坑），第一条到期就把人放出来。
- **私人房间的发言权。** 到期一律把发言权还给他（`set_speaking(true)`），不看房间设置。禁言期间管理者又关掉了他的发言权，到期他又能说了。
- **手动撤销（原来就有）。** 撤一条禁言时不看还有没有别的生效的，Matrix 上直接解；私人房间同样不看发言权。

## 做法

### 领取：租约代替翻页

- 后台照旧每 30 秒一轮，跟 HTTP 服务一起启动、一起关。每轮一条一条地领，做完一条再领下一条，最多 20 条；整台 Synapse 不通时这一轮先停（和 #350 一样）。
- 领取：`status = 'applied'`、`expires_at` 已过、“下次能领的时间”空着或者已经过了，先到期的先领。`FOR UPDATE SKIP LOCKED` 选一条，同一条语句把“下次能领的时间”设成 2 分钟以后，这就是租约；次数加一。
- 做完（记成到期，或者排好下次）就改掉它。进程中途死了，2 分钟后别的实例接着做；Matrix 上的动作都能重放，重做一遍没关系。
- 排下次只在次数还是自己领时的那个数时才写：别的实例接手以后，前一个不会覆盖它的。
- 记成到期靠状态：只有 `applied` 能改成 `reversed`，谁先改谁算，后到的看到已经撤了就当做完了，不再写审计（和 #350 一样）。
- 隐藏、封禁、踢出到期照 #350 的做法撤，只是也改成领取、也按下面的退避重试；“同一个对象上还有没有别的生效的同类动作”，管人的动作改成按 UUID 认人。

### 禁言到期：先看这个人此刻该不该禁着

不只看到期的这一条，而是看这个人在这个房间的全部禁言记录，加上房间此刻的活跃分片、他的 Matrix 账号，私人房间里再看他此刻有没有发言权（在房间里、房间设置里开着发言权）。认人按 UUID，不按文本。

| 这个人此刻的情况 | 后台怎么做 |
| --- | --- |
| 有一条禁言正在落（`pending`，开始不到 5 分钟） | 先不动，下一轮再看 |
| 房间没了（没有活跃分片），或者人没了（没有 Matrix 账号） | 不动 Matrix，直接记成到期 |
| 还有别的生效的禁言 | 在每个活跃分片上把那一条再落一次（已经禁着的不写），记成到期 |
| 私人房间里他此刻没有发言权 | 不动 Matrix，记成到期 |
| 都不是 | 在每个活跃分片上撤（`ModerationEffectGateway::reverse`），记成到期 |

- 开始超过 5 分钟还是 `pending` 的，是没落完控制面就断了的（中途重启），当它没有。正常落一条禁言是每个分片读一次、写一次权限，几秒钟。
- “再落一次那一条”是为了把之前可能被误解的改回来，比如那条生效的禁言落下的同一刻，有人在撤另一条。落禁言能重放，已经禁着的分片什么也不写。
- “下一轮再看”不算失败：不写失败码，不退避，领过的次数退回去。

### 动完再看一眼

动完 Matrix 再读一遍上面的情况。判断变了（期间有人又禁了他、那条生效的被撤了），或者活跃分片变了（期间新开了分片），这次就不记，下一轮从头再来；一样才记成到期。

这样“刚解禁，管理员又禁了他”不会被我们的解禁盖掉。他那条禁言先记成 `pending`，再去动 Matrix：

- 记 `pending` 在我们第二次读之前：我们看得到，这次不记，下一轮确保禁着；
- 在第二次读之后：他动 Matrix 也在我们解禁之后，最后是禁着的。

两种结果都对。这一眼只接得住落禁言：落禁言先在记录里留下 `pending`，我们读得到。手动撤销、另一个实例的到期解除事先不留痕迹，靠下面的锁排队。

### 同一个人一次只做一个

到期解除和手动撤销禁言动 Matrix 之前，先拿这个房间里这个人的禁言锁，做完（记成到期、撤回，或者定下这次不记）再放。拿不到就是别处正在处理他：后台下一轮再看，手动撤销回 409，管理员过一会儿再点。

- 锁是 Postgres 的 advisory lock（`pg_try_advisory_xact_lock`），按房间和这个人的 UUID 算，在一个开着的事务里拿着，做完提交。进程断了，连接一断锁就放了。拿着的时候占一个数据库连接，几秒钟：每个分片读一次、最多写一次权限。
- 为什么要锁：两边都“动完再看一眼”也挡不住这种交错。后台在把另一条禁言再落一次，管理员同一刻在撤那一条：管理员先解、后台后禁；后台第二次读时管理员还没落库，管理员第二次读时后台已经落库了，两边都照常记下。结果人还禁着，记录里却没有生效的禁言。两个管理员同时各撤一条也一样：都看到对方那条还生效，都不解。排上队以后，后到的读到的是先到的做完的样子。
- 落禁言不拿锁：它先记成 `pending` 再动 Matrix，靠上面那一眼接住。这样落禁言不会因为后台正好在处理这个人而失败。

### Matrix 撤不掉时：退避

- 有一个分片动不了就停下，已经动了的不回滚（撤和落都能重放）。
- 这条留在 `applied`，下次能领的时间往后推：30 秒起，每次翻倍，最长 15 分钟。一直试到成功，或者房间、人没了。不设“试了多少次就放弃”：放弃了这个人就一直禁着，比一直重试更糟。
- 失败码（和落治理失败同一套 `matrix.*`）记在新列里，给排查用，接口不返回。
- 第一次失败写一条 `moderation.action.expire_failed`（failed）审计，同一条连着失败不再写；控制面每次失败记一条警告，带动作 ID 和失败码。

### 记录和审计

和 #350 一样，不改：

- 不加新状态，沿用 `reversed`。网页（桌面端里也是这份网页）对治理动作严格校验：`status` 只认四种，对象是 `.strict()`，旧版桌面端见到新状态或新字段，整张治理列表都读不出来。所以接口的形状一点不改，到期的靠 `reversed_at >= expires_at` 认出来。
- 审计的操作者照旧记成下这条禁言的人，和这条动作的其他审计一样，靠动作码看出是到期。审计表的操作者类别虽然允许 `service`，但读审计的代码只认 `principal`：写了别的，现在的和旧版的控制面都读不出整张审计。

### 手动撤销禁言也用同一套判断

撤的是禁言时，和后台一样先拿禁言锁、看这个人此刻该不该禁着、动完再看一眼，区别只在定不下来的时候：

- 拿不到锁，或者有一条禁言正在落：什么也不动，回 409 `moderation.conflict`，管理员过一会儿再点。
- 动完再看一眼变了：照新的情况再动一次（正在落的那条当它会生效，确保禁着），然后照常记成撤回。手动撤销不能叫管理员等下一轮。

结果是：还有别的生效的禁言时不再误解禁，私人房间看他此刻的发言权。封禁、踢出、隐藏的撤销不变。

### 网页：过了到期时间、还没解除的

#350 的台账上，生效中的限时禁言写“{时间} 自动解除”。后台在退避的时候，过了这个时间它还是“已生效”，看着像坏了。改成：过了到期时间、还是 `applied` 的显示“正在解除 / Ending”，时间写“{时间} 到期”。“撤回”按钮留着，管理员可以不等退避、马上再试一次。接口不变，中英文一起改。

撤回回 409 `moderation.conflict`（别处正在处理这个人、有一条禁言正在落）时，网页现在和读不到治理信息说的是同一句“暂时读不到治理信息：moderation.conflict”。改成说清楚：这个人的禁言正在处理，过一会儿再点撤回。

### 数据库

一个新迁移，只加列和索引：

```sql
ALTER TABLE agent_room.moderation_action
    ADD COLUMN expiry_attempts integer NOT NULL DEFAULT 0,
    ADD COLUMN expiry_next_attempt_at timestamptz,
    ADD COLUMN expiry_failure_code text,
    ADD CONSTRAINT moderation_action_expiry_attempts CHECK (expiry_attempts >= 0),
    ADD CONSTRAINT moderation_action_expiry_failure_code_length CHECK (
        expiry_failure_code IS NULL OR length(expiry_failure_code) BETWEEN 1 AND 128
    );

CREATE INDEX moderation_action_expiry_due_idx
    ON agent_room.moderation_action (expires_at)
    WHERE status = 'applied' AND expires_at IS NOT NULL;
```

- `expiry_next_attempt_at` 一列管两件事：在做的时候是租约到期的时间，失败以后是下次重试的时间。空着就是到期马上能领。
- `expiry_attempts` 是领过几次（“下一轮再看”的那几次排下次时退回去，不算）：排下次时拿它认“还是不是我领的那次”，退避也按它算。
- 禁言锁不用表：advisory lock 不落数据。
- 旧版控制面不读也不写这几列：迁移可以在切换服务器之前跑，回滚到旧版照常读写治理记录（旧版就是 #350 那样翻页做）。已经撤了的记录上留着这几列的旧值，没关系，领取只看 `applied` 的。
- 不建新表。读一个人的禁言是按房间读出这个房间的禁言、再按 UUID 挑出这个人的，用已有的按房间的索引就够：一个房间的治理动作不多。

## 不做的

- 不去扫 Matrix 核对，比如找出房间里还压着、记录却都不生效的人。
- 封禁到期的判断不改：照 #350，同一个人还有别的生效的封禁时只记账。封禁只能绕过网页直接调接口才带时限。

## 还留着的

- **建分片和到期同时发生。** #348 补的时候这条还没到期，补到了新分片上；补完、发布之前（新分片还不在活跃分片里），后台正好把它撤了，新分片就留着这条禁言。窗口是建一个分片的最后几步，和 #348 记下的“撤销反过来也一样”是同一个问题；要堵上，得让建分片发布以后再看一眼。发布正好落在后台两次读之间的，第二次读看得到分片变了，会再来一遍。
- **私人房间里房主同一刻改他的发言权。** 改发言权的那条路不看禁言，到期解除也只在动之前看一眼他的发言权；两边恰好同时动时，以后写进 Matrix 的为准，可能和房间设置对不上，房主再改一次就好。改发言权和禁言原来就各管各的（禁言期间房主打开他的发言权，Matrix 上也会把禁言盖掉），这次不改。
- **手动撤销时，正在落的那条禁言后来失败了。** 我们已经确保他禁着，记录里却没有生效的禁言。网页上那条显示“失败”，再提交一次就有了生效的记录，能撤。
- 私人房间里封禁到期会把人请回房间：#350 用的是人工撤回同一套副作用（解封再邀请）。踢出到期不发邀请，封禁到期按说也不该发；封禁只能绕过网页才带时限，这次不改。
- 撤销的审计记的是下禁言的人，不是撤的人。原来就这样，这次不改。

## 测试

- 应用层：
  - 一轮一条一条地领，最多 20 条；整台 Synapse 不通时停下；
  - 禁言到期：没有别的禁言时在每个活跃分片上撤；还有别的生效的禁言（大小写不同的写法也算同一个人）时在每个分片上确保禁着；有一条正在落时不动、下一轮再看，不写失败；超过 5 分钟的 `pending` 当它没有；房间没了、人没了、私人房间里他没有发言权时不动 Matrix；都记成到期；
  - 动完再看一眼变了（多了一条禁言、分片变了）就不记，下一轮按新的情况做；
  - 别处正拿着这个人的禁言锁时不动、下一轮再看；
  - Matrix 有一个分片失败：留在 `applied`，退避从 30 秒翻倍到 15 分钟，第一次失败写 `expire_failed`、之后不再写；
  - 手动撤销禁言：有别的生效的禁言时不解；私人房间里他没有发言权时不还给他；有一条正在落、或者拿不到锁时回 409；
  - #350 已有的用例（隐藏、踢出、和人工撤回撞上）照样过。
- Postgres（`#[ignore]`，派发 `suite=all` 时跑）：
  - 只领到期的、已落下的；两个实例同时领只有一个领到；租约没过不能再领，过了能；退避期间不领；别的实例接手以后，前一个排下次不覆盖；
  - 读一个人的禁言：只读这个房间、这个人的（已落下的和正在落的），大写写法的 UUID 也认；私人房间按成员状态和发言权位算他能不能说；人停用、房间没了照实给出；
  - 禁言锁：同一个房间里同一个人一次只有一个拿得到，放掉以后又能拿；换个人、换个房间互不影响。
- 真实 Synapse（`#[ignore]`，派发 `suite=all` 时跑）：两个公开大厅分片里禁言一个人，到期后后台跑一轮，他在两个分片里都能说话了，旁人不受影响；另有一条不限时的禁言时，后台跑完他还是说不了。
- 网页：过了到期时间、还是 `applied` 的显示“正在解除”和到期时间，“撤回”还在。
