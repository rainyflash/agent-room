# 设备自动签名：不再要恢复密钥

## 背景

2026-10-02，维护者的桌面端每次打开都提示“这台设备需要签名”，只给两条路：输入恢复密钥，或者用另一台设备核对。他的原话：“恢复密钥是什么狗屎东西，你以为你在做国家机密？”

查下来（线上只读）：

- 桌面端其实在服务器上已经由他的签名身份签过，是安全页的判断比 Agent 的标准更严，误报了。#287 已改成同一个标准。
- 他的账户从没设过恢复密钥，也没有服务器端密钥备份；账户的签名私钥不在任何一台设备上。所以网页端那台**永远签不了**：两条路都走不通。
- 就算走得通，恢复密钥和设备核对对普通人也太重。核心体验是“一个按钮把 Agent 请进来就能聊”，加密不能把人挡在门外。

维护者定了（2026-10-02）：**服务器替账户保管签名用的钥匙，任何设备一登录就自动签名、自动找回加密历史；界面上不再有恢复密钥和设备核对。** 代价是服务器（也就是部署方）理论上能替账户签设备，和网络 Agent 进私人房间时“服务器读得到发给它的消息”是同一档信任。见 [ADR 0011](../../docs/adr/0011-automatic-device-signing.md)。

## 目标

- 人在任何一台设备（网页、桌面端）登录后几秒内，这台设备就由他的签名身份签好，Agent 照常给它房间密钥。整个过程不弹任何框、不用输任何东西。
- 换新设备时，之前的加密历史自动回来（服务器端密钥备份）。
- 界面上没有“恢复密钥”“恢复口令”“核对设备”“安全码”。
- [ADR 0009](../../docs/adr/0009-encryption-trust-on-first-use.md) 的规则不变：Agent 仍只把房间密钥发给由主人签名的设备，只信由主人签名的设备发来的消息。

## 不做

- 不提供“只在本机保管、服务器不知道”的选项。
- 本机 Bridge 上 Agent 自己的加密恢复（桌面端安全页里“这台电脑上的 Agent 恢复”）这次不动：Agent 的恢复凭据本来就自动存在系统凭据管理器里，只在存储丢了的少见情况下才会出现。以后要动另写。
- 别的 Matrix 客户端（Element 等）登录同一个账户：照旧按 Matrix 的标准流程，不在这次范围里。

## 服务器保管的是什么

Matrix 的标准做法是“密钥存储”（secret storage，4S）：账户的三把签名私钥（主密钥、自签密钥、用户签名密钥）和服务器端密钥备份的钥匙，都用一把 32 字节的随机钥匙加密，存在 Matrix 账户数据里。这把钥匙就是以前让人保管的“恢复密钥”。

现在改成**控制面保管这把钥匙**，人看不到它：

- 存什么：钥匙的 `keyId` 和 32 字节内容。
- 怎么存：用部署里已有的封存密钥按用途派生一把子密钥（和网络 Agent 的秘密分开），AES-256-GCM 封存，附加数据绑定主体 ID、用途和密钥版本，挪给别人或别的用途都打不开。新表 `principal_encryption_key`（主体 ID、`key_id`、封存后的钥匙、封存版本、更新时间），每个主体一行。
- 给谁：只给已登录的本人（登录 Cookie），只给他自己的。不进日志，响应带 `Cache-Control: no-store`。
- 部署没配封存密钥时这三个接口回答“不可用”，设备上退回到只能建立第一份身份、不再自动签别的设备（自托管而又不配密钥的少见情况）。

## 控制面接口

和 `/account/export`、账户删除一样挂在 `/account` 下，都在登录会话下；改动类的要校验来源。

- `GET /account/encryption-key`：`{ keyId, key }`（`key` 是 base64）；没有就 404。
- `PUT /account/encryption-key`，正文 `{ keyId, key }`：存下（覆盖旧的）。
- `POST /account/encryption-reset`，正文是新的签名公钥（Matrix `keys/device_signing/upload` 的正文，不带认证）：控制面核对每把公钥都属于本人、必须有主密钥，再以应用服务的身份冒充本人转给 Synapse（应用服务的请求免交互认证，MSC4190）。只在重建签名身份时用。按主体限流（一小时 3 次）。

  原来设想用 Synapse 管理接口开 10 分钟豁免（`_allow_cross_signing_replacement_without_uia`），实测这个豁免只在接了 MAS 时起作用，见“状态”。

## 设备上怎么做（网页端和桌面端共用一份代码）

替换现在的 `ensureFirstEncryptionIdentity`。登录、加密初始化好之后跑一遍，每次启动也跑；每一步都可以重复做：

1. **账户还没有签名身份（第一台设备）**：
   - 建立签名身份（这台设备随之签好）；
   - 生成一把钥匙，建密钥存储和服务器端密钥备份；
   - `PUT` 把钥匙交给服务器。
2. **这台设备已由你签名，本机有签名私钥，密钥备份的钥匙也加载了**：服务器上要是还没有钥匙，就新生成一把、把密钥存储重新加密一遍，再交给服务器；否则什么都不做。
3. **其余情况**，先 `GET` 服务器上的钥匙：
   - **要到了，和账户的密钥存储对得上**：
     1. 用它打开密钥存储，拿到签名私钥；
     2. 签这台设备，加载备份钥匙；
     3. 在后台找回历史。
   - **没要到，或者对不上**（以前设过恢复密钥、服务器不知道；或者谁手里都没有私钥）：**重建一次签名身份**。
     1. 新建签名身份，上传新签名公钥的请求改送 `POST /account/encryption-reset`，由控制面代传；
     2. 新建签名身份并签这台设备；
     3. 新建钥匙、密钥存储和密钥备份；
     4. `PUT /account/encryption-key` 交给服务器。

     之后别的设备打开时，按第 3 步的第一种情况自动签上。

- 失败不挡登录，也不弹框：安全页显示“加密还没准备好”和一个“重试”；设置上的提醒点只在这时亮。
- 两台设备同时重建：后存的钥匙生效；先存的那台下次打开时发现自己没签名，会用服务器上的钥匙签上，自己收敛。

## 界面

- **安全页**：只留“这台设备：已就绪 / 正在准备 / 出错可重试”，以及设备列表（只能撤销）。要去掉的有：恢复密钥一节、签名的两条路、核对按钮、安全码对话框和收到核对请求的提示。
- **“解不开的消息”提示**：去掉“验证这台设备”按钮。设备会自动签好，找回请求随后自动发出（#211 的逻辑不变）。
- **删除只给这些功能用的东西**：文案（中英一起）、样式和适配器方法，比如 `setupRecovery`、`recover`、核对会话。

## Agent 那边

查过 matrix-sdk-crypto 0.18 的源码（发房间密钥用 `IdentityBasedStrategy`，解密要求 `TrustRequirement::Untrusted`，见 `crates/matrix-adapter/src/sdk.rs`）。结论分三点：

- **重建签名身份之后**，Agent 看到的是“身份换了”（pin violation）。这在 0.18 里既不影响发房间密钥，也不影响解密：新身份签过的设备照常拿到房间密钥；它发的消息解出来是 `UnverifiedIdentity`，正是我们接受的（`mapping.rs` 的 `sender_device_trusted`）。发送前刷新成员身份、收到未知设备的消息刷新后再判（#116），会把短暂的缓存空档补上。
- **没重签的旧设备**会收到“未验证、不发密钥”的通知，它发的消息被隔离。自动签名正好保证每台设备都会签上。
- **以前跟主人核对过安全码的 Agent**（用过 MCP 的 `agent_room_matrix_security` 核对），重建后在它看来是“核对过的人换了身份”（verification violation）：
  - 整个房间都发不出去（`IdentityChanged`）；
  - 主人发的消息被隔离。

  这和 ADR 0009 第 3 条的设计一致，但现在重建是正常操作。所以 Agent 发现**自己的主人**有 verification violation 时，自动撤销对他的旧核对（`withdraw_verification`，同时记住新身份），记一条日志，接着照常发收。别人的身份变化仍按 ADR 0009 处理。

## 维护者现在的账户会怎样

他的账户没有密钥存储、没有备份，手里也没有谁有签名私钥。升级后：

- 第一台打开的设备（桌面端或网页端）按第 3 步的第二种情况**重建一次签名身份**；另一台下次打开时自动签上。
- 重建之前的加密历史：人自己设备上的旧会话没有服务器端备份，找不回来；Agent 发的旧消息照旧可以请 Agent 重发（[找回解不开的历史](../room-key-recovery/design.md)）。
- 房间里别的人的网页端会提示“有人的加密身份变了”（ADR 0009 第 3 条），点一下确认就好。

## 安全

- 服务器（部署方）拿得到这把钥匙，就能替账户签设备、读服务器端备份里的房间密钥，也就能读这个账户在加密房间里的消息。这是维护者接受的取舍，写进 ADR 0011。
- 封存的钥匙只给本人的登录会话；数据库泄漏而封存密钥没泄漏时，拿到的只是密文。
- 账户删除时一起删掉这一行（账户生命周期的清理里加一项）。
- 撤销设备、退出登录不影响这把钥匙：它属于账户，不属于设备。

## 分步

每步一个 PR：

1. **设计**：本文和 ADR 0011，`CLAUDE.md` 的“产品决定”记一条。
2. **控制面**：
   - 保管钥匙的表（迁移）、封存的子密钥、三个接口、应用服务代传签名公钥、限流、账户删除时清理；
   - 测试，包括真实数据库和真实 Synapse 的管理接口。
3. **设备上的自动签名**：
   - 替换 `ensureFirstEncryptionIdentity`；
   - 单元测试；
   - 真实 Synapse 上的浏览器验收：新设备登录后自动签名；重建身份后第二台设备自动签上；
   - 本机 Agent 能解开新设备发的消息。
4. **界面**：去掉恢复密钥和核对，安全页简化，删掉没人用的文案、样式和适配器方法。
5. **Agent 对主人自动撤销旧核对**（matrix-adapter，Bridge 和网络网关共用），并给无头验收加一轮：主人重建签名身份后，本机 Agent 和网络 Agent 照常给他的新设备发房间密钥、收他的消息。

第 2 到第 4 步要在同一个版本里发布：只有界面没有自动签名，人就没路可走了。
