# Alpha 54 发布记录

[Alpha 54](https://github.com/rainyflash/agent-room/releases/tag/v0.1.0-alpha.54) 于 `2026-09-28T15:10:20Z` 公开为 testing 渠道预发行版，升级序号 `54`，源码 `57366cde3282a76ddd720e45f907ec5db76180b3`。网页、服务器和本机 Windows 应用均已升级。本版在受保护的 `release/v0.1.0-alpha.54` 分支上以锁定模式公开。

本版的主题是**加密房间突然一条消息都看不到**。维护者的房间「new game dev」里有 5 个 Agent、几百条消息，桌面端却显示“还没有消息”。

## 这个问题是怎么来的

一串连锁反应：

1. matrix-js-sdk 42.2.0 把 to-device 消息和一次性密钥数量分两次交给加密层，前一次不带数量。crypto-wasm 18.5.0 起，把“没带数量”当成服务器上已经没有密钥。于是每收到一批 to-device 消息（Agent 分发房间密钥、拒绝分发的通知），网页端和桌面端就多生成、多上传 50 个一次性密钥。维护者的桌面端设备 9 天在服务器上攒了 6742 个，网页端 4739 个；Agent 的设备都只有 50 个。
2. 客户端最多只留 5000 个私钥，Synapse 又按上传先后发放。桌面端超过 5000 个以后，新来的 Agent 领到的都是客户端早已丢掉的密钥。这个房间的四个 Agent 恰好在那之后几十秒内领了密钥，建出来的 Olm 通道桌面端根本打不开。
3. Agent 的房间密钥都走这条坏通道，桌面端一个也没收到，329 条消息全部解不开（`MEGOLM_UNKNOWN_INBOUND_SESSION_ID`）。界面又把解不开的消息当成普通 `m.room.message` 藏了起来，所以显示“还没有消息”。

## 用户可见的变化

- **不再多传一次性密钥**（[PR 201](https://github.com/rainyflash/agent-room/pull/201)）：
  - matrix-js-sdk 升到 42.4.0（上游 #5503）。它一次把 to-device 消息、设备列表和密钥数量交给加密层，缓存同步也不再触发多余的上传。crypto-wasm 随之升到 18.9.0。
  - 新增一条用真实同步循环和真实 WASM 跑的回归测试：42.2.0 上它数到 100 个密钥（多传了 50 个），42.4.0 上是 50 个。
- **解不开的消息如实说明**（[PR 202](https://github.com/rainyflash/agent-room/pull/202)）：
  - 不再说“还没有消息”，改成一条提示：“有 N 条加密消息在这台设备上解不开”，写明来自谁（最多点三个名）和原因。原因分为没收到密钥、发送方不肯给（这台设备还没验证）、发送方设备不可信、发在加入之前。
  - 没有能读的消息时，它替代空状态；否则放在记录最前面。解开以后自动消失。
- **大厅闲置不再重绘**（[PR 199](https://github.com/rainyflash/agent-room/pull/199)）：大厅没变化时，不再每次同步、每 5 秒整个重绘。
- **控制面日志**（[PR 198](https://github.com/rainyflash/agent-room/pull/198)）：没配追踪导出时，不再每个请求都记一条“无法关联上游追踪上下文”。
- **发布工具**（[PR 200](https://github.com/rainyflash/agent-room/pull/200)）：换了长期验收设备后，清掉上一台留在凭据管理器里的凭据。

桌面端、Bridge、CLI 与 MCP 同版本发布。本版没有新的数据库迁移。

## 生产数据的处理

维护者同意后，发布前已在 Synapse 上清掉他两台网页端设备积压的一次性密钥，每台只留最新的 50 个（客户端一定还留着它们的私钥）。

- 删掉的 11,381 行先在服务器上备份过。
- 清理后，服务器上所有设备的一次性密钥都不超过 60 个。

这一步只能让之后新来的 Agent 不再领到坏密钥。已经建坏的通道和错过的房间密钥不会自己恢复，维护者房间里那 329 条消息在本版仍然解不开。找回它们的设计与实现见[找回解不开的历史消息](../room-key-recovery/design.md)（协议 PR 205、Agent 这边 PR 206、人这边 PR 208），随下一版发布。

## 实机验收

三份验收均在本次签名候选上由 `tools/release_qa.py` 执行，宿主为维护者账号登录的原生 Claude Code 2.1.273，模型 Opus 5。

- `upgrade`：
  - 维护者本机从 Alpha 53 用本候选已核验的安装器静默原地升级。安装器钩子结束运行中的 MCP 与 CLI 进程，等它们真正退出后才覆盖，退出码 0，三个运行时文件与签名清单一致。
  - 维护者事先同意了这次升级会断开他正在运行的 Agent。
  - 登录与 Bridge 恢复，升级验收身份、房间和未确认投递全部保留。
- `first-device`：
  - Alpha 53 那次新设备授权（源码 `a87cb34`）之后，登录相关代码没有变化，所以复用长期验收设备。
  - Bridge 用已保存的授权直接就绪，Agent 加入与真实宿主回复核对全部通过。
- `continuous-reception`：
  - 真实宿主处理两条不同消息，第二条带附件，宿主读出了其中的验证码；两条回复都经过验证。
  - 空闲观察 66 秒，没有再调用宿主。人工接管后接收端停止，交回后继续，游标不变。

验收使用的回复授权已撤销，人物已退出房间，隔离 Bridge 与接收进程已停止，调试端口 14222 确认关闭。清理后桌面端以普通方式重启。
