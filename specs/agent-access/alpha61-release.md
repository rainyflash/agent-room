# Alpha 61 发布记录

[Alpha 61](https://github.com/rainyflash/agent-room/releases/tag/v0.1.0-alpha.61) 于 `2026-10-03T00:54:40Z` 公开为 testing 渠道预发行版，升级序号 `61`，源码 `5c8aedf9bcad8f8613bd3318d18b14de47ed83d2`。网页、服务器和本机 Windows 应用均已升级。本版在受保护的 `release/v0.1.0-alpha.61` 分支上以锁定模式公开。

本版只做一件事：**人的设备自动签名，不再要恢复密钥**（[ADR 0011](../../docs/adr/0011-automatic-device-signing.md)，设计见 [设备自动签名](../device-signing/design.md)）。

## 用户可见的变化

- **登录以后这台设备自动签好，不用输任何东西**。服务器替账户保管签名用的钥匙，任何设备一登录就由你的签名身份签好，Agent 照常给它房间密钥；换新设备时，之前的加密历史自动回来。
  - 设计 [PR 289](https://github.com/rainyflash/agent-room/pull/289)。
  - 控制面保管钥匙 [PR 290](https://github.com/rainyflash/agent-room/pull/290)：钥匙用部署的封存密钥派生的子密钥加密存放，只给已登录的本人。
  - 设备上自动签名 [PR 291](https://github.com/rainyflash/agent-room/pull/291)：第一台设备建签名身份、密钥存储和服务器端密钥备份，把钥匙交给服务器；之后的设备从服务器取钥匙、自己签好。
- **界面上不再有恢复密钥、恢复口令和设备核对**（[PR 293](https://github.com/rainyflash/agent-room/pull/293)）。安全页只说这台设备“已就绪 / 正在准备 / 出错可重试”，设置上的提醒点只在出错时亮。
- **主人重建签名身份以后，Agent 照常收发**（[PR 294](https://github.com/rainyflash/agent-room/pull/294)）。以前跟主人核对过安全码的 Agent，主人换了签名身份后会整个房间发不出消息；现在 Agent 自动撤掉旧的核对、记住新身份。
- **重建签名身份不再卡在交互认证上**（[PR 295](https://github.com/rainyflash/agent-room/pull/295)）。没接 MAS 的 Synapse 对已有签名身份的账户换签名身份一律要交互认证，只有应用服务的请求例外。现在新签名公钥由控制面以应用服务的身份替本人上传，为此应用服务注册多了一个覆盖所有本地用户的非独占命名空间。
- **第一台设备建签名身份时被打断也不会卡住**（[PR 297](https://github.com/rainyflash/agent-room/pull/297)，发布中发现，见下）。

代价是部署方理论上能替账户签设备，维护者接受。

桌面端、Bridge、CLI 与 MCP 同版本发布，IPC 仍是 `4.3`。服务端多了一个数据库迁移（新表 `principal_encryption_key`），先部署服务端、再发布客户端。

## 发布中发现的问题：第一台设备的签名公钥没传上去

版本号在 [PR 296](https://github.com/rainyflash/agent-room/pull/296) 升到 Alpha 61（`12:43Z` 合并），合并后立刻派发了完整 CI 和签名候选。

完整 CI 的真实网页登录抓到一个真问题：

- 账户第一台设备建签名身份时，如果上传公钥那一下页面跳走了，私钥留在本机、公钥没传上去。
- 再打开时，matrix-js-sdk 的 `bootstrapCrossSigning` 看到本机有私钥就跳过上传。界面说“已就绪”，服务器上却一直没有签名身份，第二台设备也签不上。

修复是 [PR 297](https://github.com/rainyflash/agent-room/pull/297)（`13:30Z` 合并）：

- 服务器上没有签名身份时，一律用 `resetEncryption` 从头建，上次留下的私钥、密钥存储和备份都不沿用。
- 真实网页登录验收故意掐断第一次上传，之后向服务器确认账户真的有签名身份。

第一次派发的[完整 CI](https://github.com/rainyflash/agent-room/actions/runs/37008448780)和[签名候选](https://github.com/rainyflash/agent-room/actions/runs/37008459378)都在 `13:10Z` 取消。PR 297 的合并提交成为发布提交，在它上面重新派发。

## 为什么用了 12 个多小时

从版本 PR 合并到网页上线约 12 小时 13 分钟（`10-02 12:43Z`–`10-03 00:56Z`），大头是我这边的失误：

- 约 1 小时 30 分钟：查出、修好 PR 297，在新的发布提交上重新跑候选和完整 CI（`14:11Z` 全绿）。
- **约 9 小时空等**。部署前要等服务器上的定时备份跑完，我写的等待脚本拿远程命令的退出码当条件。最后一步 `systemctl is-active` 在服务停下时退出码是 3，正好在条件满足时被当成失败，脚本一直没往下走，也没有截止时间，直到维护者问“还没好？”才发现。以后等待脚本按命令输出判断、设截止时间，并在走开前先看头几轮输出。
- 约 1 小时 20 分钟在等设备码：第一个码（`23:25Z`）过期时，维护者正在处理他桌面端的问题（见下）；第二个码 `00:47Z` 批准。

维护者事先答应了到时直接升级他本机的桌面端。

## 为什么这次要设备码

发布门禁规定：上次新设备授权之后，登录相关的代码有变化，就不能复用长期验收设备，要重新授权一台。[PR 295](https://github.com/rainyflash/agent-room/pull/295) 给应用服务注册加了命名空间，改到了 `tools/prodops/render.py`，这个文件里也有登录回调的路由，所以门禁把它算作登录相关代码。

这次授权的设备成了新的长期验收设备（`agent-room.alpha61.acceptance.fresh-device`）。

## 维护者桌面端的消息全部解不开

发布当晚，维护者打开桌面端的房间，只看到“消息解不开”。

- 查下来：这台桌面端本机的加密存储 2026-09-30 被重建过，设备号却没换，身份密钥换了新的。Agent 的加密库遇到“同一个设备号、密钥变了”一律不认（防冒充），所以从那以后没有 Agent 给它房间密钥。重建的原因还没查实。
- 当时的处理：维护者在桌面端退出登录再登录，换了一个新设备号，自动签名以后就正常了。
- 下一版要做：启动时发现本机密钥和服务器上这台设备的对不上，就自动退出这台设备、换新设备号重新登录；网页端还要申请持久存储，免得浏览器清掉加密存储。
