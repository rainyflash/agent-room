## 用户可见的变化

- 新装的 Windows 桌面应用不再每次启动都清掉应用里的登录、这台电脑的授权和本机 Agent。从 Alpha 48 起每一台全新安装的 Windows 都中，回来的人看到的是又要登录、自己的 Agent 全掉了；以前被收走的 Agent 在更新后第一次启动时放回原处，照原来的身份接着用（#959，原因见 CLAUDE.md“代码里的坑”）。
- 同一种毛病在换账号那条路上：在 Windows 上换账号时有文件被别的程序开着（比如后台一直在等消息的 Agent），以后每次打开都清掉新账户的登录、收走新账户的 Agent。现在只把还开着的那几个文件留在原处，照样算换好了（#962）。
- 后台回复给宿主一次最多 10 分钟，以前 3 分钟（#965，见下一节）。
- “新建房间”“换个房间”一打开，光标就在名字框和搜索框里（#964）。
- 发行说明照旧提醒还在用 Alpha 74 或更早版本的人手动下载安装一次。

用户看不到的：实机验收发第二条消息时只在输入框那一块里认附件（#965 的第二个提交），记下新设置下头一次每天更新病毒库的结果（#963）。

桌面端、Bridge、CLI 与 MCP 同版本发布，IPC 和本机 MCP 的工具都没变，桌面端没加原生命令。没有迁移，部署配置没加新变量，没改告警规则，发完没跑 `telemetry-apply`。`account_reminder` 表和 Synapse `/messages → 403` 那条噪音规则照旧留着，下一版删。

回滚可以退到 Alpha 100：没有迁移。

## 第一个发布提交为什么让位

`d088f3f1` 的 CI、候选都一次过，`08:43Z` 起等维护者放行，他 `13:14Z` 说“升吧”。服务端 `13:20Z` 部署好，本机升到 Alpha 101，实机验收从 `13:21Z` 起试了四轮，都停在后台回复上：

1. 第一轮停在第二条消息：桌面端页面被点到了维护者自己的房间，没发出去。重新进验收房间以后发出去了，第二条的回复却被接收端判成超时（`receiver.host_timeout`），记成要人处理、接收端停下。宿主其实读了附件、答对了验证码，可是那一轮用了 151 秒，加上起进程和退出过了接收端给宿主的 3 分钟。
2. 原因在宿主那边：维护者的 Codex 当天自动更新（0.167.0-alpha.4.1），默认模型换成了上下文 258,400 的那个。加上他装的 11 个 MCP 服务和 20 个插件，每次调模型的底稿约 266k token，每调一次都要先压缩 30–40 秒；带附件的消息要调三次。验收一直沿用的那个任务（2026-10-09 建的）第一条 56 秒、doctor 72 秒。
3. 第二轮换了一个干净的 Codex 任务，还是这样：接收端先从服务器拿回第一轮没回完的那一条，标成跳过以后，第二条消息的草稿停在附件那一步，同名的附件在房间里上一轮的消息上也有，按名字找到了两个（Playwright 的严格模式）。手动点了发送，第二条又是超时。
4. 第三轮想换 Claude Code 当宿主：本机的 Claude Code 登录过期了，重新登录只能维护者来。

维护者看了说 3 分钟这个时限没意义，放宽就是。#965 把接收端给宿主的时间放到 10 分钟（`HOST_TIME_LIMIT`，只防宿主卡死），验收工具等宿主的时间一起放到 12 分钟（`HOST_WAIT_SECONDS`），发第二条消息时只在输入框那一块里认附件。#965 `14:44:09Z` 合并，它的合并提交成为新的发布提交。

让位的做法照 Alpha 84：

- 验收 `cleanup`（撤销测试授权、关掉验收人物的连接、停隔离 Bridge、桌面端恢复普通启动）。
- 草稿改名为 `v0.1.0-alpha.101-superseded-d088f3f1`（没有建过标签）；新版本公开以后删掉了。
- 本机这一次的记录挪进 `alpha101/attempt-d088f3f1/`，服务器上的发布目录改名为 `alpha101-attempt-d088f3f1`（正在跑的服务认的是按摘要命名的部署目录，不受影响）。
- 本机用核验过的 Alpha 100 安装器装回 100（`14:37Z`），核对了桌面端和命令行的版本、三个运行时文件的摘要。
- 升级前的两项检查改成接受生产上已经是 Alpha 101，发完改回了原来的写法。

生产在 `13:20Z`–`15:35Z` 跑的是 `d088f3f1`，网页和下载还是 Alpha 100，两者兼容，这段时间控制面就绪检查正常。

## 实机验收（第二个发布提交）

- 升级前基线一次过。本机从 Alpha 100 升级，安装器一次装上，升级验收一次通过（`15:35:41Z`–`15:37:08Z`）：登录、身份和没确认的消息都保住了。
- `start` 按 `LOGIN_PATHS` 看到登录相关路径没改，复用 Alpha 100 那台长期验收设备，没要设备码。
- 第一次停在 doctor（`15:38:51Z`，`receiver.attachment_unreadable`）：宿主还是第一个发布提交第二轮建的那个 Codex 任务，这次 48 秒就答了，没超时，可它不肯直接读验证码文件，回的是只能读经绑定的 Agent Room 会话核对过的附件、请把文件发到房间里。这个任务上一轮在房间里经 `agent_room_open_content` 读过附件，后台回复的提示把那个路径叫作“已校验的下载”，它就照这条规矩拒了契约检查。#966（合并在发布提交之后，不在这一版里）让契约检查的提示照实说那个文件是接收端写的已校验下载，doctor 没过时带上宿主交回了什么。
- 换了一个干净的 Codex 任务（`01a1fec4…`），登记那一步又被拒：`bridge.host_session.reception_already_bound`。验收人物在隔离 Bridge 里的会话还记着后台回复交给了旧任务（只在内存里），会话 15 分钟没人用才关（`host_sessions.rs` 的 `IDLE_LIFETIME`）；第一个发布提交第二轮换任务时正好隔得更久，没碰上。所以等到 `15:59Z`、中间谁都不碰那个会话，再跑一次。
- 接收端第一次启动又拿回了第一个发布提交第二轮那条没回完的投递（第二条验收消息），核对 20 秒后报 `receiver.reply_unconfirmed` 退出，预料中的：标成跳过（`receiver resolve --action skip`）、挪开这次启动的记录，再跑 `run`。
- `run` 这次一次通过（`16:02:09Z`–`16:11:09Z`）：私人房间“发布验收”里两条消息都回了，第二条读出了附件里的验证码，空闲、接管和恢复都过了。新任务每一轮调宿主的用时：doctor 113 秒，第一条 60 秒，带附件的第二条 170 秒。加上起进程和退出，第二条在原来的 3 分钟下还会超时。
- `attachment` 那一步一次过：装好的桌面端把第二条验收消息的附件存成 `alpha101-attachment.txt`，和发出去的一字不差，核对完删掉了。
- 验收跑完、证据传上去以后跑了 `cleanup`，桌面端恢复普通启动。长期验收设备还是 Alpha 100 那台（`agent-room.alpha100.acceptance.fresh-device`，人物在“发布验收”里）。
