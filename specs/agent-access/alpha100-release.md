## 用户可见的变化

- 收件箱里每一条“谁找你”前面有他的头像，Agent 的名字跟它的机器人一个颜色，和对话、Agent 表格里是同一种；“看原文”和旁边两个按钮对齐了（#953）。
- 服务器每天更新一次病毒库，那几分钟里有几条请求会慢上几秒。扫描服务改成先放掉旧的病毒库、再装新的，不再把别的服务的内存挤出去；更新的那几十秒里，上传的正文和附件要多等一会儿才扫完（#955，原因和量到的数见下面“每天更新病毒库”）。
- 邮件提醒不做了。服务器不再每小时替每个账户试算该不该提醒（这一步从没发过信），设置和隐私说明页里的相关说法一起去掉了；网页通知、桌面通知和“暂停提醒”照旧（#952）。
- 发行说明照旧提醒还在用 Alpha 74 或更早版本的人手动下载安装一次。

用户看不到的：“Agent 请求失败”的告警带上失败落在哪一步（#954，为了查 agent-room-ops#35 的登记 409）。

桌面端、Bridge、CLI 与 MCP 同版本发布，IPC 和本机 MCP 的工具都没变，桌面端没加原生命令。没有迁移（`account_reminder` 表这一版还留着，代码已经不读不写它，下一版删），compose 只多了扫描容器的一项设置，没有新变量。没改告警规则，发完没跑 `telemetry-apply`。

回滚可以退到 Alpha 99：没有迁移，旧代码要的 `account_reminder` 表还在。

## 每天更新病毒库

agent-room-ops#108、#109、#110 报的是控制面等数据库连接等了 3.3–4.1 秒（超时是 5 秒）。查下来是扫描容器里的 ClamAV 每天更新一次病毒库：它默认先装好新的一份、再放掉旧的，两份同时在内存里，它自己到 1.8 GB，机器只有 3.9 GB。数据库、聊天服务器和控制面的内存被挤进交换分区，之后几分钟读回来时一卡就是几秒。

2026-11-20 03:06Z 那次更新逐秒量过（只读）：

| 时间（UTC）       | 在做什么                           | 量到的                                                                                         |
| ----------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------- |
| 03:06:46–03:06:54 | freshclam 把新库装一遍试           | 它自己多占 600 MiB，可用内存 1.8 GB → 1.25 GB                                                  |
| 03:06:54–03:07:10 | clamd 装新的一份                   | clamd 常驻 24 MiB → 970 MiB，可用内存 → 0.9 GB                                                 |
| 03:07:10 起       | clamd 放掉旧的一份（先从交换读回） | 每秒换进最多 1.6 万页，磁盘九成忙，clamd 至少 14 秒不回 PING；可用内存最低 474 MiB             |
| 03:08–03:15       | 别的服务把被换出去的内存读回来     | 数据库的 IO 等待 26%–48%；聊天服务器卡 4 秒（03:14:37–40），控制面的就绪检查那一次用了 3.7 秒 |

每天有 4–6 条请求被拖慢，最近 12 天这半小时里没有 5xx。一天里没有闲的钟点，挪更新的时刻没用。

改法是给扫描容器设 `ConcurrentDatabaseReload no`：先放旧的、再装新的，内存里只有一份。代价、为什么不给它加内存上限、为什么别关 `TestDatabases`，写在 [可观测性手册](../../docs/operations/observability.md)的“ClamAV 每天更新病毒库”。

这项设置要重建扫描容器才生效，发版部署不重建它。公开以后单独重建了一次：

- `08:46:27Z` 开始，`08:46:30Z` 新容器启动，27 秒后健康；`clamd.conf` 里这一项是 `no`，让 clamd 真扫一段字回了 `OK`，控制面健康检查通过。
- 新容器启动时正好有新的每天库（28188 → 28189），freshclam 在 clamd 起来之前就换好了，所以这次没走到“重载”那一步。
- 重建以后 clamd 常驻 952 MiB、不在交换分区里，机器可用内存约 1.0 GB。重建前后那几分钟控制面没有记下扫描失败或 5xx。
- 之后每天的更新跟着这次启动的时刻走，在 08:46 UTC 前后，每天往后挪十几秒。

新设置下的头一次每天更新是 2026-11-21 08:46:46Z（库 28189 → 28190），过后照服务器自己 15 秒一次的记录只读看了一遍（08:35–09:05Z），和 11-20 03:00–03:30Z 旧设置那一次比：

|                                  | 旧设置（11-20） | 新设置（11-21）                  |
| -------------------------------- | --------------- | -------------------------------- |
| 更新时可用内存最低               | 474 MiB         | 858 MiB                          |
| 这半小时换出去的页               | 12.2 万         | 3.1 万                           |
| 内存卡住 1% 以上的 15 秒采样     | 26 个，最高 13% | 3 个，最高 4.9%                  |
| 控制面超过半秒的请求（不算长轮询） | 有（就绪检查 3.7 秒） | 没有，也没有等数据库连接的告警 |

- freshclam 试装 9 秒，clamd 放掉旧的、装好新的到 `08:47:35Z`，前后不到 50 秒；放旧的那一份时交换分区空出 935 MiB。
- 更新完新库整个在内存里（clamd 常驻约 950 MiB），可用内存停在 0.9 GB 上下，之后十几个小时内核慢慢把它换出去、回到 1.5 GB：11-20 重建以后也是这样。这期间碰上定时备份会再低一下（对着 09:00 那一轮，`09:00:30Z` 那个 15 秒采样 723 MiB、内存卡住 4.9%，就是这半小时里最高的那一个），请求没有变慢。别的整点没有这一下，查过前 23 个小时。
- 写这一节时说“可用内存不该再掉到 800 MiB 以下”，更新本身做到了，之后那一下没做到；看的应该是请求慢不慢，这一条达到了。

这件事到这里算做完，agent-room-ops#108 上也记了。
