# Alpha 74 发布记录

[Alpha 74](https://github.com/rainyflash/agent-room/releases/tag/v0.1.0-alpha.74) 于 `2026-10-16T09:48:17Z` 公开。

- 升级序号 `74`，源码 `94bda5d4149d2e8956f98ab4d3833728203eba36`（[PR 500](https://github.com/rainyflash/agent-room/pull/500) 的合并提交）。版本 [PR 499](https://github.com/rainyflash/agent-room/pull/499) 的合并提交 `ce61a065` 做过一次候选、部署到了生产，升级维护者本机时只换了一半，被 PR 500 取代（见下面“中途停下的几次”）。
- 网页、服务器和维护者本机的 Windows 应用都已升级。
- 本版在受保护的 `release/v0.1.0-alpha.74` 分支上以锁定模式公开，是正式版，标为 Latest。

全程由编码 Agent（Claude Code）操作，实机验收的真实宿主和上一版一样用 Codex。PR 493、495、496 改了登录相关代码（控制面的桌面登录和设备注册、`crates/bridge-core/src/authorization.rs`、`tools/prodops/render.py`），所以实机验收走了一次新设备授权，维护者批准了设备码；长期验收设备换成 Alpha 74 那台。

## 用户可见的变化

### 桌面端登录一次就好

设计 [PR 492](https://github.com/rainyflash/agent-room/pull/492)，实现 PR 493–498，[设计文档](../desktop-sign-in/design.md) 的“状态”一节记着每一步。

- 新装的电脑在桌面应用里登录一次就好：聊天登录由控制面以应用服务身份替人发，不再弹 Synapse 的确认页；这台电脑的授权跟着账户登录走，不用再批准设备码，要不到时才退回设备码（PR 493–497）。
- 运行中这台电脑的授权失效（比如在别处移除了它），桌面端停下、说清原因，点“重新连接”或“重新授权这台电脑”一步连上，不再自己连回去（PR 497）。
- 故障诊断文档跟着改了说法（PR 498）。

### 其他

- 没登录时欢迎页不再一直转圈（PR 490）。
- 房间左上角直接回到房间列表，房间菜单去掉（PR 487）。
- 两个 Agent 同时进同一个私人房间时，后一个的发言级别不再被盖掉（PR 491）。
- 聊天助手平台的共享出口整段算一个来源，按来源计的名额乘上分量（PR 489）。
- Windows 上更新时，开着一遍遍调命令行的 Agent 不再让更新只换一半：换文件期间命令行和 MCP 也先挪开（PR 500）。

发行说明写了上面这些，以及装着 Alpha 68 或更新版本的桌面端开着就会提醒这一版。

桌面端、Bridge、CLI 与 MCP 同版本发布，IPC 没变（还是 `4.5`，Bridge 同时接受 `4.4`）。这一版有一个数据库迁移，按先扩表再切换的流程部署：`202610160001_desktop_computer_grants` 加一张电脑授权的表和令牌组的 `authenticated_at` 列，旧版控制面不读。新版桌面端要新版控制面才接得通对话，照常先部署服务端再发客户端。

## 中途停下的几次

### 升级本机只换了一半（第一个发布提交）

`08:34:46Z` 升级维护者本机时，静默安装器退出码 2：桌面端、Bridge、MCP 换成了新版，命令行还是 Alpha 73，挪开的旧桌面端 `agent-room-desktop.exe.old` 也留在安装目录里。

那时维护者电脑上 ChatGPT 应用里的两个 Codex 任务一直在循环调 `agent-room read`（一个是游戏项目里的房间监听脚本）。安装器的钩子结束了命令行进程、等到四个程序都能写，模板开始写文件；写到命令行之前，Agent 又起了一个 `agent-room read`，占住 `agent-room.exe`，模板写不进去就中止了。钩子换文件期间占着的标记照常起了作用：命令行在 `08:34:46Z` 拉起的桌面端看到标记就退出了。

应用内更新用的是同一个安装器，开着循环调命令行的 Agent 的人每次更新都可能碰上，所以没有手动绕过去，而是先修安装器：PR 500 让钩子像桌面端那样，把 MCP 和命令行也挪到 `.old`，结束进程前挪一次、四个进程都不在时再挪一次，装完删掉，没装成挪回原处。钩子检查加了一条：安装器还在等的时候，从安装目录启动 MCP 和命令行必须起不来；拿旧钩子跑，会放开的三个场景都失败。

接着：

1. 草稿发行改名为 `v0.1.0-alpha.74-superseded-ce61a065`（没有建过标签），本机发布目录里第一个候选的记录挪进 `alpha74/attempt-ce61a065/`，服务器上的候选目录改名为 `alpha74-attempt-ce61a065`。“升级前”的两项检查（旧客户端、公开入口）是对着 Alpha 73 服务端做的，沿用。
2. 本机装回 Alpha 73：Alpha 73 的安装器还没有这个修复，先手动把命令行和 MCP 改名挪开，再静默安装（退出码 0），装完删掉挪开的两份。桌面端随后由 Agent 拉起，Bridge 照常用保存的授权连上。
3. PR 500 的检查全绿（含 GitHub 托管 Runner 上用真实程序名跑的安装器钩子检查）以后合并，它的合并提交成为发布提交，整条链从派发开始重跑。第二次升级本机时那两个 Codex 任务照样在跑，安装一次成功。

服务端那段时间跑的是第一个候选，旧客户端照常；第二次部署前后的旧客户端检查也都通过。
