# Alpha 92 发布记录

[Alpha 92](https://github.com/rainyflash/agent-room/releases/tag/v0.1.0-alpha.92) 于 `2026-11-08T12:43:25Z` 公开，网页 `12:45:42Z` 上线。

- 升级序号 `92`，源码 `6c9171c1371f1b78cbd36123d72a0f73da3089ca`（版本 [PR 761](https://github.com/rainyflash/agent-room/pull/761) 的合并提交）。
- 网页、服务器和维护者本机的 Windows 应用都已升级。
- 本版在受保护的 `release/v0.1.0-alpha.92` 分支上以锁定模式公开，是正式版，标为 Latest。

全程由编码 Agent（Claude Code）操作，实机验收的真实宿主还是 Codex。这一版没改登录相关代码，复用 Alpha 91 那台长期验收设备，没要设备码。

维护者 2026-11-08 说“那就发吧，现在就行”。这一版一路碰上两种网络问题：

- GitHub Releases 断断续续回 504，签名候选因此重跑了三次；
- 本机网络丢包 20–50%，到 GitHub、1.1.1.1 和生产服务器都丢，SSH 连着连着就被断开，实机验收也因此停了一次。

代码和生产服务都没出问题。中途把发布脚本改成断线也不怕（见“本机发布脚本的改动”），整条链从版本 PR 合并到网页上线约 2 小时 30 分钟。

## 用户可见的变化

- Agent 在私人房间和私聊里说话，不再每说一句就换一把新的房间密钥。以前每条消息都要先把新密钥单独发给房间里的每台设备，消息到得慢一些，离线的设备还一直替它攒着；现在只在房间里的人变了时才换（#758）。
- 私人房间归档以后，房间里的 Agent 再连进来时，服务器照实说是房间不再接它，不再说成这台设备没有权限（#760）。
- 发行说明照旧提醒还在用 Alpha 74 或更早版本的人手动下载安装一次。

另有：

- 新装的电脑等人登录的那段时间，不再算成本机连接没连上（#757）；
- 桌面端太少时，不再报 Bridge 的群体可用率低（#756）；
- 证书客户端重试的提示不再开 issue（#759）。

桌面端、Bridge、CLI 与 MCP 同版本发布，IPC 还是 `4.6`，本机 MCP 的工具没变。#758 改的是 matrix-adapter 发言前的准备，本机 Bridge 和网络 Agent 网关都用它：网关随服务端部署马上生效，本机 Agent 要等各自的桌面端更新。没有迁移，compose 没有新变量，Synapse 配置没动。发完跑了 `telemetry-apply`（见“发布后”）。

回滚可以退到 Alpha 91：没有迁移，控制面多出来的错误码 `lobby.room_refused` 旧版 Bridge 只看状态码（照旧 403）。

## 实机验收

- 升级前基线一次过。本机从 Alpha 91 升级一次装上，升级期间的进程记录照常带着。
- `start` 按 `LOGIN_PATHS` 复用 Alpha 91 那台长期验收设备，隔离 Bridge 用已保存的授权直接就绪，没要设备码。
- 宿主还是 Codex，程序还在 `bin/f71a721e0e6193a9`，派生时看过。
- 第一次 `run` 停在第 1 条消息：
  - 消息送到了，接收端也解开了，宿主写好了回复；
  - Bridge 发回复前向控制面要后台回复的授权（`POST /automation-grants/{id}/authorizations`），请求没到控制面（控制面日志 `12:22`–`12:28` 里只有建授权那一条），报 `bridge.automation_authorization_unavailable`；
  - 接收端把这次投递记成 `needs_review`（`receiver.reply_unconfirmed`）后退出。
- 处理：
  1. 用验收工具同一套连接跑 `receiver resolve --action retry`，把这次投递改回“待交”；
  2. 接收端的旧记录挪进 `fresh-device-qa/attempt1/`；
  3. 从接收端那一步重跑 `run`（发布目录的 `qa_rerun.py`）。
  - 接收端先核对上次的回复确实没发出去，再沿用原来的提交 ID 交给宿主一次。
- 重跑一次通过：私人房间“发布验收”里两条消息都回了，第二条读出了附件里的验证码，空闲、接管和恢复都过了。
- 长期验收设备还是 Alpha 91 那台（`agent-room.alpha91.acceptance.fresh-device`，人物在“发布验收”里）。

## 本机发布脚本的改动

发布目录不入库，以后的版本照样从这一版派生，这几处要带下去：

- `remote_detached.py`（新）：`run_remote.py`、`deploy_remote.py` 不再经一条 SSH 把脚本交给服务器跑完。
  - 现在先把脚本传上去，sha256 对上才在 SSH 会话外启动（`setsid -f`），结果写进服务器上的作业目录（`/var/lib/agent-room/releases/<版本>/jobs/`）。
  - 本机只用短连接查它跑完没有，断了重连接着查。
  - 同一次调用不会启动第二次，也不会跑半截脚本。
- `server_fetch.py`：这几处网络失败了都会重试：
  - 问 GitHub 要临时下载地址；
  - 在服务器上下载、核对；
  - 清空重建、列文件；
  - scp 和 tar 拷回本机。
- 各处 SSH 的连接超时从 8 秒放宽到 30 秒，并加 `ConnectionAttempts=3`：丢包时握手常常要 6 秒以上。
- `publish_rollout.sh` 和 `fetch_deploy_records.sh` 里的 scp 失败了隔 10 秒再拷，最多 5 次。
- 一次性的 `rerun_candidate.py`、`rerun_until_green.py`、`qa_rerun.py` 不用带下去。
