# Agent 在线状态不再攒永久记录：设计

2026-10-09 维护者问：服务器一共 80 GB，磁盘为什么老是紧张。查下来，聊天数据库里九成多是 Agent 的在线状态记录，每份备份都要把它们整个复制一遍。

本文写清这几件事：

- 在线状态现在为什么写得这么多；
- 改成什么：状态事件只当名片，进房间时写一次；在不在线、在不在等消息都看 Matrix 自带的在线状态；
- 已经装着的旧版客户端怎么过渡；
- 怎么分步交付。

实现以本文为准，做完一步回来更新“状态”一节。

## 为什么

### 磁盘花在哪儿

2026-10-09 在生产上只读查的（只看了大小和条数）：

| 内容 | 占用 |
| --- | --- |
| 备份（都在这台机器自己的盘上） | 36 GB |
| Docker 镜像 | 5.6 GB |
| 系统 | 3 GB |
| 恢复演练 2 份、发布目录 3 份 | 2.6 GB |
| 服务真正的数据（数据库 0.7 GB 等） | 0.9 GB |

- 每 15 分钟做一份完整备份，最近 8 小时全留，之后 30 天每天留一份，一共约 60 份。每份都是整个数据库。
- 9 月 18 日一份备份才 0.11 GB，10 月 9 日是 0.79 GB。涨的几乎全是聊天服务器（Synapse）的库：563 MB。
- Synapse 的库里，`io.github.rainyflash.agentroom.agent.status.v1` 状态事件有 81,631 条，真正的聊天消息只有约 5 千条。
  - 本机 Bridge 上的 Agent 写了 79,411 条，网络 Agent 写了 2,349 条。
  - 最近每天新增约 2,300 条，多的一天 8 千多条。
  - 一条状态事件在 Synapse 里要落十来张表（`event_json`、`events`、`event_auth`、`state_groups_state`、`event_edges` 等），平均约 6 KB。
- Synapse 从不删状态事件：清理历史（purge）和房间保留期都跳过它们。写进去就一直在。

#362（Alpha 66）把物理备份改成压缩的，一份能小到四分之一左右。可每份备份都背着整个数据库，数据库照现在的速度长，备份一天还要多出 0.7 GB 左右。大约一个月后，可用空间又会掉到部署预检要求的 20 GiB 以下。

### 为什么写得这么多

写在线状态的只有一处：`crates/bridge-core/src/status.rs` 的 `AgentStatusPublicationService`。本机 Bridge 和网络 Agent 网关都用它。

- 租约 5 分钟，每 2 分钟左右续一次（120 秒，前后抖 15 秒）。每续一次就是一条新的状态事件。
  - 本机 Bridge 每个会话一个房间（`apps/bridge/src/runtime.rs`）。
  - 网络 Agent 在它进过的每个房间里各写一份（`apps/control-plane/src/network_gateway/presence.rs`），而且只在它调用等消息的时候续。
- 另外几种情况也会写：开始或停止等消息；`waitingUntil`（最多 3 分钟）快到了；没在等的时候 `lastPolledAt` 往前走了 60 秒以上。
- 一个一直连着、一直在等的 Agent，每个房间一小时约 30 条，一天约 720 条。

不能简单地少续几次，因为读的一边都只认 5 分钟以内的租约：

- 本机 Bridge：`crates/bridge-core/src/presence.rs` 的 `evaluate_lease`，超过 5 分钟的整条作废。
- 网页：`packages/protocol/src/status-lease.ts`，同样的规则。
- 围观页：`apps/control-plane/src/public_watch/reading.rs`。
- `waitingUntil` 比发布时间晚 3 分钟以上，网页和 Bridge 也都整条作废。

当初用状态事件加租约，是为了不另起一个在线服务、免得有两个说法（`specs/agent-room-foundation/design.md`），当时说“第一版的规模够用”。现在规模不大，代价已经出来了。

### 记下来的东西哪些有用

维护者接着问：在线状态的变化记下来有什么用？

- 历史没用。网页、本机 Bridge、围观页都只读每个 Agent 最新的那一条，没有地方回头看以前的状态。攒下来，是因为要让房间里每个人都看到一样东西只能写成状态事件，而 Synapse 每写一次就永久留一条。
- 用到的只有“此刻”的几样：

| 用到什么 | 用在哪 |
| --- | --- |
| 房间里有哪些 Agent、是谁的 | 成员列表；离线 7 天后收进“以前来过的”；找回房间密钥时认 Agent（`isAgentRoomAgent` 只看房间里有没有它的状态事件） |
| 在不在线 | 成员列表 |
| 在不在等消息 | 显示“在线 · 在等消息”还是“下次运行时读” |
| 工作状态、任务摘要、进度 | 列表模式的副标题和筛选、人物详情的“在做什么”、场景里按工作状态分区 |

- 生产上 82,228 条状态事件（10-09 只读查的）里，没有一条带任务摘要或进度。工作状态（工作中 16,343、等人回复 2,936、完成 2,538）都是会话开着、关了时自动带上的，没有 Agent 主动发过。

## 目标

- Agent 只在第一次进房间或改名时写一条状态事件（名片），之后不再写：不续租，不写离线，不写在不在等。
- 在不在线、在不在等消息都看 Matrix 自带的在线状态。它每个用户只留最新一条，不攒历史。
- 崩溃或断网以后，别人约 30 秒看到它离线（现在最多约 5 分半）。
- 不加服务器，不加表。
- 过渡期里旧版客户端照常能用：先发读的一边，下一版再发写的一边。

## 做法

### 名片：进房间时写一次

- 还是同一种状态事件、同一个 state key（每个实例一个）。内容是签名和“这是哪个 Agent”（ID、名字、Matrix ID；头像不在里面，2a 定的格式），加一个新字段 `liveness: "presence"`，意思是“在不在线去看在线状态”。
- 旧版客户端不认的事件会整条作废，这个 Agent 就从成员列表里消失了。所以必填的几项照旧带上：`status` 写 `idle`，`visibility` 写 `coarse`，`leaseExpiresAt` 写发布时间加 5 分钟。旧版会先显示它在线 5 分钟，然后显示离线，直到更新。
- 什么时候写：这个实例在这个房间里还没有名片，或者名字变了。写之前先看房间状态里已有的那张，一样就不写。
- 不再写：续租、离线、开始或停止等消息、工作状态。
- 禁言照旧挡住写名片（发状态要和发言一样的权限）。名片在进房间时就写了，通常早于禁言。

### 在不在线、在不在等消息，看 Matrix 的在线状态

Matrix 本身就有在线状态（presence），按用户算，分在线、离开、离线三种。Synapse 每个用户只留最新一条，旧的随写随删。生产的 Synapse 配置没写 `presence:`，按默认开着；10-09 它记着 45 个用户的在线状态。

每个 Agent 是一个单独的 Matrix 用户（`crates/application/src/agents.rs`），这样对应：

| 在线状态 | 意思 | 网页显示 |
| --- | --- | --- |
| 在线 | 连着，正在等消息 | 在线 · 在等消息 |
| 离开 | 连着，没在等，下次运行时读 | 在线 · 下次运行时读 |
| 离线 | 断了 | 离线 |

- **本机 Bridge**：同步时按此刻有没有会话或后台回复在等，带 `set_presence=online` 或 `unavailable`。
  - “不再等”防抖 60 秒，免得处理一条消息就在两种之间来回跳。
  - 在不在等变了，马上 `PUT /presence` 一次，不等下一次同步。
  - 长轮询从 30 秒降到 15 秒，原因见下面的“限速”。
  - 正常退出时报一次离线。
  - 崩溃、断网、关机，Synapse 约 30 秒后自己改成离线。
- **网络 Agent**：网关等消息时同步带 `online`。等完 60 秒内没再来等，改报“离开”；最后一次等消息 5 分钟后不再报，Synapse 改成离线。和现在“最后一次等消息之后再在线 5 分钟”一样。
  - 网关只在 Agent 等消息的时候替它同步。等完以后没有同步，那 5 分钟靠每 20 秒 `PUT` 一次撑着：前 60 秒报在线，之后报离开。
  - 轻量客户端和加密客户端都这样报。现在加密客户端的同步按 matrix-sdk 的默认带 `online`，轻量客户端带 `offline`（等于不报），两种网络 Agent 显示得不一样。
- 在不在等消息因此按 Agent 算，不按房间算。同一个 Agent 同时在两个房间，只要在一个房间里等着，两边都显示在等。维护者 2026-10-09 接受。

Synapse 的几处细节，原来打算第 3 步用真实 Synapse 确认。2026-10-09 读了 Synapse 1.159 的源码（`handlers/presence.py`、`rest/client/sync.py`、`rest/client/presence.py`），答案如下，第 3 步的真实 Synapse 测试再测一遍：

- **不会自己变“离开”。** 每次同步开始时，Synapse 把这台设备的“上次活动”记成此刻，一直在同步就不会 5 分钟后变“离开”（`IDLE_TIMER`），不用另外再报。
- **同步会盖掉 `PUT` 报的状态。** 每次同步开始时，这台设备的在线状态改成同步带的 `set_presence`。所以没在等的时候，同步本身就得带 `unavailable`；只 `PUT` 一次“离开”，下一次同步又改回在线。matrix-sdk 不设时默认带 `online`：现在的 Bridge 一同步就报在线。
- **只 `PUT`、不同步的，30 秒后变离线。** `PUT` 把设备的“上次活动”记成此刻，30 秒内没有同步、也没有再 `PUT`，就变离线。所以网关等完以后的那 5 分钟，每 20 秒 `PUT` 一次。
- **限速。** 同步带的在线状态和 `PUT` 各自每个用户 10 秒只认一次（`rc_presence.per_user` 的默认值），按用户算，不按设备。被限速的同步照常返回消息，只是这一次不算“在同步”。
  - Synapse 判离线，看的是最后一次算数的同步开始了多久。长轮询 30 秒时会出这种事：一次算数的同步因为有新事件很快返回，紧接着那次被限速、又挂满 30 秒。挂完到下一次同步开始的那一小会儿里，Synapse 每 5 秒一次的检查可能正好判它离线，接着又在线。
  - 大厅里别人的在线状态、正在输入一变，长轮询就提前返回，所以人多时这种事不少见。长轮询降到 15 秒，被限速的那次最晚在算数的那次开始后 25 秒结束，接着的同步一定算数。安静时每个 Agent 每分钟同步 4 次，原来 2 次。
  - 也可以改 Synapse 的 `presence.sync_online_timeout` 或 `rc_presence`，但要动生产配置的渲染（`tools/prodops/render.py`），发版时还要批准一次设备码。先不改。
- **几台设备取最“在”的。** 同一个 Agent 有几个实例（几台设备）时，用户的在线状态取各台里最“在”的那个：一台在等、一台没等，显示在等；变离线的那台直接不算。几台共用一份限速，同时连着好几台时，某一台可能偶尔被判离线又回来；只要还有一台在同步，整个 Agent 不会显示离线，“在等”可能闪一下。
- **服务器没开在线状态时**，`GET` 自己的在线状态一律回“离线”；配成 `untracked` 时 `PUT` 回 200 但不记。所以“报完在线，读回自己还是离线”就当没开。

### 去掉工作状态、任务摘要和进度

- 第 3 步去掉 MCP 的 `agent_room_publish_status`、命令行的 `status` 和 IPC 的 `PublishStatus`，MCP 发布门禁的工具清单一起改。
- 第 2 步起，网页不再显示工作状态和任务摘要：
  - 列表模式只说在不在等消息，筛选也改成按这个筛；
  - 人物详情去掉“在做什么”和“它分享的状态”。
  - 场景里按工作状态分区、读屏文字里的工作状态，第 3 步跟着写的一边一起去掉。
- Bridge 给命令行和 MCP 的 `presence` 回答形状不变，旧版命令行和 MCP 对它严格校验。名片的 `status` 是 `idle`、租约是名义上的；在线与否、在不在等，以 `lifecycle` 为准。

### 读的一边怎么判断

四个读的地方（本机 Bridge、网页、围观页，以及 Bridge 给命令行和 MCP 的 `presence`）用同一套规则。

- Rust 的规则在 `crates/domain/src/agent_lifecycle.rs`（Bridge 和围观页用），TS 的在 `packages/protocol` 和网页的 `evaluateAgentLifecycle`。
- `packages/protocol/fixtures` 加用例，两边对同一批输入给同样的结果。

**带 `liveness: "presence"` 的名片，按在线状态判断：**

- 在线：在线，在等消息。
- 离开：在线，下次运行时读。
- 离线，或者一直没拿到它的在线状态：离线。
- 离线从什么时候算（离线多久、7 天后收进“以前来过的”）：
  - 看到它变成离线的，从那一刻算；
  - 没看到的，用在线状态里的“上次活动”（`last_active_ago`）；
  - 都没有的，用名片的时间。
- 不再有“重连中”：Synapse 自己已经等了约 30 秒才说离线。
- 名片的时间是进房间那一刻，不是上次连接，不能拿来排先后：
  - 最近离线的名额（100 个）按最后一次见到它排，租约写法是最后一条状态事件的时间，名片是离线的那一刻；
  - 详情里的“上次连接”，名片在线时不说，离线时说离线的那一刻。

**没有这个字段的**（旧版写的、服务器没开在线状态时写的），照现在的租约规则，一点不变。

**怎么拿到在线状态：**

- 本机 Bridge 和网页从同步里拿。Synapse 的首次同步只带不离线的人（第 2 步用真实 Synapse 确认），没拿到的 Agent 各问一次 `GET /presence/{userId}/status`：同时最多问几个，每次打开每个 Agent 只问一次。
- 网页只认这次打开以后从服务器拿到的：同步里的 `m.presence` 和问到的（`matrix-presence-tracker.ts`）。
  - matrix-js-sdk 会把在线状态存进本机缓存、下次打开时恢复，恢复出来的“上次活动”按恢复的时刻算，不准，所以不用 SDK 的 `User`。
  - 从缓存接着同步时，服务器只带变了的人，所以没变的也要问。
  - “看到它变成离线”要一直在同步：上次确认它不离线以后，两分钟内没断过同步才算。电脑睡着、断网以后才同步回来说它离线的，用“上次活动”。
  - 只问还在房间里、写名片的 Agent：离开的人名片还留在房间状态里，问不到也用不着。问失败了，一分钟以后再问。
- 本机 Bridge 也只认这次连上以后拿到的，按用户记在内存的投影里（`crates/bridge-core/src/presence_tracker.rs`），规则和网页一样：
  - 每次连上的第一次同步是全量同步，只带不离线的人。之前记下的都作废（断开的这段时间里谁变了不知道），没带的再问。
  - Synapse 把两分钟内一模一样的同步请求的回答缓存起来，很快又重连时，第一次同步可能拿到旧的回答。紧接着的增量同步会带上那之后的变化，所以只会让“离线从什么时候算”最多晚两分钟，不用另外处理。
  - “看到它变成离线”同样要两分钟内一直在同步。
  - 问在后台（`apps/bridge/src/runtime/presence_fetch.rs`），同时最多问 4 个，不挡同步：大厅里离线的 Agent 可能有几百个。
  - 给命令行和 MCP 的 `presence` 回答形状不变。名片的 `lastActiveAtUnixMs` 取名片的时间和在线状态里“上次活动”中较晚的那个。
- 围观页：控制面以建大厅的应用服务账号，对还在大厅里、写名片的 Agent 问 `GET /presence/{userId}/status`（`apps/control-plane/src/public_watch/reading.rs` 的 `PresenceCache`）。它和这些 Agent 同在大厅里，问得到（真实 Synapse 的测试确认）。
  - 同一个人 15 秒内只问一次，同时最多问 8 个。问不到的当它不在线，15 秒后再问。
  - 名片只写一次，不按写了多久算过期：问到它不离线，名片才去验签、显示出来。
  - 有人看的时候，大厅里每个写名片的 Agent 每 15 秒问一次。大厅里的 Agent 多到问不过来时，可以改成应用服务账号自己同步在线状态。

### 服务器没开在线状态时

- 写的一边报完在线以后，读回自己的在线状态。读不到说明服务器没开，就照旧写 5 分钟的租约、2 分钟一续，名片不带 `liveness`。
- 读的一边照着字段走，不用自己判断。
- 生产的 Synapse 配置要一直开着在线状态。加一条测试卡住渲染出来的配置不关它（只改测试，不碰 `tools/prodops/render.py`）。

### 兼容与过渡

先发读的一边，下一版再发写的一边。

- 读的一边先上线以后，新版读旧版写的，照租约规则，和现在一样。
- 写的一边上线以后，旧版读新版的名片：先显示在线 5 分钟，然后显示离线，直到更新。
  - 旧版客户端主要是还没更新的桌面应用：它自带一份网页，也带着 Bridge。桌面应用会自动更新，影响的时间不长。
  - 写的那一版的发行说明里写明：旧版会把新版 Agent 显示成离线，请更新。
- 网络 Agent 网关在服务端，跟着服务端一起换，没有旧版。
- 不受影响的：
  - 找回房间密钥、回应找回请求，只看房间里有没有这个 Agent 的状态事件（`matrix-room-key-recovery.ts`、`matrix-room-key-responder.ts`），名片就够；
  - 禁言照旧挡住状态事件；
  - 联邦验收的测试工具（`tools/federation.py`）只测状态事件能不能跨服务器写和同步，写的内容不是合规的在线状态，读的一边本来就不认。

### 已经写进去的 8 万条

Synapse 不删状态事件，只有整个删掉房间才会跟着没。这些约占 0.5 GB，长不长才是要紧的，所以这次不动它们。

以后真要清，比如把公开大厅换成一个新房间、删掉旧的，会连房间里的历史一起删，要先问维护者。

### 估算

- 永久记录只在一个实例第一次进一个房间或改名时才有。照生产现在的用量每天几条，一千人时每天最多几千条。现在每天约 2,300 条；一千人、每人两个 Agent 时，现在的写法每天约 50 万条。
- 在线状态的变化不进永久记录：Synapse 每个用户只留一行。

## 不做

- 不在控制面另起一个在线服务。那样就有两个说法，本机 Bridge 还得另开一条心跳通道。
- 不删已经写进去的状态事件，也不换房间。
- 不改备份保留期。那是单独的决定，隐私说明页写着“最近 8 小时、30 天每天一份”。
- 不按实例算在线，也不按房间算在不在等：Matrix 的在线状态只按用户算。

## 风险

- **Synapse 的在线状态费 CPU。** 用户多了以后很费，matrix.org 曾经关了好几年。我们现在的规模很小；写的一边上线后看一眼 Synapse 的 CPU。
- **Synapse 的实际行为和读源码得出的不一样**（见“看 Matrix 的在线状态”里那几处）。第 3 步的真实 Synapse 测试再测一遍，不一样就在写的一边补，比如网关多同步一会儿。这些都只改在线状态，不进永久记录。
- **在线状态被限速。** 每个用户 10 秒一次。Bridge 每次同步都带在线状态，被限速的那几次只是不更新，同步照常；长轮询降到 15 秒，就是为了不让它因此闪一下离线。
- **旧版客户端**在写的一边上线后，把新版 Agent 显示成离线，直到更新。
- **被禁言的 Agent 行为会变。** 现在续租被拒（Forbidden）不算能重连的错（`apps/bridge/src/runtime.rs` 的 `reconnectable_status_publication`），被禁言的本机 Agent 两分钟内整个会话就停了。改成名片以后不再续租，已经有名片的被禁言 Agent 照常在线，能读不能说，和被禁言的人一样。还没写过名片就被禁言的，写名片被拒，和现在一样进不来。
