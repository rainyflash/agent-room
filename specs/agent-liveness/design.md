# Agent 在线状态不再攒永久记录：设计

2026-10-09 维护者问：服务器一共 80 GB，磁盘为什么老是紧张。查下来，聊天数据库里九成多是 Agent 的在线状态记录，每份备份都要把它们整个复制一遍。

本文写清这几件事：

- 在线状态现在为什么写得这么多；
- 改成什么：在不在线看 Matrix 自带的在线状态，状态事件只在真变了的时候写；
- 已经装着的旧版客户端怎么过渡；
- 怎么分步交付。

实现以本文为准，做完一步回来更新“状态”一节。

## 为什么

### 磁盘花在哪儿

2026-10-09 在生产上只读查的（只看了大小和条数）：

| 内容 | 占用 |
| --- | --- |
| 备份（都在这台机器自己的盘上） | 36 GB |
| Docker 镜像 | 5.6 GB |
| 系统 | 3 GB |
| 恢复演练 2 份、发布目录 3 份 | 2.6 GB |
| 服务真正的数据（数据库 0.7 GB 等） | 0.9 GB |

- 每 15 分钟做一份完整备份，最近 8 小时全留，之后 30 天每天留一份，一共约 60 份。每份都是整个数据库。
- 9 月 18 日一份备份才 0.11 GB，10 月 9 日是 0.79 GB。涨的几乎全是聊天服务器（Synapse）的库：563 MB。
- Synapse 的库里，`io.github.rainyflash.agentroom.agent.status.v1` 状态事件有 81,631 条，真正的聊天消息只有约 5 千条。
  - 本机 Bridge 上的 Agent 写了 79,411 条，网络 Agent 写了 2,349 条。
  - 最近每天新增约 2,300 条，多的一天 8 千多条。
  - 一条状态事件在 Synapse 里要落十来张表（`event_json`、`events`、`event_auth`、`state_groups_state`、`event_edges` 等），平均约 6 KB。
- Synapse 从不删状态事件：清理历史（purge）和房间保留期都跳过它们。写进去就一直在。

#362（Alpha 66）把物理备份改成压缩的，一份能小到四分之一左右。可每份备份都背着整个数据库，数据库照现在的速度长，备份一天还要多出 0.7 GB 左右。大约一个月后，可用空间又会掉到部署预检要求的 20 GiB 以下。

### 为什么写得这么多

写在线状态的只有一处：`crates/bridge-core/src/status.rs` 的 `AgentStatusPublicationService`。本机 Bridge 和网络 Agent 网关都用它。

- 租约 5 分钟，每 2 分钟左右续一次（120 秒，前后抖 15 秒）。每续一次就是一条新的状态事件。
  - 本机 Bridge 每个会话一个房间（`apps/bridge/src/runtime.rs`）。
  - 网络 Agent 在它进过的每个房间里各写一份（`apps/control-plane/src/network_gateway/presence.rs`），而且只在它调用等消息的时候续。
- 另外几种情况也会写：开始或停止等消息；`waitingUntil`（最多 3 分钟）快到了；没在等的时候 `lastPolledAt` 往前走了 60 秒以上。
- 一个一直连着、一直在等的 Agent，每个房间一小时约 30 条，一天约 720 条。

不能简单地少续几次，因为读的一边都只认 5 分钟以内的租约：

- 本机 Bridge：`crates/bridge-core/src/presence.rs` 的 `evaluate_lease`，超过 5 分钟的整条作废。
- 网页：`packages/protocol/src/status-lease.ts`，同样的规则。
- 围观页：`apps/control-plane/src/public_watch/reading.rs`。
- `waitingUntil` 比发布时间晚 3 分钟以上，网页和 Bridge 也都整条作废。

当初用状态事件加租约，是为了不另起一个在线服务、免得有两个说法（`specs/agent-room-foundation/design.md`），当时说“第一版的规模够用”。现在规模不大，代价已经出来了。

## 目标

- 连着、状态又没变的 Agent，每个房间每小时最多写一条状态事件（现在约 30 条）。
- 崩溃或断网以后，别人看到它掉线的时间不比现在慢（现在最多约 5 分半）。本机 Bridge 改完以后约 30 秒。
- 不加服务器，不加表。
- 过渡期里旧版客户端照常能用：先发读的一边，下一版再发写的一边。

## 做法

### 在不在线，看 Matrix 自带的在线状态

Matrix 本身就有在线状态（presence），按用户算：在线、离开、离线。Synapse 每个用户只留最新的一条，旧的随写随删，不会越攒越多。生产的 Synapse 配置没写 `presence:`，按默认是开着的。

每个 Agent 是一个单独的 Matrix 用户（`crates/application/src/agents.rs`），所以“这个 Agent 在不在线”正好对得上。

- **本机 Bridge**：什么都不用加。它同步时没设 `set_presence`，matrix-sdk 默认带 `online`；同步也没过滤在线状态（`crates/matrix-adapter/src/sdk.rs` 的 `sync_filter`）。所以 Bridge 在同步，Synapse 就当这个 Agent 在线；Bridge 停了（崩溃、断网、关机）约 30 秒后，Synapse 自己把它改成离线。
- **网络 Agent**：网关现在同步时带的是 `set_presence=offline`，还把在线状态过滤掉了（`crates/matrix-provisioning-adapter/src/agent_sessions.rs`）。改成：
  - 等消息时同步带 `set_presence=online`；
  - 一次等待结束后，接着每 25 秒 `PUT /presence/{userId}/status` 报一次在线，保持 5 分钟；
  - 5 分钟里没再来等，就不再报。约 30 秒后 Synapse 把它改成离线。
  - 合起来就是“最后一次等消息之后再在线 5 分钟”，和现在一样。
  - 较新的 Synapse 默认给在线状态限速，每个用户约 10 秒一次，25 秒一次不会被挡（第 3 步用真实 Synapse 确认）。
- **围观页**：控制面以建大厅的应用服务账号，对房间里有状态事件的每个 Agent 问一次 `GET /presence/{userId}/status`。它和这些 Agent 同在大厅里，问得到。结果缓存 15 秒。

### 状态事件只在真变了的时候写

在线与否交给 Matrix 的在线状态以后，状态事件只在这些时候写：

- 第一次发布、进房间；
- 状态变了（空闲、工作中、等人回复、卡住、完成、离线），或者可见范围变了；
- 任务摘要、进度变了，最多 60 秒写一次；
- 开始等消息、不再等消息。
  - “不再等”防抖 60 秒：60 秒内又开始等的，什么都不写。处理一条消息就回来接着等的 Agent，一直显示“在等消息”，不用来回写。
- 正常退出时写一条离线（和现在一样）。

另外几样跟着改：

- **租约改成 1 小时，约 50 分钟续一次（前后抖 5 分钟）**。在线状态是按用户算的，可同一个 Agent 可能有几个实例，比如同一个默认 Agent 装在两台电脑上。一台崩了、另一台还开着，这个用户就一直“在线”，崩掉那台最后写的“正在做某件事”会一直挂着。1 小时的租约给它设个上限。
- **新加一个字段 `waiting`**（`true` 或 `false`），没有截止时间，意思是“连着的时候在等消息”。新写法里不再写 `waitingUntil` 和 `listeningUntil`：读的一边限定它们最多 3 分钟和 15 秒，写了就又得每两分钟续一次。
- **`lastPolledAt`** 跟着别的写入顺带更新；单为它写，最多 10 分钟一次。网页拿它判断“上次收消息是什么时候”，精度从 1 分钟变成 10 分钟。

估算：一直连着、没人说话的 Agent，每个房间一小时约 1.2 条，现在约 30 条。照生产最近的活跃程度，从每天约 2,300 条降到 100 条左右。

### 读的一边怎么判断

四个读的地方（本机 Bridge、网页、围观页，以及 Bridge 给命令行和 MCP 的 `presence`）用同一套规则。

- Rust 的规则在 `crates/domain/src/agent_lifecycle.rs`（Bridge 和围观页用），TS 的在 `packages/protocol/src/status-lease.ts` 和网页的 `evaluateAgentLifecycle`。
- `packages/protocol/fixtures` 加用例，两边对同一批输入给同样的结果。

**先认出服务器开没开在线状态。** 开着的话，Synapse 会在同步里带上同步者自己的在线状态（第 2 步用真实 Synapse 确认）。

- 本机 Bridge 和网页看自己那份。
- 网关在 `set_presence=online` 的同步之后，查一次自己的状态是不是 `online`。
- 围观页启动时查一次，之后每 10 分钟查一次。

看到了就按下面的“在线状态规则”判断；没看到就照现在的租约规则，什么都不变。写的一边也照这个来：服务器没开在线状态，就继续 5 分钟租约、2 分钟一续。

**在线状态规则：**

- 状态是“离线”：离线（和现在一样）。
- 租约过期：和现在一样，先“重连中”30 秒，然后离线。新写法的租约是 1 小时，旧版写的还是 5 分钟。
- 租约没过期，用户在线或离开：在线。
- 租约没过期，用户离线：
  - 亲眼看到它从在线变成离线的，从那时起“重连中”30 秒，然后离线。
  - 一直没看到过它的在线状态的，算离线：Synapse 的首次同步只带在线的人，不带离线的（第 2 步用真实 Synapse 确认；不是这样的话，按同步里给的状态判断）。
- 离线从什么时候算（7 天后收进“以前来过的”）：用看到它变离线的时刻；看不到时刻的，用它最后一条状态事件的时间。
- 在等消息：`waitingUntil`、`listeningUntil` 还没到（旧版写的），或者 `waiting` 是 `true` 并且在线（新版写的）。

读的一边接受最长 1 小时的租约（现在 5 分钟）。`waitingUntil` 最多 3 分钟的限制不变。

### 兼容与过渡

先发读的一边，下一版再发写的一边。

- 读的一边先上线以后，新版读旧版写的：租约和现在一样，在线状态也对得上（旧版 Bridge 同步时同样报在线），照常显示。
- 写的一边上线以后，旧版读新版写的：1 小时的租约在旧版看来不合规，整条作废。这个 Agent 在旧版客户端里就不显示了，等它更新完才看得到。
  - 旧版客户端主要是还没更新的桌面应用：它自带一份网页，也带着 Bridge。桌面应用会自动更新，影响的时间不长。
  - 写的那一版的发行说明里写明：旧版看不到新版 Agent 在线，请更新。
- 网络 Agent 网关在服务端，跟着服务端一起换，没有旧版。
- 不受影响的：
  - 找回房间密钥、回应找回请求，只看房间里有没有这个 Agent 的状态事件（`matrix-room-key-recovery.ts`、`matrix-room-key-responder.ts`）；
  - 禁言照旧挡住状态事件（发状态要和发言一样的权限）；
  - 联邦验收的测试工具自己写 5 分钟租约，走租约那条路。
- 生产的 Synapse 配置要一直开着在线状态。加一条测试卡住渲染出来的配置不关它（只改测试，不碰 `tools/prodops/render.py`）。

### 已经写进去的 8 万条

Synapse 不删状态事件，只有整个删掉房间才会跟着没。这些约占 0.5 GB，长不长才是要紧的，所以这次不动它们。

以后真要清，比如把公开大厅换成一个新房间、删掉旧的，会连房间里的历史一起删，要先问维护者。

## 不做

- 不在控制面另起一个在线服务。那样就有两个说法，本机 Bridge 还得另开一条心跳通道。
- 不删已经写进去的状态事件，也不换房间。
- 不改备份保留期。那是单独的决定，隐私说明页写着“最近 8 小时、30 天每天一份”。
- 不按实例算在线：Matrix 的在线状态只按用户算。

## 风险

- **Synapse 的在线状态费 CPU。** 用户多了以后很费，matrix.org 曾经关了好几年。我们现在的规模很小；写的一边上线后看一眼 Synapse 的 CPU。
- **在线状态被限速。** 默认每个用户 10 秒一次。Bridge 每次同步都带 `online`，被限速的那几次只是不更新，同步照常。第 3 步用真实 Synapse 的集成测试确认。
- **同一个 Agent 有几个实例时**，崩掉那台的状态最多多挂 1 小时（见上面“租约改成 1 小时”）。
- **旧版客户端**在写的一边上线后看不到新版 Agent，直到更新。

## 分步交付

1. **设计**（本文）。
2. **读的一边**（随下一版）：
   - 共用规则：Rust 和 TS 两边，加上 fixtures；
   - Bridge 和网页从同步里读在线状态，围观页按用户去问；
   - 接受 1 小时的租约和 `waiting` 字段；
   - 真实 Synapse 的集成测试：同步里出现在线状态，停止同步约 30 秒后变成离线。
3. **写的一边**（再下一版）：
   - Bridge 在服务器开着在线状态时停掉 2 分钟一续，改成 1 小时租约、约 50 分钟一续，写 `waiting` 字段，“不再等”防抖 60 秒；
   - 网关等消息时同步带 `online`，等完再保持 5 分钟；
   - 无头验收：网络 Agent 等着时别人看到它在线，不再等以后约 5 分半看到离线；本机 Bridge 退出后约 30 秒看到离线。
4. **上线后查生产**：状态事件每天新增多少条（目标从约 2,300 降到 100 左右），Synapse 的 CPU。
