# 新加入的 Agent 读到加入前的消息

这是[找回解不开的历史消息](./design.md)的第二期，沿用它的协议，把“请对方重发自己建的房间密钥”从“人向 Agent 要”扩到“Agent 向 Agent、向人要”。

## 背景

- 私人房间按 `private_chat` 预设创建，历史可见性是 `shared`：成员能看到房间的全部历史，包括自己加入之前的。
- 但房间是端到端加密的。Agent 加入之前的消息，用的 Megolm 会话没有发给它的设备，它解不开。Bridge 把这些事件记成“隔离事件”（`message_sync_issue`，原因 `undecryptable`），Agent 读消息时看不到它们，也就没有加入前的上下文。
- 维护者本机的实际数据：9 月 28 日新建的两个人物，第一次同步就分别有 7 条和 3 条解不开，都是加入前的消息。
- 2026-09-29 维护者决定：新请进房间的 Agent，其他 Agent 的旧消息和人的旧消息都要能读到，和房间“成员可看全部历史”的设置一致。

## 目标

- 本机 Bridge 上的人物同步到解不开的消息时，请发这条消息的那台设备重发它建的房间密钥。发送方可以是 Agent（本机 Bridge 或网络 Agent），也可以是人的网页端、桌面端。
- 收到后导入，把之前隔离的这些消息重新读出来，放回 Agent 消息记录里原来的位置。
- 人的设备当时不在线也没关系：请求在服务器上排队，等它上线同步到就回答。

## 不做

- 仍然只重发自己这台设备建的会话，不替别人转发。人换过设备、原来那台已经注销的，它建的会话就找不回来。
- 不给不在房间里的、不由主人签名的设备；房间历史不对成员开放（`joined`、`invited`）时不给。
- 只做本机 Bridge 上的人物。网络 Agent 不做：它的加密存储在服务器上，请来加入前的房间密钥，服务器就能读到加入前的消息（维护者 2026-10-05 定，见状态）。
- 人与人之间不管：别人的客户端不认识这套请求。

## 协议

沿用第一期的两个 to-device 事件，不加字段：

- 请求 `io.github.rainyflash.agentroom.room_keys.request.v1`；
- 应答 `io.github.rainyflash.agentroom.room_keys.v1`。

两头的规则和第一期一样：只认经 Olm 加密送达、发送设备由主人签名的消息；应答里每个会话的 `sender_key` 必须就是应答的这台设备。

## Agent 这边（matrix-adapter 与 Bridge 核心）

**发现。** 同步和补缺口时，遇到解不开的加密事件（仍是 `m.room.encrypted`），记下房间、发送者、发送设备（加密内容里的 `device_id`）和会话 ID。

- 发送者不限于 Agent：人发的也要。第一期网页端只向带在线状态事件的 Agent 请求，这里不看。
- 按房间、发送者和发送设备攒几秒合成一条请求。同一个会话一小时内只请求一次。
- 加密内容里没有 `device_id` 时，发给这个用户的每台设备。

**请求。** 用 `Encryption::encrypt_and_send_raw_to_device` 发给那台设备。

- 没有能用的 Olm 会话时，SDK 先领对方的一次性密钥建一条。
- 等应答的请求记在内存里，保留 7 天：人的设备可能过几天才上线。
- Bridge 重启会丢掉这些记录。所以上线后第一次同步时，对存储里仍是“解不开”的隔离事件用到的会话（最近的 500 个）重新请求一次。断线重连也会走这一步，同一个 Bridge 进程里一小时内不重复请求。

**导入。** 应答必须全部满足，有一条不满足就整条丢掉：

1. 经 Olm 加密送达，发送设备可以确定；
2. 是我们 7 天内发给这台设备的请求，`roomId` 与请求一致，每个 `sessionId` 都在请求里；
3. 发送设备由主人签名，它的 Curve25519、Ed25519 与应答里的 `senderKey`、`senderEd25519Key` 一致。

满足的拼回房间密钥导出格式，写成一份临时的加密导出文件，用 `Encryption::import_room_keys` 导入。第一期 Agent 这边是导出成文件再解开，这里反过来。

**信任。** Bridge 只把“发送设备由主人签名”的加密消息当成可信，其余隔离。

- 真实 Synapse 测试表明，matrix-sdk-crypto 0.18 对导入的会话一律判“来源不安全”（`InsecureSource`）：它认为导入的密钥没有“会话确实由那台设备建”的证明（`Device::is_owner_of_session` 对导入的会话总是否）。
- 我们的应答恰好带着这个证明：它经 Olm 从那台设备送来，设备由主人签名，应答里的 Curve25519、Ed25519 与这台设备一致。所以 matrix-adapter 记下每个凭核对过的应答导入的会话是哪台设备重发的。
- 重读时，SDK 判“来源不安全”、而会话在这份记录里的事件：发送者就是那台设备的主人、会话的 Curve25519 就是那台设备的，而且那台设备此刻仍由主人签名、主人的身份没在核对过后换过，就当作可信。别的“来源不安全”照旧隔离。
- 这份记录只在内存里，重读就发生在导入之后。Bridge 重启后重新请求、对方再次应答时会重新记下（即便 SDK 因已有这个会话而没有再导入）。
- 如果 Agent 之前已经经 Olm 收到过同一个会话（加入后对方继续用它发消息），导入的更早序号会并进原有会话，SDK 保留原来的信任，不需要这份记录。

**重读。** 导入后通知 Bridge 核心：新导入了哪些会话。

- 隔离“解不开”的事件时，存储按本机观察顺序给它预留一个序号，并记下它的会话、发送者和发送设备。
- Bridge 核心每轮同步后取走新导入的会话，从 `message_sync_issue` 取出用到它们、原因仍是“解不开”的事件，按事件 ID 重新读取（`/rooms/{roomId}/event/{eventId}`）、解密，走和同步相同的校验。
- 读出来的消息写在预留的序号上，正好是原来的位置，再删掉对应的隔离记录。解开了但签名不对之类的，改记新原因；解开了但不是消息的，删掉记录。
- 仍然解不开的保持隔离，等下一次导入。暂时读不到的（网络、限流），会话留到下一轮再读。
- 重读出来的消息排在 Agent 已经读过的消息之间，收件箱按“某条之后”取消息，不会把它们当新消息再推一遍，免得 Agent 把几天前的话当成刚收到的去回。
- 找回的旧修订写在它原来的位置；这条消息已经换上更新的修订时，不用旧的覆盖回去。
- 这个功能上线前记下的隔离事件没有预留序号，也没记会话，找不回来。

## 人这边（网页端与桌面端）

**应答。** 监听 `room_keys.request.v1`，只看经 Olm 加密送达的。请求必须全部满足：

1. 请求者此刻在房间里，而且是 Agent Room 的 Agent（房间里有它发的在线状态事件）；
2. 请求设备由主人签名，它的 Curve25519 与 Olm 送达信息里的一致；
3. 房间历史对成员开放（`shared` 或 `world_readable`）；
4. 按请求设备和房间十分钟答一次，这台设备每分钟最多答 20 次。

**导出。** 只重发这台设备自己建的会话：

- 从 SDK 导出房间密钥，只取这个房间里 `sender_key` 是本机 Curve25519、会话 ID 在请求里的；
- 每条应答最多 20 个会话，多了分几条发。

**回发。** 用 `CryptoApi.encryptToDeviceMessages` 加密发给请求设备。Agent 发请求时刚建（或刚用过）的 Olm 会话，就是两边之间最新的那条，Agent 一定解得开。

人的设备不在线时，请求在服务器上排队，网页端或桌面端下次同步到就回答。

## 威胁与应对

| 威胁 | 应对 |
| --- | --- |
| 冒充 Agent 骗人的设备交出密钥 | 只认 Olm 送达、由主人签名、此刻在房间里、带在线状态事件的 Agent 设备；Olm 本身保证发送设备的身份 |
| 新成员借此读加入前的消息 | 这正是房间“成员可看全部历史”的设置允许的；历史不对成员开放的房间不给。维护者 2026-09-29 明确选择人的旧消息也给 |
| 塞假密钥给 Agent | 只接受我们请求过的、发送设备就是会话创建者、由主人签名的应答；假会话解不开真消息，也冒充不了别的发送者 |
| 大量请求拖垮人的设备 | 按请求设备和房间限频，按这台设备限总数；只处理 Agent 的请求 |
| 旧消息被当成新消息回复 | 重读的消息只进历史，不进收件箱 |

## 交付计划

每一项一个 PR，CI 全绿就合并。

1. **设计**：本文。
2. **Agent 这边**，分两个 PR：
   - 2a matrix-adapter：发现、请求、导入，Matrix 端口加“按事件 ID 重读”和“取走有新密钥的房间”（2b 里改成“取走新导入的会话”，并加上“请求这些会话的密钥”）。真实 Synapse 集成测试：Agent A 先在加密房间里发消息，Agent B 之后才被邀请加入；B 请求、A 应答，B 导入后重读，能读到 A 在它加入前发的消息，而且判为可信。
   - 2b Bridge 核心与存储：隔离“解不开”的事件时按观察顺序预留序号；有新密钥时重读这些事件，用预留的序号写进消息记录；Bridge 启动后对仍隔离的事件重新请求一次。
3. **人这边**：网页端与桌面端应答 Agent 的请求。单元测试覆盖各条规则；真实环境里由第 2 步的 Agent 请求人的设备来验证。
4. **网络 Agent**：不做（维护者 2026-10-05 定，见状态）。
