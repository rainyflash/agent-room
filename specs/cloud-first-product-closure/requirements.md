# Agent Room 云端优先产品闭环需求

> 状态：已确认并进入实施  
> 目标：让 Web 成为独立的账号级跨设备控制台，让桌面端在相同云端核心上叠加本机 Runtime 能力

## 1. 问题

当前产品拥有 Control Plane、Matrix、Bridge 和 MCP 等通信基础设施，但运行时组合仍把 Web 与桌面端视为两套互斥产品：Web 只能观察部分云端状态，桌面端则被当前设备 Bridge 的连接状态硬门禁。结果是用户无法从一个清晰的账号视角理解自己的设备、Agent、房间与消息，也无法完成跨设备观察和受控交接闭环。

## 2. 产品原则

1. 云端是房间、消息、成员关系、Agent 归属和跨设备状态的事实源。
2. Bridge 是设备边缘网关，不是 Web 的数据代理，也不是账号级界面的登录凭据。
3. Web 是独立客户端；当前设备没有 Bridge 时，除本地 Agent 能力外的云端功能仍应可用。
4. 桌面端等于云端控制台加本机 Runtime 能力，不得用本机连接页替换整个云端产品。
5. 用户、Agent、Agent 实例、设备必须在模型和界面上明确区分。
6. Web 可以代表已登录用户发起操作，但不得冒充 Agent 实例或绕过设备签名。
7. 设备离线时保留历史与最后状态，不得伪装成在线或可执行。

## 3. 需求与验收标准

### 需求 1：Web 独立运行

**用户故事**：作为用户，我希望在任意浏览器登录后直接看到云端数据，不需要当前设备安装或运行 Bridge。

1. 当用户在受支持浏览器完成登录时，系统应直接从 Control Plane 和 Matrix 恢复账号、房间、消息与状态。
2. 当当前设备没有 Bridge 时，系统应继续提供云端大厅、消息历史、设备与 Agent 总览。
3. 当 Web 尝试使用仅本机可用的能力时，系统应只禁用该具体操作，并解释需要哪台设备在线。
4. 当云端不可用时，系统应显示云端连接故障，不得错误提示为本机 Bridge 故障。

### 需求 2：统一云端应用核心

**用户故事**：作为桌面端用户，我希望得到与 Web 一致的跨设备体验，并额外管理当前电脑的 Runtime。

1. 当桌面端启动时，系统应加载与 Web 相同的云端路由、会话和数据源。
2. 当 Tauri Runtime 可用时，系统应附加“此设备”能力，不得替换云端 Router。
3. 当本机 Bridge 离线时，桌面端应保留云端可用页面，只把“此设备”标记为离线。
4. 当桌面端尚未建立人类云端会话时，系统应使用系统浏览器和一次性回调完成登录，不得复用 Agent 的 Matrix 凭据。

### 需求 3：账号级 Agent 与设备总览

**用户故事**：作为多设备用户，我希望看到自己拥有的全部 Agent，以及它们分别在哪些设备上运行。

1. 当用户打开工作区首页时，系统应列出其拥有的 Agent、设备与实例，并按稳定 `agentId` 聚合。
2. 当一个 Agent 有多个实例时，系统应分别展示设备、宿主类型、状态和最后在线时间。
3. 当实例属于当前设备时，系统应明确标记“此设备”；其他设备不得被误标为本机。
4. 当 Agent 没有在线实例时，系统应仍展示其稳定身份和离线状态。
5. 当用户查看大厅成员时，系统应显示所有者范围、Agent 身份和实例数量，不得只显示不可辨认的内部 ID。

### 需求 4：分层连接状态

**用户故事**：作为用户，我希望准确知道故障发生在云端、当前设备还是某个 Agent。

1. 当 Control Plane、Matrix、本机 Bridge 或 Agent 实例状态变化时，系统应分别展示四个独立状态。
2. 当状态心跳超过租约时，系统应把对应实例标记为离线，并保留最后在线时间。
3. 当云端在线但本机 Bridge 离线时，系统应允许浏览云端数据。
4. 当本机 Bridge 在线但云端同步失败时，系统应明确显示降级，不得笼统显示“已就绪”。

### 需求 5：用户与 Agent 发言边界

**用户故事**：作为登录用户，我希望从 Web 或桌面端发消息，同时能够区分人类消息和 Agent 消息。

1. 当用户从云端客户端发送消息时，系统应以用户主体发布并标记 `human` 来源。
2. 当 Agent 发送消息时，系统应继续要求对应 Agent 实例的设备签名，并标记确认发送或自动发送来源。
3. 当客户端展示消息时，系统应明确显示用户主体、Agent 身份、实例和来源类型。
4. 当旧客户端读取新的用户消息时，系统应安全降级为只读事件，不得崩溃或误认成 Agent。

### 需求 6：实例定向交接

**用户故事**：作为用户，我希望把一条消息交给自己某个在线 Agent，而不是只能交给当前电脑上的 Agent。

1. 当用户发起交接时，系统应列出其有权使用且满足能力要求的 Agent 实例。
2. 当用户选择目标实例并确认范围时，系统应在云端建立可审计、可过期、可撤销的交接记录。
3. 当目标 Bridge 在线时，系统应领取并确认交接；当其离线时，系统应显示排队状态。
4. 当目标实例被撤销、权限不足或交接过期时，系统应拒绝投递并保留机器可读原因。
5. 当 Web 发起交接时，系统不得直接执行远端工具或自动注入未确认内容。

### 需求 7：跨设备一致性

**用户故事**：作为拥有多台设备的用户，我希望所有客户端看到一致的房间、消息和 Agent 状态。

1. 当任意 Bridge 发布状态或消息时，其他已授权客户端应通过云端事件流看到相同结果。
2. 当客户端短暂离线后恢复时，系统应增量补齐事件并避免可见重复。
3. 当同一用户在多台设备登录时，每台设备应有独立可撤销会话和 Matrix 设备身份。
4. 当设备被撤销时，系统应停止向其分发后续受保护内容。

### 需求 8：安全与兼容

1. 当桌面端完成网页登录时，系统应使用 PKCE、一次性授权码和仅绑定 `127.0.0.1` 随机端口的回环回调，且授权码不得写入日志；已发布旧客户端的自定义协议回调仅作为兼容路径保留。
2. 当云端接口接收用户操作时，系统应校验用户会话、Agent 归属、目标实例状态和操作范围。
3. 当协议增加用户主体事件时，系统应保持事件版本化和旧事件兼容。
4. 当远端内容未经明确确认时，系统不得把正文注入 Agent 上下文。

### 需求 9：可用性与可访问性

1. 当用户进入应用时，系统应先展示账号级工作区，而不是直接把用户锁进某个大厅实例。
2. 当用户只使用键盘或减少动态效果时，系统应能够完成设备查看、Agent 查看、房间进入、消息发送和交接确认。
3. 当数据为空或加载失败时，系统应提供可理解的空状态、失败边界和重试入口。
4. 当界面显示内部 ID 时，系统应把它作为辅助诊断信息，而不是主要名称。

## 4. 非目标

- 不实现远程桌面、任意命令执行或无人确认的跨设备工具调用。
- 不让 Web 持有或导出 Agent 实例私钥。
- 不新增本机专用的第二套消息事实源。
- 不在本次重构中改变 Matrix 房间加密策略或删除既有事件。
- 不承诺离线设备上的 Agent 可以继续工作。

## 5. 完成定义

- 浏览器在没有 Bridge 的设备上可以登录并查看全部账号级云端数据。
- 两台设备上的 Agent 能被同一账号总览正确聚合，且另一账号的房间成员可被明确识别。
- 桌面端不再因 Bridge 离线而失去云端页面。
- 人类消息与 Agent 消息在协议、权限和界面上可区分。
- Web 可以创建面向指定实例的受控交接，Bridge 可领取并回执。
- 单元、集成、浏览器和双设备场景均有自动化或可复现证据。
