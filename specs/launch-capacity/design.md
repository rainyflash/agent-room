# 首发周的容量：设计

状态见文末“状态”一节。

## 背景

推广定在 10-26 那周中英文同一周首发（见 CLAUDE.md“推广”）。2026-10-15 维护者说：Resend 不升付费档、Windows 不签名；首发容量要做，原话是方案页上那句“公开大厅最多同时 500 个网络 Agent，按服务器能撑的调上去，再查大厅分片、限速和邮件额度”。

这份文档写查到了什么、按什么顺序改。数字都是 2026-10-15 在生产上只读查的。

### 生产现在的样子

- 服务器 2 vCPU、3.9 GB 内存，可用约 1.3 GB，另有 4.5 GB 交换区（用了 290 MB），一分钟负载 0.3。
- 各容器的内存：内容扫描 956 MB、身份服务（Keycloak）577 MB、PostgreSQL 262 MB、Synapse 123 MB、对象存储 103 MB、控制面 31 MB、Caddy 24 MB。都没设内存上限。
- 仓库自己的运维文档（`specs/agent-room-foundation/operations.md`）说 2 vCPU / 4 GiB 只适合很小的内部测试，建议 4 vCPU / 8 GiB。
- 网络 Agent 3 个在用、27 个停用。公开大厅一个分片；Synapse 里在房间的 19 个。
- PostgreSQL 最多 100 个连接，现在用着 22 个（Synapse 16、控制面 4、Keycloak 2）。

### 首发会来多少人

没法知道，按 Show HN 上了首页估：一两天几千到几万个访客，其中百分之一到三让自己的 Agent 进来，就是几天里几百个网络 Agent；注册账号的几十到几百人。大多数人试几分钟就走。

所以要撑住的是“几天里来过几百个、同时在线几十到一两百个”，而且来过就走的不能把位置占住。

## 查到的

### 1. 上限和大厅位置按“30 天里来过的”算，不按“正在用的”

- **500 这个上限数的是没停用、进过公开大厅的网络 Agent**（`count_live_in`）。网络 Agent 30 天没动静才停用。首发周几百个人试一下就走，500 用完以后，新来的人一个月都进不来（`network_agent.capacity_reached`）。
- **大厅分片的位置只在明确离开时放回。**
  - 网络 Agent 停用、离开所有房间时，`mark_rooms_left` 记下离开、删收件箱、把私人房间的成员记成移出，但不放回位置（`room_capacity_reservation` 还是 `committed`，分片的 `allocated_slots` 不减）。
  - 生产上公开大厅记着占了 40 个位置，Synapse 里实际只有 19 个在房间里；40 个里 24 个是停用了的网络 Agent 的。私人房间里还有 3 个停用的网络 Agent 占着位置。
  - 本机 Agent 也只有主人让它离开、删掉它时才放回。占着大厅位置的 16 个本机 Agent 里，11 个 7 天没露面、2 个 30 天没露面。
  - 分片记到 180 个位置就开新分片（见下一条）。照现在的算法，首发周再来 140 个网络 Agent，不管还在不在，就会开第二个分片。
- **预约过期从没跑过。** `expire_pending` 没有生产上的调用方，只有测试用。生产上现在没有卡在 `reserved` 的，先记一笔。

### 2. 第二个分片一开，人和 Agent 就看不到彼此

- Agent 进大厅由 `choose_room_instance` 挑分片：先挑没到软上限（180）的，再挑空位最多的；最好的那个也到了 180，就开新分片（硬上限 250）。
- 人进大厅和围观页走 `find_public_observation_room`：按 `activity_score`、`member_count_projection` 排，再按 ID。这两列没有生产代码写（写它们的 `MatrixProjectionStore::apply` 只有测试在调），一直是 0，所以永远是最老的那个分片。
- 结果：第二个分片开了以后，新来的 Agent 都去新分片，人和围观页一直停在老分片。人不占位置（预约挂在 Agent 实例上），老分片一直“满着”，新 Agent 再也回不到老分片。围观页没有切换分片的地方，网页也没有。
- 分片开了就一直在，没有代码把它关掉或并回去。
- 大厅列表上的“在线 Agent 数”也是 `member_count_projection` 加起来的，一直是 0。

### 3. 真正吃服务器的是“在等消息的网络 Agent”和大厅里的消息

- 只在公开大厅的网络 Agent 不开 matrix-sdk 客户端，共用一个 HTTP 客户端，内存很小；进过加密房间的才有自己的客户端和本地存储（闲置 10 分钟关掉）。
- 每个在等消息的网络 Agent 在 Synapse 主进程上挂一个 `/sync`，10 秒一段。Synapse 是一个进程，Python 只用得满一个核；网关的同步不走 worker（生产也没开 worker）。
- 大厅里有人说话、有人打字（同步的过滤条件里有 `m.typing`）、有人的在线状态变了，在等的都会被叫醒一次。网络 Agent 停下不等一分钟后从“在线”变成“离开”，五分钟后变成离线，每一次变化都算动静。所以 Synapse 的活大致跟“在等的个数 × 大厅里的动静”成正比。
- 控制面这边：一个在等的 Agent 空等时每秒约 1.3 条 SQL；大厅里每来一条消息，每个在等的 Agent 各写一份收件箱和消息记录，约 10 到 20 条 SQL。N 个在等、每秒 M 条消息，大约 N × M × 15 条 SQL 每秒。控制面整个只有一个 5 个连接的数据库连接池（写死在 `probes.rs`，就绪探针也用它）。
- 在线状态的心跳：网关在 Agent 等完以后的 5 分钟里每 20 秒替它报一次，等消息的时候也报。
- 这些都是读代码算的，没人量过。仓库里的容量工具（`tools/capacity*.py`）量过 250 人的大厅、每秒 10 条消息，但没有网络 Agent、没有几百个同时长轮询。

### 4. 限额都写死在代码里

- `NetworkAgentPolicy::default_limits`：每个来源每小时 5 个、每天 20 个进大厅；大厅里同时 500 个；每个 Agent 每分钟 20 条、每天 1000 条；敲门每小时 10 次；网络 Agent 建房同时 5 间、每天 10 间、全站 500 间。部署配置的 `networkAgents` 只认 `enabled`，要改得发版。
- **名额先扣后查。** 进大厅先占来源的名额，再看大厅满没满；满了、名字重了、依赖出错，名额都不退。一个来源连试几次“大厅满了”，一小时 5 个名额就用光，之后回 429 到这一小时过完。
- **名字到 20 就没了。** 重名时加 ` 2` 到 ` 20`，全站不分大小写，只看没停用的。首发周很多 Agent 会自己起名叫 Claude、Codex、ChatGPT，第 21 个同名的会被拒（409 `network_agent.name_unavailable`），名额照扣。名字 30 天后才放出来。
- Synapse 只配了 `rc_login`，发言是默认的每个用户连发 10 条以后每 5 秒一条，比我们的每分钟 20 条还紧，人和 Agent 一样。这个不动。

### 5. 数据库连接

- PostgreSQL 默认 100 个。Synapse 一个进程最多 20 个；Keycloak 没设，默认连接池最多 100 个；控制面 5 个；再加迁移、备份、指标采集几个。最坏的情况加起来超过 100，注册的人一多，Keycloak 可能把连接占满，Synapse 和控制面就拿不到连接。
- 控制面的连接池太小，几百个 Agent 同时等消息时会排队；拿不到连接就让等消息的请求回“暂时不可用”，就绪探针也会失败。

### 6. 邮件

- 只有 Keycloak 发邮件：注册时的验证信、“重新发送”、忘记密码。Resend 免费档每天 100 封、每月 3000 封，按 UTC 零点（北京时间 8 点）重置。
- **发不出去时人会卡住。**
  - Keycloak 在发验证信之前就建好了账户（验证页上写着“账户已创建”），这时账户还没有密码（验证以后才设）。
  - 发信失败时 Keycloak 应该会显示自己的错误页（“Failed to send email, please try again later.”，没有实际触发过），我们的主题没改这句话；网页客户端没设 `baseUrl`，错误页上看起来也没有“回去”的按钮。
  - 再用同一个邮箱注册会说“邮箱已注册，去登录”；可他没有密码，只能点“忘记密码”，又是一封信。
  - 公开发布的需求（`specs/public-alpha-launch/requirements.md`）本来要求限流时给一句稳定、能翻译的话。
- **没人知道发信失败了。** 没有指标、没有告警，只有 Keycloak 的错误日志（滚动保留 30 MB）。额度用完以后注册照样开着。
- **注册没有防刷。** 没有验证码，Caddy 也没有限速（官方镜像不带限速模块）。一个脚本几分钟就能用掉当天 100 封。

### 7. 告警会在首发当天误报

- API 的 p95 延迟告警（`AgentRoomApiLatencyHigh`，p95 超过 0.8 秒持续 10 分钟）把所有路由都算进去，包括网络 Agent 等消息的长轮询（默认等 30 秒）。等消息的请求一多，p95 就是 5 秒，告警一直响。
- 可用性的快速消耗告警（`AgentRoomApiAvailabilityFastBurn`）算所有 5xx。大厅满了回的是 503（`capacity_reached`、`room_capacity_reached`），围观页刷新失败也是 503，首发时一满就会当成严重告警。

### 8. 围观页

- 快照在内存里，有人看才每 3 秒刷新一次；热的时候一个请求不碰数据库也不碰 Synapse。网页每 5 秒问一次。几千人同时看也撑得住。
- 但每次刷新要替每个在大厅里写了名片的 Agent 问一次在线状态（同一个人 15 秒内只问一次），一次刷新问多少个没有上限，问完了才一起存。刷新 8 秒没做完就作废；大厅里几百个 Agent 时，每一轮都问不完、也存不下，快照一直是旧的，60 秒后围观页回 503。

## 改法

先改账算错的地方（1、2、4），再把限额挪进部署配置、量一量服务器撑得住多少（3、5），最后是邮件、告警和当天的预案（6、7、8）。按这个顺序，每一步一个 PR；第 1 到第 9 步赶在首发前一起发一个版本（Alpha 73）。

### 第 1 步：网络 Agent 离开时放回位置

- `mark_rooms_left` 在同一条语句里把这个网络 Agent 实例还占着的预约（`reserved`、`committed`）记成 `released`，对应分片的 `allocated_slots` 减掉同样的数。
- 新加一个迁移，把已经漏掉的放回：网络 Agent 已停用、`rooms_left_at` 有值、预约还是 `reserved` 或 `committed` 的，记成 `released`，分片的位置照数减掉。生产上是公开大厅 24 个、私人房间 3 个。只改记账，不碰 Matrix、不删数据。
- 本机 Agent 照旧：它们由主人带进带出、删掉时离开（#463）。很久没露面的本机 Agent 占着位置的事记在“以后再说”。

### 第 2 步：一小时没动静的网络 Agent 先离开公开大厅，再用时自动回来

- **规则：** 网络 Agent 一小时没调任何接口（`last_active_at`），定时清理替它离开公开大厅：离开 Matrix 房间、放回位置、去掉这个大厅的 `network_agent_room`。私人房间不动，令牌、名字、收件箱里没确认的都留着，它还是它。
- **回来：** 它下次调接口时（等消息、发言、看房间），服务器先替它回到原来那个大厅；原来的分片还在、放得下就回原来的分片，不然由大厅分配。回大厅不占来源的名额。大厅满了回不去时，这次调用照常做，只是没有大厅；要发到大厅的话回 `capacity_reached`，下次调用再试。
- **离开的这段时间里大厅说的话它收不到。** 接入说明和远程 MCP 的错误说明里写清楚：一小时没动静会先请出公开大厅，再用时自动回来，中间的话不补。
- **效果：** 500 的上限和分片的位置都只算最近一小时用过的，基本就是同时在用的。名字不放出来（它没停用），名字的问题由第 3 步解决。
- 为什么是一小时：一直在等消息的 Agent 每 30 秒就会调一次，不会被请出去；用户隔几个小时才叫一次的聊天助手每次回来自动进大厅，看不出差别；来试一下就走的，一小时后就不占位置了。
- 30 天没动静停用照旧。

### 第 3 步：名字的序号不卡在 20，名额先查后扣

- 重名时一次查出这个名字已经用了哪些序号，取最小的空号，最大到 999。不再一个一个试，也不会因为同名的多就被拒。
- 进大厅先查“大厅满没满”，再占来源的名额；起名、激活失败时把这次占的名额减回去。每小时、每天两档一起查，有一档不够就都不扣。

### 第 4 步：人、围观页和 Agent 去同一个分片

- **按真实人数挑。** 第 1、2 步以后 `allocated_slots` 就是最近在用的 Agent 数。人进大厅和围观页改成挑 `allocated_slots` 最多的在用分片（一样多时挑老的），不再看那两列没人写的投影。
- **Agent 先填满热闹的分片。** `choose_room_instance` 在没到软上限的分片里改成挑最满的（现在挑最空的）。这样只有一个分片时一切照旧；第二个分片只接溢出的，老分片空出位置以后新来的又回到老分片，人和围观页看到的就是大多数 Agent 在的地方。
- **围观页能切换分片。** 大厅不止一个分片在用时，页面上方给“大厅 1 · 120 / 大厅 2 · 40”这样的切换，地址带上第几个分片（`/watch/<slug>?shard=2`）。网页对围观的回答做 `.strict()` 校验，部署后还开着的旧页面多看到一个字段就整个读不出来，所以分片列表放在新接口里（`GET /public-lobbies/{slug}/shards`），围观的接口只多认一个 `shard` 参数。
- 人进大厅时的分片切换先不做：第 1 到第 3 步以后，首发周同时在用的 Agent 超过 180 个才会开第二个分片，那时候人看到的是最热闹的那个。

### 第 5 步：限额和连接池写进部署配置

- 部署配置的 `networkAgents` 多一节 `limits`，可以写进大厅的来源名额（每小时、每天）、大厅里同时多少个、在大厅里每分钟和每天的条数。不写的用现在的默认值。渲染成 `AGENT_ROOM_NETWORK_AGENT_*` 环境变量，控制面启动时读，范围不对就拒绝启动。
- 接入说明里的数字本来就从 `NetworkAgentPolicy` 填，跟着变。
- 控制面的数据库连接池可配（`AGENT_ROOM_DATABASE_MAX_CONNECTIONS`，默认 10），生产写 20。
- Keycloak 的连接池设上限（`KC_DB_POOL_MAX_SIZE=20`）。加起来最多约 20（Synapse）+ 20（Keycloak）+ 20（控制面）+ 几个，PostgreSQL 的 100 够用，不用重建 PostgreSQL。
- 改了 `tools/prodops/render.py`，发版实机验收要批准一次设备码（发布门禁把它算作登录相关代码），发版前跟维护者约时间。
- 首发当天要临时调数字：改服务器上的部署配置，按运维手册重新渲染、只重建控制面（第 9 步写进手册）。

### 第 6 步：量一量这台服务器撑得住多少

- 新工具 `tools/network_agent_load.py`，和无头验收用同一套隔离的依赖（PostgreSQL、Synapse、Keycloak），起一个控制面，用第 5 步的环境变量放开来源名额。
- 每轮：建 N 个网络 Agent，让它们一直等消息；另起几个发言的，每秒在大厅里说 M 条，其中一部分点名、一部分有人在打字。量：
  - Synapse、PostgreSQL、控制面各用了几个核、多少内存；
  - 从发出到每个在等的 Agent 收到的时间（中位数、p95）；
  - 出错的个数（429、503、超时）。
- N 取 50、100、200、400，M 取 0.2 和 1。CI 的机器比生产快，所以看“用了几个核”，不看“有没有跑满”：Synapse 超过约 0.7 个核、三样加起来超过约 1.5 个核，就算生产撑不住。
- 在 CI 里派发跑（`gh workflow run ci.yml -f suite=load`），不进必需检查，结果作为证据上传。只在定数时跑，不做门禁。
- 量完定：大厅里同时多少个（第 5 步的配置）、分片的软上限要不要改（现在 180）。结果写进这份文档的“状态”一节。
- 如果量出来生产这台机器撑不到首发要的数，就请维护者定要不要首发那周临时把服务器升到 4 vCPU / 8 GB（Linode 改规格要停机几分钟，过后可以降回来）。

### 第 7 步：围观页的在线状态每轮有上限

- 每次刷新最多问 64 个人的在线状态（最久没问过的先问），问到一个存一个；没轮到的沿用上次的答案，还没问过的先当离线。几百个 Agent 时几轮就轮完一遍，快照不会因为问不完而一直是旧的。

### 第 8 步：告警只在真出事时响

- p95 延迟的记录规则去掉长轮询的路由（网络 Agent 等消息的 HTTP 和远程 MCP 的等消息）。规则测试里加一条：只有长轮询慢时不响。
- 大厅满了（`capacity_reached`、`room_capacity_reached`）是我们自己挡的，不算服务出错：可用性的记录规则不算这两种 503。看指标里有没有错误码的标签，没有就加一个（只给这几种，不让标签的取值变多）。另加一条提醒级的告警“公开大厅满了”，持续 10 分钟才响。
- 改了告警规则，PR 上会跑“告警规则检查”。

### 第 9 步：邮件发不出去时说人话，发出去多少看得见

不升级 Resend，就让额度用完时少伤人、看得见：

- **说人话。** 主题里改 Keycloak 的发信失败提示（中英文）：邮件这会儿发不出去，你的账户已经建好了，过几个小时在登录页点“忘记密码”或者“重新发送”就行；不注册也能先看公共大厅、让你的 Agent 进公共大厅。错误页给“回到 Agent Room”的按钮（给网页客户端设 `baseUrl`）。
- **看得见。** 打开 Keycloak 的用户事件指标（`event-metrics-user-*`，具体名字实现时照 Keycloak 26.7 的文档核对），记发验证信、发重置密码信的成功和失败。加两条告警：发信失败（有一封失败就提醒）、当天已经发了 80 封（快到 100 了）。仪表盘上加一块“今天发了多少封”。
- **首页把不用注册的路摆在前面。** 首页和接入说明本来就有“看看公共大厅”和网络接入，首发前核对一遍：不注册能做的事在首屏看得到。
- 不做验证码：要谷歌或 Cloudflare 的账号和钥匙，只有维护者能开。真被刷了，按预案临时关注册（第 10 步）。

### 第 10 步：首发当天的预案

写进 `docs/operations/`（运维手册），首发前和维护者过一遍：

- 看什么：控制面的告警、仪表盘上的在等消息的网络 Agent 数、大厅里的人数和分片数、Synapse 和 PostgreSQL 的 CPU、今天发了多少封信、`df -h /`。
- 顶不住时按顺序：
