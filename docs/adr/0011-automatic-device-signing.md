# ADR 0011：人的设备自动签名，签名用的钥匙由服务器保管

- 状态：已采纳
- 日期：2026-10-02
- 修改：[ADR 0009](./0009-encryption-trust-on-first-use.md) 第 4 条“已有公开身份但本机缺私钥时，两边都不覆盖它，交给确认或恢复流程”。对人的设备改为自动签名，必要时重建一次签名身份。ADR 0009 的其余决策不变。

## 背景

ADR 0009 之后，Agent 只把房间密钥发给由主人签名的设备。人的新设备要签名，只有两条路：

- 输入恢复密钥；
- 在另一台已签名、手里有签名私钥的设备上核对。

维护者 2026-10-02 的实际情况是两条都走不通：

- 账户从没设过恢复密钥；
- 签名私钥不在任何一台设备上。

所以网页端那台永远签不了，桌面端还每次误报“需要签名”。就算走得通，这一步也和“一个按钮就能聊”的产品方向相反。维护者明确表示不需要这一档保密：“你以为你在做国家机密？”

## 决策

1. **服务器保管签名用的钥匙。** 账户的密钥存储钥匙（以前的“恢复密钥”）由控制面封存保管，只交给本人已登录的会话。人看不到，也不用管它。
2. **设备登录后自动签名。** 网页端和桌面端登录后，用这把钥匙打开密钥存储、签好这台设备、加载服务器端密钥备份，并在后台找回加密历史。
3. **找不到可用的钥匙就重建一次签名身份。** 账户有签名身份、服务器却没有能打开它的钥匙时（以前设过服务器不知道的恢复密钥，或者签名私钥已无处可寻），由当前设备重建签名身份，并把新钥匙交给服务器。Synapse 换签名身份要交互认证，由控制面以应用服务的身份代传新的签名公钥（见下面“修订”）。
4. **界面上不再有恢复密钥和设备核对。**
5. **Agent 对自己的主人自动撤销旧核对。** 核对过安全码的 Agent 遇到主人重建身份，不再拒绝发送，自动接受新身份；对别人仍按 ADR 0009 第 3 条处理。

## 后果

- 人在任何设备上登录都能直接收发加密消息，换设备时历史自动回来，不会碰到任何加密相关的操作。
- **代价：服务器（部署方）能替账户签设备、读服务器端备份里的房间密钥，因而能读这个账户在加密房间里的消息。** 这与 [ADR 0010](./0010-network-agents.md) 里“网络 Agent 凭口令进的私人房间，服务器能读到发给它的消息”属于同一档信任。端到端加密此后防的是：
  - 传输和存储层面的泄漏；
  - 没有封存密钥的数据库泄漏；
  - 没登录的人。

  不再防部署方本身。

- 重建签名身份后：
  - 房间里别人的网页端会提示一次“有人的加密身份变了”；
  - Agent 不受影响（matrix-sdk-crypto 0.18 对没核对过的人只记一笔“身份变了”，不影响收发）；
  - 人自己旧设备上、没进服务器端备份的旧会话找不回来。
- 部署要配封存密钥，否则自动签名不可用。生产已经配了，网络 Agent 用的就是它。

## 修订（2026-10-02）

原来第 3 条写的是“控制面用管理接口开 10 分钟豁免”（`_allow_cross_signing_replacement_without_uia`）。实测 Synapse 1.159：这个豁免只在接了 MAS（认证交给 Matrix Authentication Service）时起作用；没接 MAS 的部署（我们就是），换签名身份一律要交互认证。唯一的例外是应用服务发的请求（MSC4190）。

所以改成：

- 设备照旧在本机生成新的签名私钥。
- 上传新签名公钥的那一个请求，改送控制面 `POST /account/encryption-reset`。
- 控制面核对这些公钥都属于登录的本人，再以应用服务的身份、冒充本人，转给 Synapse。

为此，应用服务注册多了一个覆盖本服务器所有用户的非独占命名空间：应用服务令牌从此能冒充本服务器的任何用户。控制面本来就持有 Synapse 管理员令牌（能直接替任何用户登录），所以控制面能做的事没有变多，仍在上面“代价”一条之内。

这把令牌只在控制面和 Synapse 之间用，不出后端。

## 重新评估的条件

- 出现需要对抗部署方的场景，比如别人托管、你又不信任的服务器。这时应提供“钥匙只在本机”的选项，也就是退回 ADR 0009 的恢复流程，作为这类部署的默认值。
- Matrix 规范或 SDK 提供了不经第三方保管、又不需要人操作的设备互认方式（例如同一账户设备之间的自动核对），就改用它，撤掉服务器保管。
