# ADR 0009：加密房间首次见到即信任，核对安全码改为可选

- 状态：已采纳
- 日期：2026-09-21
- 取代：[私聊验收](../../specs/human-agent-conversation/private-chat-verification.md)中「发送前必须与每位参与者完成 SAS 核对」的要求。ADR 0008 的其余决策不变。

## 背景

私人房间和私聊是端到端加密的。此前网页和 Bridge 都要求发送方先与房间里的**每一位**参与者完成 SAS 安全码核对：

- 网页在发送前检查每个参与者；
- Bridge 发送前逐个检查，且只把房间密钥发给核对过的设备（`OnlyTrustedDevices`）；
- Agent 收到未核对的人发来的消息时隔离不投递。

一个有三位 Agent 的私人房间，要在三个 Agent 宿主里各核对一次安全码才能发出第一条消息。维护者实际使用时被这一步挡住，无法聊天。另外，Agent 从不自动建立自己的加密身份，没手动调用 `establish_identity` 的 Agent 根本进不了加密房间。

## 决策

采用 Matrix MSC4153 的做法，与 Element 等客户端的默认行为一致。

1. **只信任由主人签名的设备。** 房间密钥只发给由其主人加密身份交叉签名的设备：网页用 `OnlySignedDevicesIsolationMode`，Bridge 用 `CollectStrategy::IdentityBasedStrategy`。收到的消息也只在发送设备由主人签名时视为可信：`VerificationState::Verified` 或 `Unverified(UnverifiedIdentity)`。未签名、未知或发送者不符的设备仍被排除或隔离。
2. **首次见到即记住身份，不要求核对。** 发送前只检查本机设备已由自己的身份签名。不检查参与者是否核对过。
3. **身份变化要确认。**
   - 网页：房间里有人的加密身份变了时，第一次发送提示并记下这些人。用户按「确认并发送」后，记住新身份（曾核对过的一并撤销核对要求）再发送。
   - Bridge：核对过的参与者换了身份时拒绝发送，返回 `bridge.security.identity_changed`，重新核对后恢复。
4. **身份自动建立。**
   - Agent 上线时，若从未建立过加密身份，Bridge 自动建立；发送前再检查一次。
   - 网页账户第一次同步完成后，若从未建立过身份，自动建立。
   - 已有公开身份但本机缺私钥时，两边都不覆盖它，交给确认或恢复流程。
5. **SAS 核对保留为可选的更强保证。** 核对过的人一旦换身份，发送会被拦下，直到重新核对或确认。

## 后果

- 私人房间和私聊里，人与 Agent 不做任何核对就能收发，加密不变，服务端仍读不到正文。
- 代价是首次见到某个参与者时，信任的是服务端给出的身份。服务端若在首次接触前伪造身份，不核对就发现不了；首次接触之后的身份变化都会被发现并提示。需要更强保证的用户可以核对安全码。
- 服务端伪造的**未签名**设备拿不到房间密钥，它发的消息也不会被 Agent 当作可信。
- 网页和桌面端内嵌网页、Bridge、MCP 需要同一版本才能完整生效：旧 Bridge 仍会隔离未核对的人发来的消息。

## 重新评估的条件

- 有证据表明服务端在首次接触前伪造身份是现实威胁，例如出现需要对抗运营方的部署；此时应让核对成为该类房间的默认要求，而不是恢复对所有房间的强制核对。
- 桌面端能经本机可信通道自动互认本机 Agent 的身份时：同一台电脑上的人和 Agent 可以不经服务端完成核对，首次接触的信任缺口随之消失。
- Matrix 规范或 SDK 调整 MSC4153 的身份变化处理时，按新的接口对齐提示与确认方式。
